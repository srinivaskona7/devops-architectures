Section 1 of 19

Observability pillars and what to measure

8 concepts · about 45 minutes

You cannot fix what you cannot see. This section gives you the vocabulary and the three or four checklists that decide what to measure before you touch any tool.

Goals
  • Tell monitoring from observability and pick the right signal for a question
  • Apply the four golden signals and the RED and USE methods
  • Choose metric types and decide what is worth measuring
1.1

Monitoring versus observability

In plain words

Monitoring watches things you already know can go wrong and tells you when they do. Observability is how well you can ask new questions of a running system, using the data it emits, without shipping new code.

The problem it solves

Dashboards built for yesterday's failures stay green while a new kind of failure hurts users. In a microservice system most incidents are unknown unknowns.

What it does

  • Monitoring answers "is it broken" with known checks and alerts.
  • Observability answers "why is it broken, for whom, since when" using high-detail telemetry you can slice by any attribute.
  • Both rely on the same raw material: metrics, logs and traces.
Check yourself
Which one lets you investigate a failure nobody predicted?

Observability, because rich telemetry can be sliced in new ways after the fact.

1.2

The three pillars

In plain words

Metrics are numbers over time. Logs are timestamped event records. Traces follow one request across services. Each is good at a different job.

The problem it solves

Using only one signal forces awkward answers: counting errors from logs is expensive, and reading one log line cannot show which of eight services was slow.

What it does

  • Metrics are cheap, compact and ideal for alerting and trends. They lose per-request detail.
  • Logs carry full detail for one event but cost more to store and search.
  • Traces show the path and timing of one request, linking services together.
  • The usual workflow is metric alert, then trace to find the service, then logs to find the line.
1.3

The four golden signals

In plain words

Google's SRE book names four signals that describe the health of almost any user-facing service: latency, traffic, errors and saturation.

The problem it solves

Teams drown in hundreds of graphs. You need a short list that will catch most user-visible problems.

What it does

  • Latency: how long requests take. Track successes and failures separately, because a fast error hides slow successes.
  • Traffic: demand on the service, such as requests per second.
  • Errors: rate of failed requests, including wrong content or slow responses counted as failures.
  • Saturation: how full the most constrained resource is, such as CPU, memory, queue depth or connections.
Check yourself
Why measure latency of errors separately?

A quick failure lowers average latency and can hide a real slowdown in successful requests.

1.4

The RED method

In plain words

For every request-driven service, graph three things: Rate, Errors and Duration. It is the golden signals trimmed for microservices.

The problem it solves

With dozens of services you need one identical dashboard layout per service so that anyone on call can read any of them.

What it does

  • Rate is requests per second, errors is failed requests per second (or a ratio), duration is a latency distribution such as p50 and p99.
  • Works for HTTP, gRPC and queue consumers.
  • Saturation is deliberately left to the USE method.

RED in PromQL

promqlRED for an http_server service
# Rate
sum(rate(http_requests_total{job="checkout"}[5m]))
# Errors as a ratio
sum(rate(http_requests_total{job="checkout",code=~"5.."}[5m]))
  / sum(rate(http_requests_total{job="checkout"}[5m]))
# Duration p99
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket{job="checkout"}[5m])))
1.5

The USE method

In plain words

For every resource such as a CPU, disk or network link, check Utilization, Saturation and Errors. Brendan Gregg created it for hunting bottlenecks.

The problem it solves

When a host is slow, guessing at causes wastes time. USE gives a systematic checklist across all resources.

What it does

  • Utilization is the fraction of time the resource is busy.
  • Saturation is extra work waiting, such as run queue length or disk queue.
  • Errors are error counts, such as network drops or disk errors.
  • RED is for services, USE is for infrastructure. Use both.

USE for a Linux node

promqlUSE with node_exporter
# CPU utilization
1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))
# CPU saturation, load per core
node_load1 / count(count by (cpu) (node_cpu_seconds_total))
# Memory utilization
1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes
# Network errors
rate(node_network_receive_errs_total[5m])
1.6

SLIs, what to measure

In plain words

A service level indicator (SLI) is a measurement of how well the service serves users, written as a ratio of good events to all events.

The problem it solves

CPU graphs do not tell you whether users are happy. You need numbers that track user experience.

What it does

  • Good SLIs: availability (non-5xx over all requests), latency (requests faster than 300 ms over all requests), freshness and correctness for data pipelines.
  • Measure close to the user: load balancer or client, not just inside the pod.
  • Keep a short list per service, two to four.
1.7

Metric types

In plain words

Prometheus metrics come in four types: counter, gauge, histogram and summary.

The problem it solves

Using the wrong type gives wrong answers, such as averaging a percentile or graphing a raw counter that only goes up.

What it does

  • Counter only increases (resets on restart). Always use rate() on it.
  • Gauge goes up and down, such as memory in use or queue size.
  • Histogram counts observations into buckets, so percentiles can be computed on the server and across instances.
  • Summary computes quantiles in the client and cannot be aggregated across instances.
Check yourself
Why prefer histograms over summaries for latency in Kubernetes?

Bucket counters from many pods add up, so you can compute a fleet-wide percentile.

1.8

Symptoms versus causes

In plain words

Alert on symptoms users feel (errors, slowness). Use causes (CPU, disk) for dashboards and diagnosis.

The problem it solves

Alerting on every high CPU wakes people for harmless spikes while real outages from other causes go unnoticed.

What it does

  • A symptom alert catches every cause, including ones you never thought of.
  • A cause alert is justified only when it predicts a future symptom, for example a disk that will fill in four hours.
  • Fewer, symptom-based pages reduce alert fatigue.

Prometheus architecture and data model

7 concepts · about 50 minutes

Prometheus is a time series database with a pull-based collector and a query language. It is the default metrics system on Kubernetes.

Goals
  • Describe the Prometheus pull model and its components
  • Read a time series with its labels and understand staleness
  • Write a scrape configuration and check target health
2.1

Prometheus architecture

In plain words

Prometheus is one server that scrapes HTTP endpoints on a schedule, stores the numbers in a local database, evaluates rules, and answers queries. Alerts are sent to a separate Alertmanager.

The problem it solves

Push-based systems need every app to know where to send data and can hide dead apps. A central collector that pulls knows exactly what it expects to see.

What it does

  • Targets expose plain text at /metrics.
  • The server stores samples in its own TSDB on local disk.
  • Rules produce new series or alerts, Grafana and API clients run PromQL.
  • Short-lived jobs use the Pushgateway, which Prometheus then scrapes.
2.2

The data model

In plain words

Everything is a time series: a metric name plus a set of key-value labels, holding a stream of timestamped numbers called samples.

The problem it solves

You need to slice one measurement by many dimensions, such as per pod or per status code, without inventing a new name for each.

What it does

  • http_requests_total{job="api",code="500"} is one series. Change one label and it is a different series.
  • Samples are a 64-bit float and a millisecond timestamp.
  • The name is itself the hidden label __name__.
  • Labels beginning with __ are internal and removed before storage.

Exposition format

textWhat /metrics looks like
# HELP http_requests_total Total HTTP requests.
# TYPE http_requests_total counter
http_requests_total{method="GET",code="200"} 10234
http_requests_total{method="GET",code="500"} 17
2.3

Scraping and scrape configuration

In plain words

Every scrape_interval Prometheus makes an HTTP GET to each target and stores what it returns. A job is a group of targets with the same purpose.

The problem it solves

You need predictable, central control of how often and where data is collected.

What it does

  • scrape_interval is commonly 15s to 60s, and scrape_timeout must be shorter.
  • Prometheus adds job and instance labels to every series.
  • Each scrape also writes up (1 or 0) and scrape_duration_seconds.

A minimal prometheus.yml

yamlprometheus.yml
global:
  scrape_interval: 30s
  scrape_timeout: 10s
  evaluation_interval: 30s
rule_files:
  - /etc/prometheus/rules/*.yml
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]
scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ["localhost:9090"]
  - job_name: node
    static_configs:
      - targets: ["10.0.1.11:9100", "10.0.1.12:9100"]
bashValidate before reload
promtool check config prometheus.yml
curl -s localhost:9090/api/v1/targets | head -c 400
curl -X POST localhost:9090/-/reload   # needs --web.enable-lifecycle
2.4

The up metric and staleness

In plain words

up is a series Prometheus creates for each target: 1 if the last scrape worked, 0 if not. When a series stops appearing, Prometheus marks it stale instead of showing the old value for five minutes.

The problem it solves

You must know when a target disappears. And queries should not show data from a pod that was deleted a minute ago.

What it does

  • up == 0 is the base alert for a broken scrape.
  • A target that vanishes from service discovery produces no up series at all, so use absent() for "should exist but does not".
  • Stale markers end a series cleanly; the default lookback for instant queries is 5 minutes.

Alerts for missing targets

promqlDown and missing
up{job="node"} == 0
absent(up{job="node"})
count(up{job="node"} == 1) / count(up{job="node"}) < 0.9
Check yourself
Why is up == 0 not enough?

If discovery drops the target there is no up series, so the expression returns nothing; absent() catches that.

2.5

Choosing a metric type for instrumentation

In plain words

When you write your own code, the client library gives you counter, gauge, histogram and summary objects. The name and unit conventions matter as much as the type.

The problem it solves

Inconsistent names and units make dashboards impossible to reuse and queries wrong.

What it does

  • Use base units: seconds, bytes, ratios 0 to 1. Put the unit in the name: _seconds, _bytes.
  • Counters end with _total.
  • Never put unbounded values such as user IDs or URLs with IDs into labels.
  • Name format: application_what_unit, for example checkout_orders_total.

Python client example

pythonInstrumenting a service
from prometheus_client import Counter, Histogram, start_http_server

REQS = Counter("checkout_orders_total", "Orders placed", ["status"])
LAT = Histogram("checkout_request_duration_seconds", "Request latency",
                buckets=(0.05, 0.1, 0.25, 0.5, 1, 2.5))

def handle():
    with LAT.time():
        REQS.labels(status="ok").inc()

start_http_server(8000)   # serves /metrics
2.6

Push versus pull and the Pushgateway

In plain words

Prometheus pulls from long-lived services. For batch jobs that finish before a scrape, the Pushgateway holds the last pushed values so Prometheus can still collect them.

The problem it solves

A nightly backup job lives for 90 seconds. It cannot be scraped reliably.

What it does

  • The job pushes its metrics to the gateway at the end.
  • The gateway keeps them until deleted, so stale values can mislead. Add a timestamp metric and alert if it is old.
  • Do not use it as a general push proxy for services; you lose up health checking.

Example

bashPush a success timestamp
cat <<EOM | curl --data-binary @- http://pushgateway:9091/metrics/job/nightly_backup
# TYPE backup_last_success_timestamp_seconds gauge
backup_last_success_timestamp_seconds $(date +%s)
EOM
promqlAlert if no success for 26 hours
time() - backup_last_success_timestamp_seconds{job="nightly_backup"} > 26*3600

Service discovery and relabeling

8 concepts · about 45 minutes

In Kubernetes and autoscaling groups, targets appear and vanish constantly. Prometheus finds them by asking the platform, then relabeling rules decide which to scrape and what labels they get.

Goals
  • Explain why static target lists fail in dynamic environments
  • Configure Kubernetes and EC2 service discovery
  • Use relabeling to filter targets and shape labels safely
3.1

Why service discovery

In plain words

Service discovery (SD) lets Prometheus ask Kubernetes, AWS, Consul or DNS for the current list of targets instead of reading a hand-edited file.

The problem it solves

Pods are replaced every deploy. A static list is wrong within minutes and someone must edit it.

What it does

  • SD mechanisms refresh the target list continuously.
  • Each discovered target arrives with metadata labels that start with __meta_.
  • Relabeling turns this metadata into the final labels.
3.2

Kubernetes service discovery

In plain words

kubernetes_sd_configs has roles: node, pod, service, endpoints, endpointslice and ingress. Each role yields targets of that object type.

The problem it solves

You want every pod that opts in to be scraped without touching Prometheus config.

What it does

  • pod creates one target per container port, with labels such as __meta_kubernetes_pod_name and __meta_kubernetes_namespace.
  • endpoints and endpointslice follow Services and keep pod and service labels.
  • The Prometheus service account needs RBAC get, list, watch on those resources.

Annotation based pod scraping

yamlprometheus.yml pod job
scrape_configs:
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_path]
        action: replace
        target_label: __metrics_path__
        regex: (.+)
      - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        regex: ([^:]+)(?::\d+)?;(\d+)
        replacement: $1:$2
        target_label: __address__
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod
Note

The prometheus.io/scrape annotations are a convention of the config above, not a built-in feature. With the Prometheus Operator you use ServiceMonitor and PodMonitor instead.

3.3

How relabeling works

In plain words

A relabel rule reads a few labels, joins their values with a separator, tests the result against a regular expression, then applies an action.

The problem it solves

Discovery gives you many targets and noisy metadata. You need to choose what to scrape and build clean, consistent labels.

What it does

  • relabel_configs run before the scrape, on target labels.
  • metric_relabel_configs run after the scrape, on each sample.
  • The regex is fully anchored. Default regex is (.*), default separator is ;.
  • Labels starting with __ are dropped after relabeling.
3.4

Relabel actions

In plain words

The action field decides what happens when a rule matches. The common ones are keep, drop, replace, labelmap, labeldrop and labelkeep.

The problem it solves

Without actions you could not remove a target, rename a label or strip a high-cardinality one.

What it does

  • keep and drop filter targets or series by regex.
  • replace writes a new value into target_label using capture groups.
  • labelmap copies labels whose names match a regex, for example all pod labels.
  • labeldrop and labelkeep remove or retain labels by name.
  • Newer versions add more actions such as keepequal, lowercase; check the current docs.
3.5

Dropping noisy metrics

In plain words

metric_relabel_configs can discard series you never use before they hit disk.

The problem it solves

Some exporters emit thousands of series. Storing them costs memory and money and slows queries.

What it does

  • Drop whole metrics by name using __name__.
  • Drop a label that has too many values, but make sure series stay unique afterwards.
  • Always measure first: topk(10, count by (__name__)({__name__=~".+"})).

Example

yamlDropping unused series
scrape_configs:
  - job_name: kubelet-cadvisor
    metrics_path: /metrics/cadvisor
    scheme: https
    kubernetes_sd_configs:
      - role: node
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: container_(tasks_state|memory_failures_total|blkio_.*)
        action: drop
      - regex: id|name
        action: labeldrop
Careful

Dropping a label can merge two series into one with the same labels and cause duplicate sample errors. Test with a small change first.

3.6

AWS EC2 and file based discovery

In plain words

ec2_sd_configs lists EC2 instances through the AWS API; file_sd_configs reads JSON or YAML files that another tool writes.

The problem it solves

Not everything runs in Kubernetes. VMs in an Auto Scaling group must be found automatically.

What it does

  • EC2 SD needs IAM permission ec2:DescribeInstances (use an instance role or IRSA).
  • Instance tags become __meta_ec2_tag_<name> labels, ideal for keep rules.
  • file_sd_configs is the universal adapter: any script can write targets to a file and Prometheus reloads it on change.

Example

yamlEC2 and file discovery
scrape_configs:
  - job_name: ec2-node
    ec2_sd_configs:
      - region: ap-south-1
        port: 9100

PromQL fundamentals

7 concepts · about 55 minutes

PromQL is the query language for Prometheus. Alerts, dashboards and recording rules are all PromQL expressions.

Goals
  • Select series with label matchers and range vectors
  • Use rate and increase correctly on counters
  • Aggregate with sum, avg, topk and by or without
4.1

Instant and range vectors

In plain words

A selector such as http_requests_total{job="api"} returns an instant vector: the latest value of every matching series. Adding [5m] returns a range vector: all samples in the last five minutes per series.

The problem it solves

You need a way to ask both "what is the value now" and "how did it change over a window".

What it does

  • Instant vector: one sample per series at one time. Graphs and alerts use this.
  • Range vector: a list of samples per series. Only functions like rate() can consume it.
  • A scalar is a single number; a string is rarely used.
4.2

Label matchers

In plain words

Inside braces you filter by labels with four operators: =, !=, =~ (regex match) and !~ (regex not match).

The problem it solves

A metric name alone returns series from every service and environment.

What it does

  • Regexes are fully anchored: code=~"5.." matches 500 to 599 only.
  • A selector must have at least one matcher that does not match the empty string.
  • Matching on __name__ selects across metrics, which is expensive.

Examples

promqlSelectors
http_requests_total
http_requests_total{job="api", env="prod"}
http_requests_total{code=~"5.."}
http_requests_total{namespace!~"kube-.*|monitoring"}
4.3

rate, irate and increase

In plain words

Counters only go up, so their raw value is useless. rate(x[5m]) gives the per-second average increase over the window. increase(x[5m]) gives the total increase. irate uses only the last two samples.

The problem it solves

You need requests per second, not "10 billion requests since the server first started". Counters also reset to zero on restart, which rate handles.

What it does

  • rate handles counter resets and extrapolates to window edges.
  • Window must hold at least two samples: use at least 4 times the scrape interval (with 30s scrape use 2m or more).
  • irate is jumpy and suits only fast-moving graphs. Never use it in alerts.
  • increase(x[1h]) equals rate(x[1h]) * 3600.

Examples

promqlCounter functions
rate(http_requests_total{job="api"}[5m])
increase(http_requests_total{job="api"}[1h])
sum(rate(http_requests_total[5m])) by (job)
Careful

Do not apply rate to a gauge, and do not apply avg before rate. Always rate first, then aggregate.

Check yourself
Rate window with a 15s scrape interval, minimum sensible value?

About 1m (four samples). Many teams use 5m for stability.

4.4

Aggregation operators

In plain words

sum, avg, min, max, count, topk, bottomk, quantile and a few more combine many series into fewer.

The problem it solves

One pod's metric tells little. You want per service, per namespace, or the five worst offenders.

What it does

  • by (label) keeps only the listed labels. without (label) removes the listed labels and keeps the rest.
  • count by (job) (up == 1) counts healthy targets per job.
  • topk(5, expr) returns the 5 largest series.

Examples

promqlAggregations
sum by (namespace) (rate(container_cpu_usage_seconds_total[5m]))
avg without (instance) (node_load1)
topk(5, sum by (pod) (rate(container_network_receive_bytes_total[5m])))
count by (job) (up == 0)
4.5

Arithmetic and comparison

In plain words

You can add, divide and compare vectors. Operators match series on identical label sets unless you tell them otherwise. Comparison without bool filters; with bool returns 0 or 1.

The problem it solves

Ratios such as error percentage need two queries combined into one.

What it does

  • Arithmetic: + - * / % ^.
  • Comparison > < == != >= <= keeps only series that satisfy it. This is how alerts work.
  • Use ignoring(label) or on(label) when label sets differ.

Example

promqlError ratio per service
sum by (service) (rate(http_requests_total{code=~"5.."}[5m]))
  /
sum by (service) (rate(http_requests_total[5m]))
  > 0.05
Check yourself
What does a comparison like x > 5 return?

Only the series of x whose value is above 5; the others disappear.

4.6

Gauges, delta and deriv

In plain words

For gauges use direct values or avg_over_time, max_over_time, delta and deriv.

The problem it solves

Gauges such as memory can spike. A raw point may miss the peak.

What it does

  • max_over_time(x[1h]) is the peak in the last hour.
  • delta(x[1h]) is the change of a gauge across the window.
  • deriv(x[1h]) is the per-second slope using regression.
  • *_over_time functions also include min, sum, count, quantile.

Examples

promqlGauge queries
max_over_time(container_memory_working_set_bytes{pod=~"api-.*"}[1h])
avg_over_time(node_load1[10m])
delta(node_filesystem_free_bytes{mountpoint="/"}[6h])
4.7

Time offsets, @ modifier and the Prometheus HTTP API

In plain words

offset 1d looks one day back. The @ modifier pins evaluation to an exact timestamp. The HTTP API lets scripts run any PromQL.

The problem it solves

"Is traffic lower than the same time yesterday" needs two time points in one expression, and automation needs a machine interface.

What it does

  • rate(x[5m] offset 1w) is last week's rate.
  • /api/v1/query evaluates at one instant; /api/v1/query_range returns a graph with start, end, step.
  • Results are JSON with data.result.

Example

bashQuery by API

curl -sG localhost:9090/api/v1/query --data-urlencode 'query=sum(rate(http_requests_total[5m])) / sum(rate(http_requests_total[5m] offset 1d))'

PromQL in depth

7 concepts · about 55 minutes

These patterns appear in nearly every real alert and dashboard.

Goals
  • Compute percentiles with histogram_quantile and understand its limits
  • Join series with on, ignoring and group_left
  • Forecast and detect missing data with predict_linear and absent
5.1

Histograms and buckets

In plain words

A histogram metric exposes cumulative counters per bucket: x_bucket{le="0.5"} counts observations at or below 0.5 seconds. It also exposes x_sum and x_count.

The problem it solves

Averages hide tail latency. A p99 of 3 seconds can sit beside an average of 100 ms.

What it does

  • Buckets are cumulative, so le="+Inf" equals _count.
  • Average latency is rate(x_sum) / rate(x_count).
  • Percentiles are computed from bucket counts and are only as precise as bucket boundaries.
  • Native histograms (newer, sparse, exponential) remove fixed buckets; check the current docs for support in your version.

Average latency

promqlMean latency
sum(rate(http_request_duration_seconds_sum[5m]))
  / sum(rate(http_request_duration_seconds_count[5m]))
5.2

histogram_quantile

In plain words

histogram_quantile(0.99, ...) estimates the 99th percentile from bucket rates, assuming values spread evenly inside a bucket.

The problem it solves

You need fleet-wide percentiles which cannot be averaged from per-pod percentiles.

What it does

  • Input must be rate() of buckets, aggregated with sum by (le, ...). Keep le.
  • The estimate is wrong if bucket boundaries are far from your target. Put a boundary at your SLO value.
  • Result is NaN if there were no observations.

Examples

promqlp99 by service
histogram_quantile(
  0.99,
  sum by (le, service) (rate(http_request_duration_seconds_bucket[5m]))
)

Share of requests faster than 300 ms, usable as an SLI.

promqlLatency SLI
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
  / sum(rate(http_request_duration_seconds_count[5m]))
Check yourself
Why must le stay in the by clause?

histogram_quantile needs the bucket boundaries to interpolate; without le it cannot compute the percentile.

5.3

Vector matching with on and ignoring

In plain words

When two vectors are combined, Prometheus pairs series with exactly the same labels. on(a,b) pairs by only those labels, ignoring(c) pairs by all but those.

The problem it solves

The numerator and denominator often have different extra labels, so a plain division returns nothing.

What it does

  • Use on() with the shared labels, such as on(namespace, pod).
  • One-to-one matching is default. If one side has many matches for one on the other, you must say so with group_left or group_right.
  • Mismatch errors say "many-to-many matching not allowed".

Example

promqlMemory usage as a share of the limit
sum by (namespace, pod) (container_memory_working_set_bytes{container!=""})
  /
sum by (namespace, pod) (kube_pod_container_resource_limits{resource="memory"})
5.4

group_left and info metrics

In plain words

group_left lets the many side keep labels copied from the one side. It is used with "info" metrics such as kube_pod_info or kube_node_labels whose value is always 1 and whose labels carry metadata.

The problem it solves

CPU metrics have a pod name but not the owning team or the node's instance type. You need to attach that information.

What it does

  • Multiply by an info metric (value 1) so values do not change.
  • group_left(label) copies named labels to the result.
  • Common pattern: attach team from a pod label metric.

Example

promqlCPU by team
sum by (team) (
  sum by (namespace, pod) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))
  * on (namespace, pod) group_left (label_team)
  kube_pod_labels
)
Note

kube_pod_labels carries pod labels only when allowed in the kube-state-metrics settings (--metric-labels-allowlist). Check the current docs for your version.

5.5

Forecasting and missing data

In plain words

predict_linear(x[6h], 4*3600) extrapolates a gauge four hours ahead. absent() returns 1 when a selector matches nothing. absent_over_time does the same across a window.

The problem it solves

A full disk can be predicted and a vanished metric is a silent failure.

What it does

  • Disk-full prediction alerts give time to react before an outage.
  • Use gauges only. A window of 6h smooths daily cycles.
  • absent() only works for selectors with equality matchers.

Example

promqlDisk full within four hours
predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[6h], 4*3600) < 0
Check yourself
With 20 GB free and a fall of 6 GB per hour, when does the disk fill?

In about 3.3 hours (20 divided by 6), inside the four hour horizon, so the alert fires.

5.6

Subqueries and the resolution of time

In plain words

A subquery expr[1h:1m] runs an instant expression every minute over one hour, producing a range vector that range functions can use.

The problem it solves

You cannot apply max_over_time to the result of rate() directly, because rate() returns an instant vector.

What it does

  • Syntax is [range:step]; omit step for the global evaluation interval.
  • Heavy: every step recalculates the inner query. Prefer a recording rule for repeated use.
  • Typical use: peak rate over the last day.

Example

promqlPeak request rate in 24h
max_over_time(sum(rate(http_requests_total[5m]))[1d:5m])

Useful query patterns

In plain words

A short list of queries you will write again and again: restarts, CPU throttling, pod readiness and percent of nodes ready.

The problem it solves

Knowing the syntax is not the same as knowing which question to ask.

What it does

  • Restarts in the last hour from kube-state-metrics.
  • CPU throttling ratio from cAdvisor.
  • Pods not ready by namespace.
  • Each can be turned into an alert after a sensible for.

Queries

Recording rules and alert rules

7 concepts · about 50 minutes

Rules run inside Prometheus on a schedule. Recording rules make queries cheap; alert rules turn queries into notifications.

Goals
  • Write recording rules with a clear naming convention
  • Write alert rules with for, labels and annotations
  • Test rules with promtool before deploying
6.1

Recording rules

In plain words

A recording rule evaluates a PromQL expression on a schedule and stores the result as a new series.

The problem it solves

Dashboards that compute a p99 over thousands of series on every refresh are slow and load Prometheus heavily.

What it does

  • The result is stored like any metric, so later queries read one cheap series.
  • Rules are grouped; groups run on their own interval, rules in a group run in order.
  • Use them for expensive aggregations, for SLI building blocks and for federation.

Example

yamlrules/recording.yml
groups:
  - name: http_sli
    interval: 30s
    rules:
      - record: service:http_requests:rate5m
        expr: sum by (service) (rate(http_requests_total[5m]))
      - record: service:http_errors:ratio_rate5m
        expr: |
          sum by (service) (rate(http_requests_total{code=~"5.."}[5m]))
            / sum by (service) (rate(http_requests_total[5m]))
6.2

Naming recording rules

In plain words

The convention is level:metric:operations, for example service:http_requests:rate5m.

The problem it solves

When you see job_cpu in a graph you cannot tell if it is raw, summed or averaged.

What it does

  • level lists the labels kept (service, job, cluster).
  • metric is the original metric name, with _total removed after rate.
  • operations lists applied functions, newest first.
  • Colons are reserved for recording rules, so exporters never use them.
Check yourself
What does the colon in a metric name tell you?

It is a recording rule output, not a raw scraped metric.

6.3

Alert rules

In plain words

An alert rule is a PromQL expression plus a for duration. When the expression returns series for longer than for, one alert per series fires.

The problem it solves

Alerting by eye does not scale and a single noisy sample should not wake someone.

What it does

  • States: inactive, pending (true but not yet for the full for), firing.
  • labels are added to the alert and drive Alertmanager routing, such as severity.
  • annotations hold human text: summary, description, runbook_url. Templates use {{ $labels.x }} and {{ $value }}.
  • keep_firing_for (newer) holds an alert open to avoid flapping; check your version.

Example

yamlrules/alerts.yml
groups:
  - name: availability
    rules:
      - alert: HighErrorRatio
        expr: service:http_errors:ratio_rate5m > 0.05
        for: 10m
        labels:
          severity: page
          team: payments
        annotations:
          summary: "{{ $labels.service }} error ratio is {{ $value | humanizePercentage }}"
          runbook_url: https://runbooks.example.com/high-error-ratio
      - alert: TargetDown
        expr: up == 0
        for: 5m
        labels:
          severity: ticket
        annotations:
          summary: "{{ $labels.job }} on {{ $labels.instance }} is down"

In plain words

for: 10m means the condition must hold on every evaluation for ten minutes before the alert fires.

Brief spikes cause pages that nobody can act on.

Common rule mistakes

In plain words

Most broken rules fall into a handful of patterns: wrong label match, missing for, stale series and rule groups that take longer than their interval.

The problem it solves

Silent failures in monitoring are worse than loud ones.

What it does

What an exporter is

In plain words

An exporter is a small program that reads the state of something (a kernel, a database, a cloud API) and serves it at /metrics.

The problem it solves

You cannot add instrumentation to Linux, MySQL or a managed service, but you still need their numbers.

What it does

A probe is only useful with alerts on failure, slowness and approaching certificate expiry.

In plain words

Scale, long-term storage and cardinality

8 concepts · about 55 minutes

One Prometheus is simple and fast. This section covers what to do when you need more history, more clusters or lower cost.

Goals
  • Understand TSDB storage and size it with arithmetic
  • Pick between federation, remote write, Thanos, Mimir and VictoriaMetrics

8.1

How the TSDB stores data

In plain words

Prometheus writes new samples to memory and a write-ahead log (WAL), then every two hours compacts them into immutable blocks on disk. Old blocks are deleted when they exceed retention.

The problem it solves

You need fast writes and compact storage without an external database.

What it does

  • Samples cost about 1 to 2 bytes each after compression.
  • Default retention is 15 days; set --storage.tsdb.retention.time and --storage.tsdb.retention.size.
  • Memory is dominated by the number of active series (several KB per series).
  • Local storage is not replicated; for durability use remote write or Thanos.
8.2

Sizing storage

In plain words

Disk needed = samples per second × bytes per sample × retention seconds.

The problem it solves

Guessing disk size leads to full disks or waste.

What it does

  • Samples per second = active series ÷ scrape interval.
  • Worked example: 100 000 series scraped every 15 s gives 100 000 ÷ 15 = 6 667 samples per second.
  • One day is 6 667 × 86 400 = 576 000 000 samples. For 15 days that is 8.64 billion samples.
  • At 1.5 bytes per sample this is 12.96 GB; at 2 bytes it is 17.28 GB. Add 20 to 30 percent headroom for the WAL and compaction.
  • So plan roughly 20 GB for 100 000 series at 15 s for 15 days.

Cardinality

In plain words

Cardinality is the number of distinct series. Every unique combination of label values is a new series.

The problem it solves

A label such as user_id or request_path with unbounded values creates millions of series, exhausting memory and crashing Prometheus.

What it does

  • Avoid IDs, emails, full URLs, timestamps in labels.
  • Find offenders with the TSDB status page or topk(10, count by (__name__)({__name__=~".+"})).
  • Set sample_limit and label_limit per job to protect the server.

8.6

Thanos

In plain words

Thanos adds global query and cheap long retention on top of existing Prometheus servers by shipping their blocks to object storage such as S3.

The problem it solves

You want unlimited history, one query across clusters, and HA Prometheus pairs without duplicate data.

What it does

  • Sidecar next to Prometheus uploads 2-hour blocks to S3 and serves recent data.
  • Store Gateway serves old blocks from S3. Querier fans out queries and deduplicates replicas using the replica label.
  • Compactor merges and downsamples blocks (5-minute and 1-hour resolutions).
  • Ruler evaluates rules globally. Alternative ingestion path: Receive for remote write.

Alertmanager and alert design

11.1

What Alertmanager does

In plain words

Alertmanager receives alerts from Prometheus, removes duplicates, groups them, applies silences and inhibitions, and sends notifications to receivers.

The problem it solves

Without it, a failed node with 40 pods would send 40 separate pages.

What it does

  • Prometheus keeps pushing a firing alert on every evaluation; Alertmanager dedups.
  • It sends a notification when a group first fires, again on changes, and a reminder every repeat_interval.
  • Runs as a cluster of 3 replicas using gossip for HA. Point Prometheus at all replicas.

In plain words

  • matchers select by label, such as severity="page" and team="payments".
  • Children inherit group and timing settings unless overridden.
  • Each alert goes to the deepest matching route.

SLI, SLO and error budget

In plain words

An SLI is a measured ratio of good events. An SLO is the target for it over a window. The error budget is the allowed failure: 100 percent minus the SLO.

The problem it solves

"Make it as reliable as possible" has infinite cost. A target lets you balance reliability against shipping features.

What it does

  • SLO 99.9 percent over 30 days gives an error budget of 0.1 percent.
  • In time: 30 days × 24 × 60 = 43 200 minutes; 0.001 × 43 200 = 43.2 minutes of full outage.
  • In requests: at 10 million requests per day, 30 days is 300 million; 0.001 × 300 million = 300 000 failed requests allowed.
  • SLO 99.99 percent shrinks the budget to 4.32 minutes. SLO 99 percent gives 432 minutes.
Check yourself
Budget for a 99.95 percent SLO over 30 days?

0.0005 × 43 200 = 21.6 minutes.

12.2

Burn rate

In plain words

Burn rate is how fast you consume the error budget compared to a pace that would use exactly all of it at the end of the window. Burn rate 1 spends the budget exactly in 30 days.

The problem it solves

An error ratio of 0.5 percent is trivial against a 99 percent SLO but a disaster against 99.99 percent. Burn rate gives one scale for all SLOs.

What it does

  • Burn rate = observed error ratio ÷ allowed error ratio (1 − SLO).
  • Example: SLO 99.9 percent allows 0.001. Observed 0.0144 gives burn rate 0.0144 ÷ 0.001 = 14.4.
  • Time to exhaustion = window ÷ burn rate. At 14.4, 30 days ÷ 14.4 = 2.08 days (about 50 hours).
  • At burn rate 1000 the budget is gone in 43.2 minutes.
12.3

The budget fraction behind 14.4, 6 and 3

In plain words

The famous numbers come from choosing how much of the monthly budget one alert may consume before it fires.

The problem it solves

You need thresholds with a clear meaning instead of guesses.

What it does

  • Budget consumed = burn rate × alert window ÷ SLO window (720 hours for 30 days).
  • 14.4 over 1 hour: 14.4 × 1 ÷ 720 = 2 percent of the budget.
  • 6 over 6 hours: 6 × 6 ÷ 720 = 5 percent.
  • 3 over 3 days (72 hours): 3 × 72 ÷ 720 = 30 percent. Burn rate 1 over 3 days: 10 percent.
  • So a page means "2 percent of the monthly budget gone in an hour".
Check yourself
Burn rate to consume 5 percent of the budget in 6 hours?

0.05 × 720 ÷ 6 = 6.

12.4

Multiwindow multi-burn-rate alerts

In plain words

Each alert checks two windows: a long one for significance and a short one (about one twelfth of it) to confirm the problem is still happening.

The problem it solves

A single long window keeps alerting for an hour after the issue is fixed. A single short window pages on blips.

What it does

  • Page: burn rate above 14.4 over 1 hour AND over 5 minutes.
  • Page: burn rate above 6 over 6 hours AND over 30 minutes.
  • Ticket: burn rate above 3 over 1 day AND over 2 hours (or 6 over 3 days).
  • Ticket: burn rate above 1 over 3 days AND over 6 hours.
  • With SLO 99.9 percent the error-ratio thresholds are 14.4 × 0.001 = 0.0144, 6 × 0.001 = 0.006, 3 × 0.001 = 0.003 and 0.001.

  • Alert rules then reference the recorded series.

Tracing and OpenTelemetry

8 concepts · about 55 minutes

Metrics tell you that something is slow. Traces tell you where. OpenTelemetry (OTel) is the open standard for producing and moving that data.

Goals
  • Explain traces, spans and context propagation
  • Configure an OpenTelemetry Collector pipeline
  • Choose a sampling strategy and follow semantic conventions
14.1

Traces and spans

In plain words

A trace is the story of one request. It consists of spans: timed operations such as an HTTP handler or a database query, linked parent to child.

The problem it solves

In a system of 30 services, a log line from one service cannot tell you why the whole request took 4 seconds.

What it does

  • Each span has a name, start time, duration, attributes, events and a status.
  • All spans of a request share a trace ID; each has its own span ID and a parent span ID.
  • The longest chain of spans shows the critical path.
14.2

Context propagation

In plain words

For a trace to span services, each call must pass the trace ID along. The W3C traceparent HTTP header does that.

The problem it solves

Without propagation each service starts a new unrelated trace.

What it does

  • Format: version, trace ID, parent span ID and flags, joined by dashes, for example 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01.
  • SDK instrumentation for HTTP and gRPC clients and servers injects and extracts it automatically.
  • Message queues need the header copied into message metadata.
  • Put the trace ID into logs to link logs and traces.
14.3

OpenTelemetry components

In plain words

OpenTelemetry has a specification, language SDKs and APIs, the OTLP protocol and the Collector. It does not store data; you pick a backend.

The problem it solves

Each vendor had its own agent and format, so switching backends meant re-instrumenting every service.

What it does

  • API: what your code calls. SDK: implements it, samples, batches and exports.
  • OTLP over gRPC (port 4317) or HTTP (port 4318) is the standard wire format for traces, metrics and logs.
  • Auto-instrumentation exists for Java, Python, Node.js, .NET and others; the OpenTelemetry Operator can inject it into Kubernetes pods by annotation.
14.4

In plain words

Configure a tracer provider with a resource (who am I) and an OTLP exporter, then create spans or let auto-instrumentation do it.

The problem it solves

Without a service name resource, backends show every service as "unknown_service".

What it does

  • service.name is the most important attribute.
  • BatchSpanProcessor buffers spans and exports in batches, so latency is not affected.
  • The standard environment variables (OTEL_SERVICE_NAME, OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_TRACES_SAMPLER) configure SDKs without code.

In plain words

The OpenTelemetry Collector is a standalone process that receives telemetry, processes it and exports it. A pipeline connects receivers, processors and exporters for one signal.

14.6

Sampling

In plain words

Sampling keeps a fraction of traces. Head sampling decides when the trace starts. Tail sampling decides after the trace completes, so it can keep all errors and slow traces.

The problem it solves

Storing 100 percent of traces from a busy system is costly, and most traces are boring.

What it does

  • Head: simple, cheap, random (for example 10 percent), but may drop the one failing trace.
  • Tail: needs all spans of a trace in one Collector instance (use a load-balancing exporter keyed by trace ID) and memory to buffer them.
  • Example policy: keep 100 percent of errors, 100 percent over 2 seconds, 5 percent of the rest.
  • Arithmetic: 2 000 traces per second × 86 400 = 172.8 million traces per day. At 5 percent kept that is 8.64 million; at 10 KB per trace about 86 GB per day instead of 1.7 TB.

Tail sampling policy

14.7

Semantic conventions

In plain words

Semantic conventions are agreed attribute names, such as http.request.method, service.name, db.system and k8s.pod.name.

The problem it solves

If every team names the same thing differently, backends and dashboards cannot work across services.

What it does

  • Some HTTP and database attribute names changed in recent versions (for example http.method became http.request.method); check the current spec for your SDK.
  • Keep attribute values low in cardinality when they become metric labels.
  • Add business attributes under your own prefix, such as shop.order_id.

Loki and LogQL

8 concepts · about 55 minutes

Loki is built like Prometheus for logs. It indexes only labels, not the log text, which makes it cheap, and it changes how you query and how you design labels.

Goals
  • Explain how Loki indexes labels and stores log chunks
  • Write LogQL queries for filtering, parsing and metrics from logs
  • Design labels and retention to keep Loki cheap and fast
15.1

How Loki stores logs

In plain words

Loki groups log lines into streams, one per unique set of labels. It indexes the labels and compresses the lines into chunks in object storage such as S3.

The problem it solves

Full-text indexing of every line (as in Elasticsearch) costs a lot of CPU, memory and disk for logs that are rarely read.

What it does

  • Index = labels only (small). Chunks = compressed lines (large, in S3 or similar).
  • A query first selects streams by labels, then scans the chunks of those streams for text matches.
  • Fast when labels narrow the search; slow when you scan huge streams with a broad regex.
  • Components: distributor, ingester, querier, query frontend, compactor; check the current docs for the deployment modes (monolithic, simple scalable, microservices).
Check yourself
What does Loki index?

Only the labels of each stream, not the text of the lines.

15.2

Labels and cardinality

In plain words

A label is a key and value such as namespace="shop". Every unique combination creates a new stream.

The problem it solves

Putting high-cardinality values (user ID, request ID, pod IP) in labels creates millions of tiny streams, which makes ingestion and queries slow and costly.

What it does

  • Good labels: cluster, namespace, app, container, level (low and bounded).
  • Bad labels: trace_id, user_id, URL path with IDs. Keep these inside the log line and filter or parse them at query time.
  • Rough count: 5 clusters × 20 namespaces × 3 containers = 300 streams per level value, which is fine; adding a pod label with 50 pods each multiplies it by 50.
  • Loki enforces limits such as maximum streams per tenant; check the current defaults.

Log queries, selectors and filters

In plain words

A LogQL query begins with a stream selector in braces, then adds line filters.

The problem it solves

You need to find the error lines of one service in the last 15 minutes without reading everything.

What it does

  • Selector: {namespace="shop", app="api"} uses =, !=, =~ and !~. At least one non-empty matcher is required.
  • Line filters: |= "error" contains, != "healthz" excludes, |~ "timeout|refused" regex, !~ negative regex.
  • Put the most selective filter first, and prefer plain strings over regex.
  • Order of work: selector, then filters, then parsers.

Examples

textLogQL

15.4

Parsers and label filters

In plain words

Parsers turn a line into temporary labels at query time. Then you can filter on fields.

The problem it solves

Structured fields live inside the line, such as status=503 or a JSON latency_ms, and are not Loki labels.

16.2

Sampling strategies

In plain words

Sampling keeps a subset of traces. Head sampling decides at the start of the request; tail sampling decides after seeing the whole trace.

The problem it solves

Storing every trace at high traffic is costly, but random sampling can drop the rare slow or failed requests you need most.

What it does

  • Head: simple, cheap, for example keep 5 percent. Cannot know yet if the request will fail.
  • Tail (OpenTelemetry Collector tail_sampling processor): keep all errors, all slow traces, plus 5 percent of the rest. Needs all spans of a trace on the same collector, so route by trace ID.
  • Arithmetic: 2 000 requests per second × 86 400 s = 172.8 million traces a day. At 5 percent that is 8.64 million.
  • Always keep metrics for 100 percent of traffic; sampling affects only traces.

17.1

Limits of a single Prometheus

In plain words

Prometheus stores data on local disk in one instance. It has no built-in clustering, global view or cheap long-term storage.

The problem it solves

17.2

Thanos components

In plain words

Thanos adds components around existing Prometheus servers. It does not replace them.

The problem it solves

You want to keep your Prometheus and add global queries and cheap history step by step.

What it does

  • Tools: Chaos Mesh, LitmusChaos, AWS Fault Injection Service (FIS) for AWS-level faults such as stopping instances or throttling EBS.

19.3

Running a game day

In plain words

A game day is a scheduled exercise where a team practises a failure scenario together, with observers.

The problem it solves

Real incidents are a poor place to learn who has access to what, where the runbook is, or how to reach a vendor.

What it does

  • Before: choose a scenario, set scope, announce, name a facilitator and a scribe, agree abort criteria and a rollback.
  • During: the facilitator injects the failure; responders work as in a real incident (use the real channels, tools and roles); the scribe records timestamps.
  • After: a review within a few days: detection time, diagnosis time, recovery time, gaps found, actions with owners.
  • Run them quarterly and increase difficulty gradually.

Scenario template

textGame day card
Scenario: primary RDS instance fails over during peak checkout
Scope: staging, 14:00 to 15:30
Abort if: customer-facing error rate above 2 percent in production (should be unaffected)
Success: alert fires within 5 minutes, failover under 2 minutes, runbook accurate
19.4

On-call rotation design

In plain words

On-call means one or more people are responsible for responding to alerts outside normal work.

The problem it solves

A bad rotation burns people out, and tired engineers make poor decisions and leave.

What it does

  • Size: a rotation of fewer than 5 to 6 people is hard to sustain. With 8 people and one week each, each person carries 52 ÷ 8 = 6.5 weeks per year.
  • Primary and secondary layers, with escalation after 5 to 15 minutes of no acknowledgement.
  • Follow-the-sun for global teams avoids night pages.
  • Compensation and time off after a heavy week are part of the design.
  • Measure: pages per shift, night pages, time to acknowledge. A common target is a small number of actionable pages per shift (the Google SRE book mentions two incidents per 12 hour shift as a limit).

19.5

Alert quality and noise reduction

In plain words

Every page must be urgent, actionable and need a human. Anything else should be a ticket or a dashboard.

The problem it solves

Noisy alerts train people to ignore pages. Alert fatigue is a leading cause of missed real incidents.

What it does

  • Page on symptoms users feel (SLO burn rate), not on causes (CPU high).
  • Each alert has an owner, severity, runbook link and a clear first step.
  • Review weekly: which alerts fired, were they actionable, how many were duplicates? Delete or fix the worst offenders.
  • Use Alertmanager grouping, inhibition (a cluster-down alert suppresses its child alerts) and silences with expiry and a reason.

Inhibition rule

yamlalertmanager inhibit
inhibit_rules:
  - source_matchers:
      - alertname = "KubeNodeNotReady"
    target_matchers:
      - severity = "warning"
    equal: ["node"]
19.6

Runbooks

In plain words

A runbook is a short document attached to an alert that tells the responder what it means and what to do first.

The problem it solves

At 3 am nobody remembers details. Without a runbook each page restarts the investigation from zero.

What it does

  • Fixed sections: what this alert means, user impact, dashboards to open, diagnosis commands, mitigation steps (rollback, scale, failover), escalation contacts.
  • Keep commands copy-ready and safe; mark dangerous steps.
  • Link from the alert annotation runbook_url; test the links.
  • Update the runbook after every incident where it was wrong. Treat a missing step as a bug.

Skeleton

textrunbook.md
# HighErrorRate on checkout
Meaning: more than 2 percent 5xx for 5 minutes.
First look: Grafana Checkout dashboard, then Loki {app="checkout"} |= "error".
Mitigation: if a deploy happened in the last hour, run: kubectl rollout undo deploy/checkout -n shop
Escalate: payments team on-call if the provider returns 429.
19.7

Incident response and blameless postmortems

In plain words

During an incident, roles keep the work orderly. Afterwards, a blameless review turns the event into lasting fixes.

The problem it solves

Without roles everyone investigates and nobody communicates. Without a blameless culture people hide mistakes.

What it does

  • Roles: incident commander (decides, coordinates), operations lead (hands on), communications lead (status updates), scribe.
  • Mitigate first, find root cause later. Roll back before you investigate if a deploy is the likely trigger.
  • Postmortem within about a week: timeline, impact, contributing factors (systems and processes, not people), what went well, action items with owners and dates.
  • Track actions to completion; an unfixed action is the same incident waiting.
Check yourself
Why mitigate before finding the root cause?

Restoring service limits user impact; the investigation can continue safely afterwards.
