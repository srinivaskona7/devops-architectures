Section 1 of 21

Infrastructure as code and the Terraform workflow

8 concepts · about 45 minutes

Clicking through a console is fast once and impossible to repeat, review or audit. Infrastructure as code (IaC) moves that knowledge into text files so that VPCs, clusters and databases are created the same way every time. Terraform is the most widely used tool for this.

Goals
  • Explain why infrastructure is described in files and reviewed like application code
  • Run the init, plan, apply and destroy cycle and read a plan correctly
  • Pin Terraform and understand how the dependency graph orders changes
1.1

What infrastructure as code means

In plain words

You write files that describe the infrastructure you want. A tool reads them, compares them with what exists, and makes the real world match. The files live in Git, so every change has an author, a review and a history.

The problem it solves

Hand-built environments drift apart. Nobody remembers which checkbox made staging differ from production, a lost engineer takes the knowledge with them, and rebuilding after a disaster takes weeks.

What it does

  • Gives a reviewable pull request for every infrastructure change.
  • Makes environments reproducible: the same code can build dev, staging and production.
  • Acts as documentation that cannot go stale, because it is what actually runs.
  • Enables automation, such as a pipeline that plans on every pull request.
Check yourself
Why is a pull request for infrastructure better than a console change?

It gives review, history, and a repeatable result instead of an undocumented one-off action.

1.2

Declarative versus imperative

In plain words

An imperative script says how to do things step by step: create this, then attach that. A declarative file says what the end result must be, and the tool works out the steps.

The problem it solves

Imperative scripts break when run twice or from a different starting point: "create bucket" fails if the bucket exists. Engineers end up writing endless existence checks.

What it does

  • Terraform is declarative: you state that a bucket named X with versioning exists.
  • It computes the difference between desired and actual state and only performs the needed actions.
  • Running it again with no change does nothing. This property is called idempotence.
  • The trade-off is that some procedural tasks (ordered, one-off migrations) fit badly and need other tools.

The same intent in HCL

hclmain.tf
resource "aws_s3_bucket" "logs" {
  bucket = "acme-prod-logs-eu-west-1"
}

resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id

  versioning_configuration {
    status = "Enabled"
  }
}
1.3

Terraform in the tool landscape

In plain words

Terraform is one of several IaC tools. Some are cloud specific, some use general programming languages, and some run inside Kubernetes.

The problem it solves

Choosing a tool by habit leads to rewrites later. You need to know what each is good at.

What it does

  • Terraform and OpenTofu: one language (HCL) and thousands of providers, so one workflow covers AWS, Azure, GCP, Kubernetes and SaaS.
  • CloudFormation, ARM/Bicep, Deployment Manager: native to one cloud, with deep coverage but no cross-cloud reuse.
  • Pulumi and AWS CDK: general languages such as TypeScript or Python; powerful loops and tests, but more room for complex code.
  • Crossplane: manages cloud resources through Kubernetes custom resources, useful when the cluster is already your control plane.
  • Ansible: configuration of machines, a different job from provisioning.

1.4

Installing and pinning Terraform

In plain words

Terraform is a single binary. Different versions behave differently and can write state that older versions cannot read, so teams pin the version.

The problem it solves

If one engineer upgrades locally and applies, the state format may move forward and teammates and CI suddenly fail with version errors.

What it does

  • Install with a version manager such as tfenv, tfswitch or mise, or from the vendor package repository.
  • Declare the allowed range with required_version in the terraform block.
  • Commit a file such as .terraform-version so tools and CI choose the same release.
  • Upgrade deliberately in a pull request, never by accident.

Pin in code

hclversions.tf
terraform {
  required_version = ">= 1.9.0, < 2.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
bashCheck what you run
terraform version
terraform -help | head -20
Note

Terraform 1.5 and earlier are MPL licensed. Later releases use the Business Source License; OpenTofu is the open-source fork. A later concept compares them.

1.5

The core workflow: init, plan, apply

In plain words

Every change follows the same loop. init prepares the folder, plan shows what would change, apply makes the change, and destroy removes everything.

The problem it solves

Changing real infrastructure blindly is dangerous. The loop forces you to see the effect before it happens.

What it does

  • terraform init downloads providers and modules and configures the backend. Run it after cloning or changing providers.
  • terraform plan reads state, refreshes from the cloud, and prints a diff. It changes nothing.
  • terraform apply shows a plan, asks for confirmation, then performs it and updates the state.
  • terraform destroy plans and applies the deletion of everything the configuration manages.

Day-to-day commands

bashThe loop
terraform init
terraform fmt -recursive
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
terraform output
Check yourself
What does init do that plan does not?

It installs providers and modules and sets up the backend; plan assumes init already ran.

1.6

Reading a plan

In plain words

The plan lists each resource with a symbol: + create, - destroy, ~ update in place, -/+ replace (destroy and create). The summary line counts them.

The problem it solves

Most outages from Terraform come from approving a plan nobody read, for example a database being replaced when only a tag was meant to change.

What it does

  • Look first at the summary: "Plan: 2 to add, 1 to change, 1 to destroy".
  • Every -/+ or must be replaced line deserves attention. A comment says which attribute forces replacement.
  • Values marked (known after apply) are decided by the cloud at creation time.
  • (sensitive value) hides secrets in output; the real value is still in state.

Plan output you should stop and read

textA dangerous plan
  # aws_db_instance.main must be replaced
-/+ resource "aws_db_instance" "main" {
      ~ identifier = "shop-db" -> "shop-database" # forces replacement
    }

Plan: 1 to add, 0 to change, 1 to destroy.
Danger

A replaced database loses its data unless a snapshot or prevent_destroy protects it. Stop and rethink instead of applying.

Check yourself
What does `~` mean in a plan?

An in-place update; the resource is kept and only the listed attributes change.

1.7

Saved plans and exit codes

In plain words

terraform plan -out=file stores the exact plan. terraform apply file runs precisely that plan, without recomputing it.

The problem it solves

Between plan and apply, someone may change the code or the cloud. Without a saved plan, what you approved is not necessarily what runs.

What it does

  • A saved plan applies without a confirmation prompt, because it was already reviewed.
  • -detailed-exitcode makes plan return 0 for no changes, 1 for an error, and 2 when changes are present, which pipelines use for drift checks.
  • terraform show tfplan prints it again; terraform show -json tfplan gives machine-readable output for policy tools.
  • Saved plans can contain secrets in plain form, so store them as protected artifacts.

Pipeline friendly flags

bashNon-interactive usage
terraform plan -input=false -lock-timeout=5m -out=tfplan
terraform show -json tfplan > plan.json
terraform plan -detailed-exitcode >/dev/null; echo "exit=$?"
terraform apply -input=false tfplan
Careful

-auto-approve on a fresh plan skips review. Use it only after a separate approval step, never as a habit on a laptop.

1.8

The dependency graph and -target

In plain words

Terraform builds a graph from references between resources. If a subnet uses a VPC's ID, the VPC comes first. Independent resources are created in parallel (10 at a time by default).

The problem it solves

Doing ordering by hand is error prone, and serial creation is slow.

What it does

  • Any reference such as aws_vpc.main.id creates an edge in the graph.
  • Destroy runs in reverse order.
  • terraform graph outputs the graph in DOT format for visualisation.
  • -target restricts a run to one resource and its dependencies. It is an emergency tool: it skips the rest of the configuration and can leave state inconsistent with code.

Looking at the graph

bashGraph and parallelism
terraform graph | head -20
terraform apply -parallelism=5
Careful

Habitual use of -target hides broken dependencies. If you need it often, split the configuration into smaller states instead.

Check yourself
How does Terraform know to create the VPC before the subnet?

The subnet references the VPC's attribute, creating a dependency edge in the graph.

Section 2 of 21

HCL basics, types and variables

7 concepts · about 45 minutes

HCL (HashiCorp Configuration Language) is the language of Terraform files. It is declarative and small: blocks, arguments and expressions. Learning its few building blocks well makes every module readable.

Goals
  • Read and write HCL blocks, arguments and references
  • Choose the right type for a variable and validate its value
  • Use locals and outputs, and keep sensitive values out of logs
2.1

Blocks, arguments and files

In plain words

HCL is made of blocks (resource "aws_vpc" "main" { ... }) that contain arguments (cidr_block = "10.0.0.0/16"). A block has a type, optional labels, and a body.

The problem it solves

Without a clear structure, large configurations become unreadable. HCL gives a uniform shape so every resource, variable and output looks alike.

What it does

  • Terraform loads every *.tf file in a directory as one configuration; file names are only a convention.
  • Common blocks are terraform, provider, resource, data, variable, output, locals and module.
  • Comments use #, // or /* */.
  • Common layout: main.tf, variables.tf, outputs.tf, versions.tf.

Anatomy of a resource

hclmain.tf
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true

  tags = {
    Name = "shop-prod"
  }
}
Note

The first label is the resource type (decided by the provider), the second is a local name. The address aws_vpc.main is how other code refers to it.

2.2

Primitive types

In plain words

Every value has a type. The simple ones are string, number and bool.

The problem it solves

Cloud APIs are strict. A port passed as a string or a flag spelled "yes" causes confusing errors. Types catch mistakes early.

What it does

  • Strings use double quotes; "${var.name}-db" interpolates a value.
  • Numbers can be integers or decimals; Terraform converts between string and number where it can.
  • Booleans are true and false (no quotes).
  • null means "no value", and tells a provider to use its default for that argument.

Examples

hclPrimitive values in locals
locals {
  region   = "eu-west-1"
  port     = 5432
  multi_az = true
  note     = null
  banner   = <<-EOT
    Managed by Terraform.
    Do not edit in the console.
  EOT
}
2.3

Collection and structural types

In plain words

Collections hold many values: list(...) is ordered, set(...) is unordered and unique, map(...) is key to value pairs of one type. Structural types, object({...}) and tuple([...]), mix types.

The problem it solves

Real configuration has shapes such as "a list of subnet definitions, each with a CIDR and a zone". You need a way to describe that shape so Terraform can check it.

What it does

  • list(string) is written ["a", "b"]; index with list[0].
  • map(string) is written { env = "prod" }; index with map["env"].
  • set(string) removes duplicates and has no index. for_each requires a set or map.
  • object({ name = string, size = number }) fixes the keys and the type of each.
  • any accepts anything, but loses validation, so use sparingly.

A typed variable

hclvariables.tf
variable "subnets" {
  description = "Private subnets to create"
  type = list(object({
    name = string
    cidr = string
    az   = string
  }))
  default = [
    { name = "a", cidr = "10.0.1.0/24", az = "eu-west-1a" },
    { name = "b", cidr = "10.0.2.0/24", az = "eu-west-1b" },
  ]
}
Check yourself
Which type does `for_each` accept?

A map or a set of strings (a list must be converted with toset).

2.4

Input variables and ways to set them

In plain words

Variables are the parameters of a configuration or module. You declare them with variable blocks and provide values from outside.

The problem it solves

Hard-coded values force you to copy code per environment. Variables let one codebase serve many.

What it does

  • Precedence from lowest to highest: default, environment TF_VAR_name, terraform.tfvars, *.auto.tfvars, then -var-file and -var on the command line (later ones win).
  • A variable without a default is required; Terraform prompts or fails in non-interactive mode.
  • description is documentation shown by tools; always set it.
  • Variables cannot be changed during a run; use locals for computed values.

Providing values

hclprod.tfvars
environment    = "prod"
instance_count = 3
bashUsing them
terraform plan -var-file=prod.tfvars
terraform plan -var 'instance_count=5'
TF_VAR_environment=dev terraform plan
2.5

Validating variables

In plain words

A validation block rejects bad input with your own message, before any plan is made.

The problem it solves

A typo such as environment = "porduction" would create misnamed resources or fail deep inside a cloud call with a vague error.

What it does

  • condition is an expression that must be true; error_message explains the rule.
  • You can use any function, such as contains, regex, can and length.
  • Since Terraform 1.9 a validation may refer to other variables. Check the current docs for your version.
  • precondition and postcondition blocks (in lifecycle) check assumptions about resources and data sources.

Validation examples

hclvariables.tf
variable "environment" {
  type        = string
  description = "Deployment environment"

  validation {
    condition     = contains(["dev", "stage", "prod"], var.environment)
    error_message = "environment must be dev, stage or prod."
  }
}

variable "cidr" {
  type = string

  validation {
    condition     = can(cidrhost(var.cidr, 0))
    error_message = "cidr must be a valid CIDR block."
  }
}
Check yourself
What does `can()` do?

It returns true if the expression evaluates without an error, which makes it handy in validations.

2.6

Locals and outputs

In plain words

Locals are named expressions inside a module, like variables in a function body. Outputs are values a module or root configuration exposes to the outside.

The problem it solves

Repeating "${var.project}-${var.environment}" in fifty places invites mistakes. And other configurations need IDs such as a VPC ID without looking in the console.

What it does

  • locals { name = "..." } is referenced as local.name (singular).
  • Outputs are printed after apply and are readable with terraform output.
  • In modules, outputs are the only way the caller sees inside values: module.network.vpc_id.
  • Mark an output sensitive = true to hide it in the CLI output.

Example

hcllocals.tf and outputs.tf
locals {
  name = "${var.project}-${var.environment}"
  tags = {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

output "vpc_id" {
  description = "ID of the VPC"
  value       = aws_vpc.main.id
}
2.7

Sensitive values

In plain words

Marking a variable or output sensitive = true hides its value from plan and apply output and from logs.

The problem it solves

Passwords and tokens in CI logs are a common leak.

What it does

  • The value is redacted in the CLI as (sensitive value).
  • It is still stored in plain text in the state file, and any output derived from it must also be marked sensitive.
  • Better: never let Terraform know the secret. Let the service generate it (for example RDS manage_master_user_password, which stores it in Secrets Manager).
  • Ephemeral values and write-only arguments exist in recent Terraform and provider versions; check the current docs before relying on them.

Declaring one

hclvariables.tf

HCL expressions, loops and functions

8 concepts · about 50 minutes

Infrastructure is repetitive: three subnets, ten security group rules, five buckets. HCL has expressions to avoid copy and paste while keeping plans readable.

Goals
  • Create many resources with count and for_each and know which to prefer
  • Transform data with for expressions, splats and built-in functions

3.1

References and string templates

In plain words

An expression is anything that produces a value: a literal, a reference like aws_vpc.main.id, a function call, or a template such as "${var.name}-db".

The problem it solves

You need values from one resource inside another, and names built from parts.

What it does

  • Prefixes: var., local., module., data. and a resource type for resources.
  • "${...}" inserts a value into a string; %{ if ... } adds directives in templates.
  • Attribute access with a dot and indexing with brackets: aws_subnet.private[0].id.
  • Unknown values (not available until apply) show as (known after apply).

Examples

hclReferences
resource "aws_subnet" "a" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"

  tags = {
    Name = "${local.name}-private-a"
  }
}
3.2

Conditionals

In plain words

The ternary expression condition ? true_value : false_value chooses between two values. Combined with count, it can switch a resource on or off.

The problem it solves

Some resources only exist in some environments, for example a NAT gateway per zone in production but a single one in dev.

What it does

  • The two result values must be of compatible types.
  • count = var.enabled ? 1 : 0 creates zero or one copy of a resource.
  • Refer to an optional resource safely with one(aws_x.y[*].id) or try(aws_x.y[0].id, null).
  • Keep conditions simple. If a module is full of them, split it in two.

Switching a resource

hclnat.tf
resource "aws_eip" "nat" {
  count  = var.enable_nat ? 1 : 0
  domain = "vpc"
}

output "nat_ip" {
  value = one(aws_eip.nat[*].public_ip)
}
3.3

count

In plain words

count = N creates N copies of a resource, addressed as resource.name[0], [1] and so on.

The problem it solves

You need several identical resources without repeating the block.

What it does

  • count.index gives the position.
  • Instances are tracked by index. Removing the first item of a list shifts the others, so Terraform plans to destroy and recreate resources after it.
  • Good for "zero or one" toggles. Poor for lists of things that can change in the middle.

Example and the trap

hclcount example
variable "names" {
  type    = list(string)
  default = ["a", "b", "c"]
}

resource "aws_s3_bucket" "logs" {
  count  = length(var.names)
  bucket = "acme-logs-${var.names[count.index]}"
}
Careful

If names loses "a", Terraform sees index 0 now holding "b" and plans to change or replace several buckets. Use for_each for lists that evolve.

Check yourself
When is count the right choice?

For a simple on/off toggle (0 or 1) or a fixed number of truly identical items.

3.4

for_each

In plain words

for_each creates one instance per key of a map or per element of a set. Instances are addressed by key: aws_s3_bucket.logs["audit"].

The problem it solves

count identifies things by position, so edits in the middle cause churn. Keys are stable.

What it does

  • each.key and each.value are available inside the block.
  • Removing one key only destroys that instance.
  • Keys must be known at plan time (not derived from resource IDs not yet created).
  • Convert a list with toset(list), or build a map with a for expression.

Example

hclfor_each over a map
variable "buckets" {
  type = map(object({ versioning = bool }))
  default = {
    audit  = { versioning = true }
    assets = { versioning = false }
  }
}

resource "aws_s3_bucket" "this" {
  for_each = var.buckets
  bucket   = "acme-${each.key}"
}

resource "aws_s3_bucket_versioning" "this" {
  for_each = { for k, v in var.buckets : k => v if v.versioning }
  bucket   = aws_s3_bucket.this[each.key].id

  versioning_configuration {
    status = "Enabled"
  }
}
Check yourself
Why can for_each not use keys that depend on a resource's generated ID?

Keys must be known at plan time, and generated IDs are only known after apply.

3.5

For expressions and splats

In plain words

A for expression transforms a list or map into a new list or map. A splat [*] is a short form to collect one attribute from every item.

The problem it solves

Cloud inputs rarely match the shape of your data. You need to filter, reshape and extract.

What it does

  • [for s in var.list : upper(s)] builds a list; {for k, v in var.map : k => v.id} builds a map.
  • An if clause filters: [for s in var.list : s if s != ""].
  • aws_subnet.private[*].id returns a list of all IDs when count is used. For for_each use values(aws_subnet.private)[*].id.
  • flatten, merge, zipmap, setproduct combine and reshape collections.

Examples

hclfor expressions
locals {
  subnet_ids = [for s in aws_subnet.private : s.id]
  az_by_name = { for k, s in aws_subnet.private : k => s.availability_zone }
  prod_only  = [for e in var.envs : e if e == "prod"]
}
3.6

Dynamic blocks

In plain words

A dynamic block generates repeated nested blocks (like several ingress rules) from a collection.

The problem it solves

for_each works on whole resources. Many resources have inner blocks that repeat, and you cannot loop those with for_each on the resource.

What it does

  • Syntax: dynamic "ingress" { for_each = ... content { ... } }.
  • Inside, use ingress.value and ingress.key (named after the block label).
  • Overuse makes code unreadable. Prefer separate rule resources, such as aws_vpc_security_group_ingress_rule, when the provider offers them.

Example

hcldynamic block

  type    = list(number)
  default = [80, 443]

  name   = "web"
  vpc_id = aws_vpc.main.id

    for_each = var.ports
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}

In plain words

Providers, resources and data sources

7 concepts · about 45 minutes

Terraform itself knows nothing about AWS or Kubernetes. Plugins called providers translate HCL into API calls. This section covers how they are chosen, pinned and used.

Goals
  • Configure and version providers, including several regions or accounts with aliases
  • Declare resources and read existing infrastructure with data sources

4.1

What a provider is

In plain words

A provider is a plugin binary that knows one API: AWS, Azure, Google Cloud, Kubernetes, Helm, GitHub, Datadog and thousands more. It defines the resource types and data sources you can write.

The problem it solves

One tool cannot hard-code every vendor's API. Plugins let vendors ship support independently of Terraform's own release cycle.

What it does

  • terraform init downloads providers from a registry (registry.terraform.io, or registry.opentofu.org for OpenTofu).
  • A source address looks like hashicorp/aws: namespace plus type.
  • Each provider runs as a separate process and talks to Terraform over gRPC.
  • Resource type names start with the provider name: aws_, azurerm_, google_, kubernetes_.

Declaring providers

hclversions.tf
terraform {

      source  = "hashicorp/aws"

      version = "~> 2.30"
    }
  }
}

  region = "eu-west-1"

4.2

Version constraints and the lock file

In plain words

version = "~> 6.0" allows any 6.x but not 7.0. The first init records the exact versions chosen, with checksums, in .terraform.lock.hcl.

The problem it solves

A provider upgrade can change behaviour. Without pinning, the same code could plan differently tomorrow than today.

What it does

  • Operators: =, !=, >, >=, <, <= and ~> (pessimistic: only the last digit given may rise).
  • Commit .terraform.lock.hcl so everyone and CI use identical provider builds.
  • terraform init -upgrade moves to the newest allowed versions; review that as a pull request.
  • terraform providers lock -platform=linux_amd64 -platform=darwin_arm64 adds checksums for several platforms, which avoids CI-only lock failures.

Commands

bashLock file operations
terraform init
terraform init -upgrade
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64
git add .terraform.lock.hcl
Check yourself
What does `~> 6.0` allow?

Any 6.x release at or above 6.0, but not 7.0.

4.3

Provider configuration and authentication

In plain words

The provider block sets region, endpoints and credentials. Credentials should come from the environment or an assumed role, not from the code.

The problem it solves

Access keys in .tf files end up in Git and in state.

What it does

  • AWS provider searches env vars (AWS_ACCESS_KEY_ID, AWS_PROFILE), shared config files, SSO, and instance or OIDC roles in that general order.
  • assume_role makes Terraform call STS and work in another account.
  • default_tags applies tags to every taggable resource automatically.
  • In CI, use short-lived OIDC credentials (covered later).

Example

hclprovider.tf

    }
  }

4.4

In plain words

The problem it solves

Data sources, lifecycle rules and provisioners

6 concepts · about 45 minutes

Not everything is created by your code. Data sources read what exists, lifecycle rules change how Terraform treats a resource, and provisioners are an escape hatch to avoid.

5.1

Data sources

In plain words

A data block reads information from the provider without creating anything: the latest AMI, an existing VPC, the current account ID, a Route 53 zone.

The problem it solves

Infrastructure is shared. Your stack needs facts about things that another team or an earlier stack created, without copying IDs into code.

What it does

  • Evaluated during plan when arguments are known; otherwise deferred to apply.
  • Referenced as data.aws_vpc.shared.id.
  • Read-only: removing the block does not delete anything.
  • Failed lookups (zero or two matches) produce an error, which is useful as a safety check.

Common lookups

hcldata.tf
data "aws_caller_identity" "current" {}

data "aws_region" "current" {}

data "aws_vpc" "shared" {

    Name = "shared-prod"

Check yourself
Does deleting a data block delete the real object?

No. Data sources only read; they never create or destroy.

5.2

The lifecycle block

In plain words

lifecycle changes the default behaviour of one resource: block deletion, create the replacement first, or ignore some changes.

The problem it solves

Default behaviour is unsafe for certain resources. Replacing a database destroys data; replacing a load balancer in the wrong order causes downtime; autoscaling changes a count that Terraform keeps reverting.

What it does

  • prevent_destroy = true makes any plan that would destroy it fail.
  • create_before_destroy = true builds the new one, then deletes the old.
  • ignore_changes = [attr] stops Terraform diffing attributes changed by something else.
  • replace_triggered_by forces replacement when another resource changes.
  • Lifecycle arguments must be literal values, not variables.

Example

hcllifecycle.tf
resource "aws_db_instance" "main" {
  identifier     = "shop-prod"
  engine         = "postgres"
  instance_class = "db.t4g.medium"

  allocated_storage           = 50
  username                    = "shopadmin"
  manage_master_user_password = true
  skip_final_snapshot         = false
  final_snapshot_identifier   = "shop-prod-final"

  lifecycle {
    prevent_destroy = true
    ignore_changes  = [allocated_storage]
  }
}
Note

prevent_destroy only protects against Terraform. Someone deleting the resource in the console, or removing the whole block from code, still removes it (the latter fails only while the block remains).

5.3

Preconditions, postconditions and check blocks

In plain words

These are assertions in code. A precondition tests an assumption before a resource is created, a postcondition tests the result afterwards, and a check block runs independent health assertions.

The problem it solves

Silent wrong assumptions, such as picking an AMI of the wrong architecture, show up later as confusing failures.

What it does

  • precondition and postcondition live inside lifecycle, and fail the run with your message.
  • check "name" { assert { ... } } produces warnings, not errors, and can contain a scoped data source such as an HTTP probe.
  • Variable validation checks inputs; these check the world.

Example

hclassertions.tf
data "aws_ami" "app" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }

  lifecycle {
    postcondition {
      condition     = self.architecture == "x86_64"
      error_message = "The AMI must be x86_64."
    }
  }
}

  data "http" "home" {
    url = "https://shop.example.com/healthz"
  }

  assert {
    condition     = data.http.home.status_code == 200
    error_message = "Health endpoint did not return 200."
  }
}

The problem it solves

What it does

In plain words

The problem it solves

Occasionally you need to re-run something when an input changes, or fetch a value no provider offers.

What it does

  • terraform_data with triggers_replace re-creates itself when inputs change, so other resources can use replace_triggered_by.
  • external data runs on every plan, so it must be fast, free of side effects and deterministic.
  • Both create hidden dependencies on local tools being installed on whoever runs Terraform.

Example

5.6

Provisioners and why to avoid them

In plain words

Provisioners (local-exec, remote-exec, file) run scripts after a resource is created. HashiCorp documents them as a last resort.

The problem it solves

People use them to configure servers or call APIs when no resource exists. But Terraform cannot model what a script does.

What it does

  • Not tracked in the plan: you cannot see what they will do, and they do not run again unless the resource is recreated.
  • A failed provisioner marks the resource tainted, forcing recreation next time.
  • They need network access (SSH) from the machine running Terraform and credentials in code.
  • when = destroy provisioners fail destroy runs when the script breaks.
  • Better options: AMI baking with Packer, user_data or cloud-init, EKS add-ons and Helm releases, configuration tools, or a dedicated provider.

If you must

hcllocal-exec as a last resort
resource "terraform_data" "notify" {

  provisioner "local-exec" {
    command = "echo created ${aws_ecr_repository.shop.name} >> changes.log"
  }
}
Careful

If you find yourself writing remote-exec to install software, stop: use an image or user data.

State, remote backends and locking

8 concepts · about 50 minutes

State is Terraform's memory. Losing it, corrupting it or letting two people write at once are the most common ways to hurt a team, so this section is worth reading slowly.

Goals
  • Explain what the state file holds and why it must be shared and protected
  • Configure an S3 backend with native locking or DynamoDB locking
  • Choose between terraform_remote_state and data sources for sharing values
6.1

What state is

In plain words

The state is a JSON file that maps each resource in your code to the real object in the cloud, with all its attributes. By default it is terraform.tfstate in the working directory.

The problem it solves

Terraform cannot find "the bucket I created last week" by name alone. It needs a record of what it owns, plus metadata like dependencies, to plan correctly and to delete in the right order.

What it does

  • Plan compares three things: your code, the state, and the refreshed real infrastructure.
  • State holds every attribute, including passwords and keys, in plain text.
  • Never edit the JSON by hand; use terraform state subcommands.
  • Never commit it to Git.

Looking at state

bashInspect without editing
terraform state list
terraform state show aws_vpc.main
terraform show -json | head -c 600
Check yourself
Why is state sensitive?

It stores all resource attributes, including secrets such as passwords, in readable form.

6.2

Why local state fails for teams

In plain words

A local file on one laptop works for learning. For a team it breaks immediately.

The problem it solves

If two engineers run apply from separate copies, each overwrites the other's record, resources are duplicated or orphaned, and CI cannot see anything.

What it does

  • No sharing: CI and teammates have no state.
  • No locking: concurrent runs corrupt the picture.
  • No history or encryption: a deleted laptop is a lost infrastructure map.
  • Remote backends fix all of these.
6.3

The S3 backend

In plain words

The S3 backend stores state as an object in an S3 bucket. It is the standard choice on AWS.

The problem it solves

You want durable, encrypted, versioned shared storage that costs almost nothing and uses IAM for access control.

What it does

  • Enable bucket versioning so a bad state can be rolled back, plus encryption and Block Public Access.
  • key is the object path, so one bucket serves many stacks: prod/network/terraform.tfstate.
  • The backend block cannot use variables. Pass values with -backend-config or a partial configuration.
  • The bucket must exist before init; create it once manually or with a small bootstrap stack.

Configuring it

hclbackend.tf
terraform {
  backend "s3" {
    bucket       = "acme-tfstate-111122223333"
    key          = "prod/network/terraform.tfstate"
    region       = "eu-west-1"
    encrypt      = true
    use_lockfile = true
  }
}

6.4

State locking: S3 native lock and DynamoDB

In plain words

A lock makes a second run wait or fail while the first is writing. The S3 backend supports two ways to do this.

The problem it solves

Two applies at the same moment can write conflicting state. Locking turns that into a clear "state is locked" error.

What it does

  • Native S3 locking (use_lockfile = true) writes a .tflock object next to the state using S3 conditional writes. It needs no extra table. It arrived in Terraform 1.10 and became the recommended method; check the current docs for your version.
  • DynamoDB locking (dynamodb_table = "...") uses a table with partition key LockID. It is the older method and is deprecated in the S3 backend; plan a migration.
  • A crashed run can leave a lock; terraform force-unlock <ID> removes it. Only do so when you are sure nobody is running.
  • -lock-timeout=5m makes a run wait instead of failing.

DynamoDB variant for older versions

hclbackend.tf (legacy locking)
terraform {
  backend "s3" {
    bucket         = "acme-tfstate-111122223333"
    key            = "prod/network/terraform.tfstate"
    region         = "eu-west-1"
    encrypt        = true
    dynamodb_table = "acme-tflock"
  }
}
Careful

Do not enable both methods during migration longer than necessary, and test the permission set. Native locking needs s3:PutObject and s3:DeleteObject on the .tflock object too.

Check yourself
What does force-unlock do?

Removes a stuck lock; use it only when no run is active, since it allows concurrent writes.

In plain words

One stack often needs values from another, such as the VPC ID from the network stack. The two ways are reading its state with terraform_remote_state, or looking it up from the cloud with a normal data source.

The problem it solves

Copying IDs by hand goes stale. But reading another stack's whole state gives the reader access to all its secrets.

What it does

  • Prefer data sources or a parameter store across team boundaries.

6.8

Protecting state

In plain words

State is a secret store and the source of truth, so protect it like a production database.

The problem it solves

What it does

  • Enable versioning and consider MFA delete or object lock for the state account.
  • Avoid putting secrets in resources at all, so state holds fewer of them.
  • Split state per stack and environment to limit blast radius, and keep a restore procedure: list versions, copy back an earlier one.

7.1

When state must be changed by hand

In plain words

Normal changes go through plan and apply. State surgery is for the cases where the code changed shape but the real object did not: renamed resources, moved modules, adopted resources, or abandoned ones.

The problem it solves

What it does

  • Prefer declarative blocks (moved, import, removed) because they are reviewed in a plan and repeatable in every environment.

Modules and their design

8 concepts · about 45 minutes

A module is a folder of Terraform files used as a unit. Every configuration is already one (the root module). Good modules make a team faster; bad ones add a layer of confusion.

Goals
  • Explain what a module is and structure one with inputs, outputs and files
  • Decide what belongs in a module and what interface it should expose
  • Avoid common module mistakes such as thin wrappers and hidden provider configuration
8.1

What a module is

In plain words

A module is a directory of .tf files that takes inputs (variables), creates resources, and returns outputs. You call it from another configuration with a module block.

The problem it solves

Without modules, every team copies and pastes the same 200 lines of VPC code and fixes bugs in only some of the copies.

What it does

  • The root module is the directory where you run Terraform. Modules it calls are child modules.
  • A call looks like module "network" { source = "./modules/network" ... }.
  • Resources inside get addresses prefixed with module.network..
  • Each module call is a separate instance with its own inputs.

Calling a module

hclmain.tf
module "network" {
  source = "./modules/network"

  name       = "shop-prod"
  cidr_block = "10.0.0.0/16"
}

output "vpc_id" {
  value = module.network.vpc_id
}
8.2

Standard module layout

In plain words

By convention a module has main.tf, variables.tf, outputs.tf, versions.tf and a README.md, plus an examples/ folder and tests/.

The problem it solves

When every module is laid out differently, people cannot find things, and registries and documentation tools cannot parse them.

What it does

  • Required providers and versions go in versions.tf, but no provider blocks in reusable modules (the caller configures them).
  • Every variable has a type and description; every output has a description.
  • examples/ contains runnable calls that double as documentation and test fixtures.
  • terraform-docs generates the input and output tables for the README.

Layout on disk

textmodules/network
modules/network/
  main.tf
  variables.tf
  outputs.tf
  versions.tf
  README.md
  examples/basic/main.tf
  tests/basic.tftest.hcl

terraform-docs markdown table modules/network > modules/network/README.md
8.3

Inputs: the module's interface

In plain words

Variables are the public interface. Design them like a function signature: few, clearly named, typed and validated.

The problem it solves

Modules with 80 pass-through arguments are as hard to use as the raw resources, and every change to the interface breaks callers.

What it does

  • Expose business concepts (private_subnet_cidrs, enable_nat), not every attribute of every resource.
  • Give sensible defaults so the simple case needs few inputs.
  • Use object types with optional() for grouped settings.
  • Add validation to catch bad input early; prefer secure defaults such as encryption on.

Example

hclvariables.tf
variable "name" {
  type        = string
  description = "Name prefix for all resources"
}

variable "cidr_block" {
  type        = string
  description = "VPC CIDR range"
  default     = "10.0.0.0/16"

  validation {
    condition     = can(cidrnetmask(var.cidr_block))
    error_message = "cidr_block must be a valid IPv4 CIDR."
  }
}

variable "azs" {
  type        = list(string)
  description = "Availability zones to spread subnets over"
}

variable "single_nat_gateway" {
  type        = bool
  description = "Use one NAT gateway instead of one per zone"
  default     = false
}
Check yourself
Why should reusable modules not contain provider blocks?

The caller must choose credentials, regions and aliases; embedded providers also block deleting the module cleanly.

8.4

Outputs: what a module returns

In plain words

Outputs are the only values a caller can read from a module. Return IDs, ARNs and endpoints that other code needs.

The problem it solves

If a module returns nothing useful, callers must look up resources with data sources or copy IDs, undoing the benefit of reuse.

What it does

  • Return whole objects sparingly; stable, small outputs are easier to keep backward compatible.
  • Output lists of IDs for things made with count or for_each.
  • Mark sensitive outputs.
  • Changing or removing an output is a breaking change for callers.

Example

hcloutputs.tf
output "vpc_id" {
  description = "ID of the VPC"
  value       = aws_vpc.this.id
}

output "private_subnet_ids" {
  description = "IDs of private subnets in AZ order"
  value       = [for k in sort(keys(aws_subnet.private)) : aws_subnet.private[k].id]
}
8.5

What belongs in a module

In plain words

A module should represent one meaningful building block: a VPC, a database with its subnet group and security group, a cluster. It should be larger than one resource and smaller than a whole platform.

The problem it solves

Modules that wrap a single resource add indirection without value. Modules that do everything cannot be reused or tested.

What it does

  • Good cohesion: resources that are created, changed and destroyed together.
  • Avoid thin wrappers that only rename arguments of one resource.
  • Avoid god modules that create network, cluster, database and DNS in one call.
  • Rule of thumb: if you cannot describe the module in one sentence, split it.
Check yourself

8.6

Composition over nesting

In plain words

Prefer a flat set of small modules that the root wires together to modules that call other modules several levels deep.

The problem it solves

Deeply nested modules hide what is created, make provider passing painful and produce long addresses that are hard to refactor.

What it does

  • The root module passes outputs of one module as inputs to another: vpc_id = module.network.vpc_id.
  • Keep nesting to one level where possible.
  • Modules take dependencies as inputs (an ID) rather than creating or looking them up internally. This is dependency inversion for infrastructure.

Wiring modules

  name               = "shop-prod"

}
8.7

Passing providers and count/for_each on modules

In plain words

Modules can be repeated with for_each or count, and can receive non-default providers through a providers map.

The problem it solves

You may need one module instance per team or per region, or a module that works in a second account.

What it does

  • module "team" { for_each = var.teams ... } creates one instance per key; access with module.team["a"].
  • providers = { aws = aws.dr } passes an aliased provider to the child.
  • Modules with their own provider configuration cannot be used with for_each, another reason to keep providers in the root.
  • Declare configuration_aliases in the child's required_providers when it needs more than one.

Example

hclfor_each on a module

8.8

Anti-patterns to avoid

In plain words

Some module habits look neat and cause pain later.

The problem it solves

Teams hit these repeatedly: broken callers, giant plans, and impossible upgrades.

What it does

  • Hidden provider config inside modules.
  • Boolean explosion: dozens of enable_x flags create combinations nobody tests.
  • Wrapping the community module only to rename its inputs.
  • Hard-coded names that prevent two instances in one account.
  • Reading remote state inside a module, which couples it to a layout.
  • No versioning: all callers use main and break together.

Module sources, versioning and the registry

7 concepts · about 45 minutes

Once a module is shared, its version matters more than its code. This section covers where modules come from and how to change them without breaking consumers.

Goals
  • Choose a module source such as local path, Git tag or registry and pin it correctly

9.1

Module sources

In plain words

The source argument says where Terraform downloads a module from during init: a local path, a Git repository, a registry, an S3 bucket and more.

The problem it solves

Teams need one way to reuse code within a repo and another across repositories and organisations.

What it does

  • Local: ./modules/network (always the current checkout, no version).
  • Git: git::https://github.com/acme/terraform-aws-network.git?ref=v1.4.0 (tag, branch or commit).
  • Registry: terraform-aws-modules/vpc/aws with a separate version argument.
  • terraform init copies modules into .terraform/modules; terraform get refreshes them.
  • Monorepo subdirectory: git::https://...//modules/network?ref=v1.4.0 (double slash).

Examples

hclThree sources
module "local" {
  source = "./modules/network"
}

  source = "git::https://github.com/acme/terraform-aws-network.git?ref=v1.4.0"
}

module "registry" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"
}
9.2

Pinning versions

In plain words

Always pin a module to a version or tag. Unpinned modules change when the source repository changes.

The problem it solves

If production tracks main, an unrelated merge in the module repo changes your next plan, and you cannot reproduce last week's run.

What it does

  • Registry modules use version constraints; Git modules use ?ref= with a tag or commit SHA, not a moving branch.
  • Use exact versions for production roots and ~> ranges only where you review upgrades.
  • Dependency tools such as Renovate and Dependabot open upgrade pull requests for module and provider versions.
  • Read the changelog and the plan in that pull request.
Check yourself
Why is ?ref=main a bad pin?

A branch moves, so the same code can produce different plans over time.

9.3

Semantic versioning for modules

In plain words

Version numbers MAJOR.MINOR.PATCH tell consumers the risk: patch fixes bugs, minor adds backward compatible features, major may break callers.

The problem it solves

Consumers need to know whether upgrading will change their infrastructure.

What it does

  • Breaking changes: removing or renaming a variable or output, changing a default that alters resources, renaming resources without a moved block, raising the minimum provider major version.
  • Minor: adding an optional variable with a default that changes nothing, adding an output.
  • Add moved blocks inside the module so internal renames do not destroy resources for callers.
  • Record changes in a CHANGELOG and tag releases.

Release routine

Environment strategy

7 concepts · about 50 minutes

The same infrastructure usually exists in several environments. The question is how to keep them alike where they should be and different where they must be, without one mistake reaching production.

What an environment strategy must give you

The testing pyramid for infrastructure

In plain words

Checks range from instant and free (formatting, syntax) to slow and real (creating infrastructure and testing it). Run the cheap ones often, the expensive ones rarely.

Teams either test nothing and discover errors in production, or run slow full deployments for every typo.

7 concepts · about 50 minutes

Static checks cannot prove a module behaves correctly. Tests create or plan the module with sample inputs and assert on the result. Policy as code enforces rules that apply to every change.

12.1

terraform test

In plain words

terraform test runs files named *.tftest.hcl. Each run block executes a plan or apply of your module with given variables, then evaluates assert conditions.

The problem it solves

Before native tests, module authors used external languages for even simple checks like "the VPC has three subnets".

What it does

  • Test files live in tests/ or next to the module.
  • command = plan is fast and creates nothing; command = apply (default) creates real resources and destroys them after the test.
  • variables blocks set inputs; assert blocks check outputs and resource attributes.
  • expect_failures verifies that bad input is correctly rejected by a validation.

  azs  = ["eu-west-1a", "eu-west-1b"]
}

  command = plan

  assert {
    condition     = length(output.private_subnet_ids) == 2
    error_message = "Expected one private subnet per AZ."
  }
}

run "rejects_bad_cidr" {
  command = plan

  variables {
    cidr_block = "not-a-cidr"
  }

  expect_failures = [var.cidr_block]
}

13.1

What drift is

In plain words

Drift is when real infrastructure no longer matches the code and state, usually because someone changed it in the console, a script ran, or another tool modified it.

The problem it solves

The next apply will either undo the change silently or fail. Drift in security groups or IAM can also be a security incident.

What it does

  • Common sources: emergency console fixes, autoscaling, operators and controllers editing AWS resources, expired or rotated values.
  • Terraform detects drift during every plan, since it refreshes state from the API.
  • Resolve by either updating the code to match reality, or applying to revert reality.
13.2

A scheduled pipeline runs terraform plan -detailed-exitcode regularly and alerts when it returns exit code 2.

The problem it solves

Without checks, drift is found only when someone makes an unrelated change and a surprising plan appears.

What it does

  • Exit codes: 0 no changes, 1 error, 2 changes pending.
  • Run nightly per stack using a read-only role, and send findings to Slack or open an issue.
  • terraform apply -refresh-only records accepted drift in state without changing infrastructure.
  • Commercial tools (HCP Terraform health checks, Spacelift, env0) offer drift detection too.

In plain words

A moved block tells Terraform that a resource has a new address, so it updates state instead of destroying and recreating.

The problem it solves

Renaming a resource, adding count or for_each, or moving it into a module changes its address, which looks like delete plus create.

What it does

  • Syntax: moved { from = old_address to = new_address }.
  • Appears in the plan as "has moved to"; apply updates the state entry.
  • Works for resources, modules and changes between single, count and for_each instances.
  • Keep the block in the code for as long as any state might still hold the old address; for shared modules, keep it indefinitely.
  • Preferred over terraform state mv because it is reviewed and applies in every environment.

Refactoring workflow

In plain words

Refactoring means changing code structure without changing infrastructure. The test of success is a plan that shows no changes (apart from moves).

The problem it solves

Reshaping a large configuration can accidentally recreate production resources.

What it does

  • Make small steps: one rename or extraction per pull request.
  • Add moved blocks first, then run plan and read for any destroy or replace.
  • Extracting a module: create the module, add moved blocks from root addresses to module.x.address, plan, apply.
  • Splitting a state: use removed and import blocks, or state mv between states, with backups.

Check for surprises

What is the success criterion of a refactor?

The plan shows only moves and no create, update or destroy of real resources.

13.5

Splitting a big state

In plain words

Over time one state grows to hundreds of resources: plans become slow, locks collide and every change risks everything.

The problem it solves

Blast radius and run time grow with the size of a state.

What it does

  • Split along change frequency and ownership: network (rare), cluster (occasional), application infrastructure (often).
  • Procedure: back up, move resources with terraform state mv -state-out, or removed plus import blocks in the new stack; plan both stacks until clean.
  • Connect stacks afterwards with data sources or published parameters instead of shared state.
  • Avoid splitting too finely, which makes ordering and sharing harder.

Safe destroys

In plain words

The problem it solves

What it does

  • Protect stateful resources: prevent_destroy, RDS deletion_protection, S3 versioning and force_destroy = false, final snapshots.

Common failures and fixes

In plain words

Some errors appear again and again. Recognising them saves hours.

The problem it solves

Under pressure people reach for state edits or force flags that make things worse.

What it does

  • Error acquiring the state lock: someone else is running, or a crash left a lock. Wait, then force-unlock only if sure.
  • Resource already exists: created outside; import it.
  • Cycle: two resources depend on each other; break with a separate rule resource (for security groups, use standalone rule resources).
  • Provider produced inconsistent result: usually a provider bug or eventual consistency; re-run plan, check issues for the provider version.
  • Value depends on resource attributes that cannot be determined: a for_each key is unknown; use static keys.

14.1

Why run Terraform in CI

In plain words

A pipeline runs plan on every pull request and apply after merge, using one identity with the right permissions.

The problem it solves

Laptop applies have no review trail, depend on local versions and credentials, and let people apply code that was never merged.

What it does

14.2

GitHub OIDC to AWS

In plain words

GitHub Actions can request a short-lived signed token (OIDC) that proves "this job runs in repo X on branch Y". AWS trusts that token and hands out temporary credentials. No secret is stored in GitHub.

The problem it solves

Static IAM access keys stored as secrets leak, never expire and are shared. OIDC replaces them with credentials that last about an hour.

What it does

  • In AWS, create an IAM OIDC identity provider for token.actions.githubusercontent.com.
  • Create a role whose trust policy allows sts:AssumeRoleWithWebIdentity only for matching claims (sub, aud).
  • The workflow needs permissions: id-token: write and the aws-actions/configure-aws-credentials action.
  • Restrict sub to the repo and the branch or environment, never a wildcard on the whole organisation.

Trust relationship in Terraform

hcloidc.tf
resource "aws_iam_openid_connect_provider" "github" {
  url            = "https://token.actions.githubusercontent.com"
  client_id_list = ["sts.amazonaws.com"]
}

data "aws_iam_policy_document" "trust_apply" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:acme/infra:environment:prod"]
    }
  }
}

14.3

Separate roles for plan and apply

In plain words

Use two roles: a read-only role for pull request plans and a write role for apply that only the main branch or a protected environment can assume.

The problem it solves

If pull requests can assume an admin role, anyone who can open a PR (or a malicious dependency in it) can change production.

What it does

  • tf-plan role: read access plus the ability to read and lock state; its trust allows pull_request subjects.
  • tf-apply role: write permissions; trust allows only environment:prod or the main branch.
  • A GitHub environment with required reviewers makes the apply job wait for approval, and gives a sub of repo:org/repo:environment:prod.
  • Scope permissions to the resources managed; avoid AdministratorAccess where practical, but accept it initially for infrastructure bootstrap roles.

In plain words

Reviewers need to see what the change does, not only the diff of the code.

What it does

  • Run fmt, validate, then plan -out and upload the plan as an artifact for apply, or re-plan at apply time.

Pipeline safety checklist

In plain words

A short list of controls that stop most CI mistakes and compromises.

The network module

In plain words

The network module creates a VPC with public subnets (load balancers, NAT) and private subnets (nodes, database) in each availability zone.

The problem it solves

Kubernetes and databases need private address space, internet egress through NAT, and subnet tags so the AWS load balancer controller finds the right subnets.

What it does

  • Uses cidrsubnet to carve subnets from the VPC range, keyed by AZ with for_each.
  • Tags subnets with kubernetes.io/role/elb (public) and kubernetes.io/role/internal-elb (private).
  • Outputs the VPC ID and lists of subnet IDs.
  • In production, prefer the community VPC module if you need VPC endpoints, flow logs and many options; the small version shows the idea.

16.1

OpenTofu: what and why

In plain words

OpenTofu is an open-source fork of Terraform, hosted by the Linux Foundation. It was created after HashiCorp changed Terraform's licence from MPL to the Business Source License in August 2023 (starting from version 1.6).

The problem it solves

Companies and vendors that build products around Terraform needed a guarantee that the core tool stays open source and governed by a community.

What it does

  • Forked from the last MPL release, Terraform 1.5.x; its first stable release was 1.6.
  • Command is tofu (tofu init, tofu plan, tofu apply); configuration files are the same HCL.
  • Uses its own registry at registry.opentofu.org, which mirrors most providers.
  • HashiCorp is now part of IBM; keep an eye on licensing and roadmaps and check current terms.
16.2

Compatibility and differences

In plain words

For most configurations, tofu and terraform are interchangeable. The two have diverged and each has features the other lacks.

The problem it solves

A team must know whether they can move, and what they would lose or gain.

What it does

  • OpenTofu features include native state encryption, early evaluation of variables in backend and module source, for_each on providers, and a -exclude flag; check the current release notes for the full list.
  • Terraform features include HCP Terraform integration, Sentinel, and its own newer features such as ephemeral values and stacks; availability in OpenTofu varies.
  • State files are compatible up to the fork point. Later Terraform versions may write state that OpenTofu cannot read; always test first.
  • The terraform block works in both; use required_version consistently.

A wrong choice causes either giant pull requests and slow CI, or version drift and copy-pasted code.

18.7

Stacks, dependency graphs and blast radius

In plain words

Blast radius is how much one bad apply can damage. Split infrastructure into layers that change at different speeds so a mistake in one cannot reach the rest.

The problem it solves

One state for everything means every plan touches everything, takes long and one error can delete the database.

What it does

  • Layers by rate of change: foundations (accounts, DNS), network, platform (EKS), data, applications.
  • Each layer is its own state. Higher layers read lower ones through outputs, data sources or a parameter store; dependencies flow one way and form a graph without cycles.
  • Run order is the topological order of this graph. Tools such as Terragrunt run-all, Terraform Stacks in HCP (check current docs) or a CI matrix encode it.
  • Add guards: prevent_destroy on data, separate IAM roles per layer, and manual approval for lower layers.
  • Rule of thumb: if a plan lists more than a few hundred resources, split it.
Check yourself
Why must dependencies flow in one direction?

Cycles between stacks make apply order impossible and destroy needs the reverse order; one-way flow keeps both defined.

19.1

What a provider is

In plain words

A provider is a separate program that Terraform starts and talks to over gRPC. It translates resource blocks into API calls for one service.

The problem it solves

Terraform core knows nothing about AWS, GitHub or your internal platform. Providers keep that knowledge outside core and allow anyone to extend it.

What it does

  • terraform init downloads providers from a registry and records versions and hashes in .terraform.lock.hcl.
  • Each provider declares resource types, data sources, and optionally functions, with schemas.
  • Core calls it to validate, plan (diff), apply (create, read, update, delete) and read.
  • Providers are written in Go. The recommended library today is the Terraform Plugin Framework; the older SDKv2 still exists.

Pinning providers

hclversions.tf
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

When to write a provider

In plain words

Write one only when no existing provider or simpler path covers your API.

The problem it solves

Providers are real software: Go code, tests, releases, documentation and upgrades. A provider written for one small script becomes a burden.

What it does

  • First look for an existing one on the registry, or for a generic option: the http data source, restapi community providers, or terraform_data with a local script.
  • Justified when: an internal platform API is used by many teams, you want drift detection and plan output for it, or a vendor has no provider.
  • Cost estimate: schema design, CRUD functions, acceptance tests, signed releases and docs.
  • OpenTofu and Terraform share the plugin protocol, so one provider usually works with both.

What it does

19.4

Writing a resource

In plain words

A resource implements four methods that map to the API, plus a schema that describes its fields.

The problem it solves

Terraform only works well if Read returns exactly what the API holds, so drift is visible, and if Create stores computed IDs in state.

What it does

  • Schema: name Required, id Computed, optional settings with defaults using plan modifiers.
  • Create: read the plan into a model, call the API, write the result (including generated ID) to state.
  • Read: fetch by ID; if the API says not found, remove the resource from state so Terraform recreates it.
  • Update and Delete follow the same pattern. Add ImportState so terraform import works.
  • Return errors as diagnostics with clear text; never panic.

Method outline

goresource_item.go
func (r *itemResource) Create(ctx context.Context, req resource.CreateRequest, resp *resource.CreateResponse) {
	var plan itemModel
	resp.Diagnostics.Append(req.Plan.Get(ctx, &plan)...)
	if resp.Diagnostics.HasError() {
		return
	}

	created, err := r.client.CreateItem(ctx, plan.Name.ValueString())
	if err != nil {
		resp.Diagnostics.AddError("Cannot create item", err.Error())
		return
	}

	plan.ID = types.StringValue(created.ID)
	resp.Diagnostics.Append(resp.State.Set(ctx, plan)...)
}

The problem it solves

What it does

19.6

Import blocks and generated configuration

In plain words

An import block tells Terraform that an existing object should become a given resource address. With -generate-config-out, Terraform writes the matching HCL for you.

The problem it solves

Hand-writing code for 200 existing resources and running terraform import one at a time is slow and not reviewable.

What it does

  • The import block holds to (address) and id (provider-specific import ID, found in the resource docs).
  • terraform plan -generate-config-out=generated.tf writes a draft resource block. Clean it up: remove defaults and computed attributes, replace literals with variables.
  • Import blocks are planned like any change, so the pull request shows exactly what will be adopted. Remove the blocks after apply.
  • A clean follow-up plan with zero changes proves the code matches reality.

Example

hclimport.tf
import {
  to = aws_s3_bucket.logs
  id = "acme-central-logs"
}

import {
  for_each = toset(["sg-0123456789abcdef0", "sg-0fedcba9876543210"])
  to       = aws_security_group.legacy[each.key]
  id       = each.key
}
bashGenerate code
terraform plan -generate-config-out=generated.tf
terraform apply
Note

for_each in import blocks needs a recent Terraform release; check the current docs for your version.

Check yourself
How do you know an import is complete?

A plan after the import shows no changes, meaning the code matches the real object.

19.7

Migrating console-built infrastructure

In plain words

Moving to Terraform is a programme, not a command. Work in slices and keep production running throughout.

The problem it solves

Big-bang rewrites stall, and half-imported estates are worse than none because nobody trusts either source.

What it does

  • Inventory first: tag or list resources by owner and layer. Tools such as terraformer or the AWS Resource Explorer can help; always review output.
  • Import foundations first (network, IAM), then data, then compute. Each slice gets its own state.
  • Freeze console changes for the slice being imported, and enable drift checks afterwards.
  • Add a service control policy or IAM boundary later that blocks console writes in production.
19.8

CloudFormation to Terraform

In plain words

Existing CloudFormation stacks can be replaced with Terraform without deleting resources, if you retire the stack carefully.

The problem it solves

Deleting a stack deletes its resources. Importing them while the stack still owns them leaves two owners.

What it does

  • Step 1: set DeletionPolicy: Retain on every resource in the template and update the stack.
  • Step 2: import the resources into Terraform and reach a clean plan.
  • Step 3: delete the CloudFormation stack. Retained resources stay.
  • Alternatively, keep CloudFormation for what AWS manages best (for example StackSets and Control Tower) and use Terraform for the rest.
  • Resources with generated names cannot always be imported by name; look up the ID in the stack outputs or aws cloudformation list-stack-resources.

Commands

Never delete the stack before every resource is retained. A stack delete removes anything without the Retain policy.

20.1

Infracost in a pull request

In plain words

Infracost reads Terraform code or a plan and prices the resources from cloud price lists. It posts the monthly cost difference on the pull request.

The problem it solves

A one-line change such as an instance type or an extra NAT gateway can add hundreds of dollars a month, and nobody notices until the bill.

What it does

  • infracost breakdown --path . prints the monthly estimate. infracost diff compares against a baseline.
  • Run with a plan JSON for the most accurate result, since counts and conditionals are resolved.
  • Usage-based items such as data transfer or requests need a usage file; without it they show zero or defaults.
  • Check the current Infracost docs for CLI flags, pricing API keys and the GitHub integration.

Local run

bashBreakdown and diff
terraform plan -out tfplan
terraform show -json tfplan > plan.json
infracost breakdown --path plan.json
infracost diff --path plan.json --compare-to baseline.json
20.2

Reading estimates and the arithmetic behind them

In plain words

Most estimates are hours in the month multiplied by an hourly price, plus storage and usage.

The problem it solves

Numbers without a feel for the arithmetic are either trusted blindly or ignored.

What it does

  • A month has about 730 hours (8 760 hours per year divided by 12).
  • NAT gateway at an example rate of 0.045 dollars per hour: 0.045 × 730 = 32.85 dollars per month before data processing charges. Three of them: 98.55.
  • Moving prod from one NAT to three adds 65.70 per month in hourly charges alone.
  • Prices differ by region and change over time; use the tool, not these example rates.
Check yourself

2 × 0.045 × 730 = 65.70 dollars per month.

In plain words

Triage: severities, suppressions and false positives

In plain words

Scanners produce many findings. Triage decides which block the pipeline, which become tickets and which are accepted with a reason.

The problem it solves

If every finding fails the build, teams disable the scanner. If none do, it is theatre.

What it does

  • Start in report-only mode, fix the critical ones, then fail on HIGH and CRITICAL only.
  • Suppress with an inline comment that carries a reason, for example #checkov:skip=CKV_AWS_18:access logs bucket itself , so exceptions are visible in review.
  • Keep a baseline file for old findings so only new ones block.
  • Review suppressions quarterly; expired reasons are risk.

Inline suppression

Why require a reason in each suppression?

It makes the exception reviewable and lets later audits decide whether it still applies.

Secrets, state and supply chain risks

In plain words

Terraform code and state are part of your attack surface. Credentials, modules and providers all come from somewhere.

The problem it solves

A leaked state file exposes secrets. A tampered module or provider runs with your cloud credentials.

What it does

  • Do not put secrets in .tf or .tfvars. Use Secrets Manager or SSM, ephemeral values and write-only attributes where your provider and Terraform version support them (check the current docs).
  • Mark outputs and variables sensitive = true; this only hides them in CLI output, state still holds them.
  • Commit .terraform.lock.hcl, pin module versions to tags or digests, and review upgrades via Renovate or Dependabot.
  • Scan for committed secrets with gitleaks or the GitHub secret scanning feature.
  • CI uses OIDC with a role limited to what that stack needs.

Reading a secret at runtime

Data sources still write the value into state. Prefer letting the application read the secret itself, and give Terraform only the ARN.

Ten Terraform troubleshooting scenarios

10 concepts · about 55 minutes

Each scenario gives the symptom, the cause, the fix and how to prevent it. Before changing anything: read the full error, take a copy of the state, and make sure nobody else is applying.

Goals
  • Diagnose the ten most common Terraform failures from their symptoms
  • Apply the safest fix for each and avoid making state worse
  • Build a habit of reading the error and the plan before acting
21.1

Scenario 1, state lock held by a dead run

In plain words

Plan fails with "Error acquiring the state lock" and shows a lock ID, owner and time.

The problem it solves

A CI job was cancelled mid-apply or a laptop lost power, and the lock was never released.

What it does

  • First confirm the owner and time. If the run is still going, wait; do not unlock.
  • With S3 native locking, the lock is a .tflock object beside the state. With DynamoDB it is a row keyed by LockID.
  • Remove it with terraform force-unlock <ID> once you are sure nothing runs.
  • Prevent repeats: use -lock-timeout, and make CI jobs non-cancellable during apply.

Commands

bashUnlock
terraform plan -lock-timeout=2m
terraform force-unlock LOCK_ID
terraform plan
21.2

Scenario 2, plan wants to replace a resource

In plain words

Plan shows -/+ destroy and then create replacement for a database or load balancer after a harmless edit.

The problem it solves

Some attributes cannot change in place. Changing them forces replacement, which for a database means data loss.

What it does

  • Read the line marked # forces replacement to see the exact attribute.
  • Revert the change or find an in-place alternative (for example a separate resource for the setting).
  • If a rename caused it, use a moved block so the address changes without recreation.
  • Protect important resources with prevent_destroy = true so the plan errors instead.

Rename without recreation

hclmoved block
moved {
  from = aws_db_instance.main
  to   = aws_db_instance.primary
}
Check yourself
Which block renames an address with no recreation?

A moved block with from and to.

21.3

Scenario 3, AccessDenied and expired credentials

In plain words

Errors like AccessDenied, ExpiredToken or no valid credential sources appear during plan or apply.

The problem it solves

The identity used by Terraform lacks permission, or its token expired during a long apply.

What it does

  • Run aws sts get-caller-identity in the same environment to see who you really are.
  • OIDC role sessions have a maximum duration (default one hour); a slow EKS plus RDS apply can exceed it. Raise the role session duration or split the stack.
  • The error text names the missing action, for example rds:CreateDBInstance. Add the least privilege needed, not *.
  • Assume-role chains and AWS_PROFILE in the shell can silently point to another account; print the account ID before apply.

Scenario 4, drift after a manual console change

In plain words

A plan shows changes nobody wrote, for example a security group rule reverting, or tags being removed.

The problem it solves

Someone edited the resource by hand, or another controller (autoscaler, Kubernetes controller) modifies it.

What it does

  • Decide who is right. If the console change should stay, update the code. If not, apply to revert it.
  • For attributes managed by something else, use lifecycle { ignore_changes = [...] }.
  • Detect drift early: scheduled terraform plan -detailed-exitcode (exit code 2 means changes) in CI that alerts.
  • Reduce root causes with IAM policies denying console writes in production.
