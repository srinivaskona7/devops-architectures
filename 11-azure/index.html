Section 1 of 16

Tenants, management groups, subscriptions and resource groups

8 concepts · about 50 minutes

Azure organises everything in a tree. Knowing where each level sits tells you where to attach access, rules and cost, and it is the first thing to map when you come from AWS.

Goals
  • Map the Azure resource hierarchy onto AWS Organizations and accounts
  • Choose the right scope for policy, RBAC and billing
  • Use resource groups, regions, zones and tags to organise and govern resources
1.1

The Azure hierarchy at a glance

In plain words

Azure has four nesting levels: a tenant at the root, management groups below it, subscriptions inside those, and resource groups holding the actual resources.

The problem it solves

Without a hierarchy you cannot apply one rule or one permission to hundreds of environments at once.

What it does

  • AWS equivalent: Organization root, OUs, accounts. Azure has an extra layer, the resource group, which has no AWS twin.
  • Main difference: the Azure subscription is the billing and quota boundary but not as hard an isolation wall as an AWS account. Identity lives in the tenant, not in the subscription.
  • Permissions and policy set on a level are inherited by everything beneath it.

List your own tree

bashWhere am I
az account show --query '{sub:name,id:id,tenant:tenantId}' -o json
az account list --query '[].{name:name,state:state}' -o table
az account management-group list --query '[].{name:name,display:displayName}' -o table
Check yourself
Which Azure level is the closest to an AWS account?

The subscription.

1.2

Tenants and Microsoft Entra ID

In plain words

A tenant is a dedicated instance of Microsoft Entra ID (formerly Azure Active Directory). It holds users, groups and applications and is trusted by your subscriptions.

The problem it solves

Someone has to answer "who are you" for every subscription. Doing it per subscription would mean duplicated users everywhere.

What it does

  • AWS equivalent: IAM Identity Center plus the Organization, roughly. Plain AWS IAM users live per account.
  • Main difference: one tenant holds all identities, and many subscriptions trust it. A subscription belongs to exactly one tenant at a time, but can be moved.
  • Every tenant has an ID (a GUID) and a default *.onmicrosoft.com domain.
  • Most companies run one production tenant. Separate tenants are used for strict isolation or acquisitions.

Find the tenant

bashTenant details
az account show --query tenantId -o tsv
az rest --method get --url https://graph.microsoft.com/v1.0/organization --query 'value[0].{name:displayName,id:id}' -o json
Note

Tenant ID appears in every token's tid claim and in login URLs. It is not a secret.

1.3

Management groups

In plain words

A management group is a folder for subscriptions. You attach policy and role assignments to it and every subscription below inherits them.

The problem it solves

Applying "only EU regions" to forty subscriptions one by one is slow and error prone.

What it does

  • AWS equivalent: Organizational Units with SCPs.
  • Main difference: Azure Policy and RBAC are inherited down the tree, but there is no deny-everything SCP that overrides even owners. Deny effects in Policy and denyAssignments come close.
  • Up to six levels deep below the tenant root group (check the current limits).
  • Typical design from the Cloud Adoption Framework: Platform (Identity, Connectivity, Management) and Landing zones (Corp, Online), plus Sandbox and Decommissioned.

Create and move

bashManagement group commands
az account management-group create --name mg-landingzones --display-name "Landing Zones" --parent mg-contoso
az account management-group subscription add --name mg-landingzones --subscription 00000000-0000-0000-0000-000000000000
Check yourself
What gets inherited by subscriptions placed in a management group?

Azure Policy assignments and RBAC role assignments made on that group.

1.4

Subscriptions

In plain words

A subscription is the container that gets billed, has quotas and holds resource groups. Most workloads get one subscription per environment or per team.

The problem it solves

You need a boundary for cost reporting, service limits and blast radius.

What it does

  • AWS equivalent: AWS account.
  • Main difference: quotas (vCPU per region and family, public IPs) are per subscription per region, and you ask for more with a support request. There is no separate root user; access is through Entra and RBAC only.
  • Subscriptions can be created through an enrolment (EA, MCA) with the Microsoft.Subscription APIs, which allows subscription vending automation.
  • Resource providers such as Microsoft.ContainerService must be registered in a subscription before first use.

Register providers and check quota

bashProvider and usage checks
az provider register --namespace Microsoft.ContainerService --wait
az provider show --namespace Microsoft.ContainerService --query registrationState -o tsv
az vm list-usage --location westeurope --query "[?contains(name.value,'standardDSv5Family')]" -o table
1.5

Resource groups

In plain words

A resource group is a logical box for resources that share a lifecycle. Delete the box and everything inside goes with it.

The problem it solves

Resources created for one application need to be deployed, permissioned, tagged and cleaned up together.

What it does

  • AWS equivalent: CloudFormation stack or a tag-based resource group, but mandatory. Every resource lives in exactly one group.
  • Main difference: the group has a region, but that only stores metadata. Resources inside can be in other regions. RBAC and policy can be assigned at group scope.
  • Moving resources between groups is possible for many types but not all; check the move support table.
  • Pattern: one group per application per environment, plus separate groups for networking and shared items that live longer.

Create and clean up

bashResource group lifecycle
az group create --name rg-shop-dev --location westeurope --tags app=shop env=dev owner=platform
az resource list --resource-group rg-shop-dev -o table
az group delete --name rg-shop-dev --yes --no-wait
Danger

az group delete removes every resource inside, including databases. Use resource locks on production groups.

Check yourself
Does the region of a resource group limit where its resources can be?

No. It only stores the group metadata.

1.6

Azure Resource Manager and resource IDs

In plain words

Azure Resource Manager (ARM) is the single API front door. Portal, CLI, Bicep, Terraform all call it, and every resource has a path-like ID.

The problem it solves

You need one consistent way to authenticate, authorise, log and deploy every service.

What it does

  • AWS equivalent: the AWS control plane APIs plus ARNs and CloudTrail. Azure has one shared layer, which is why RBAC, policy, tags and locks work the same on every resource type.
  • A resource ID looks like /subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Storage/storageAccounts/<name>.
  • Templates (ARM JSON, Bicep) are declarative and idempotent; deployments run at tenant, management group, subscription or resource group scope.
  • Every write is recorded in the Activity Log.

Call ARM directly

bashaz rest
az rest --method get --url "https://management.azure.com/subscriptions/$(az account show --query id -o tsv)/resourcegroups?api-version=2021-04-01" --query 'value[].name' -o tsv
1.7

Regions, region pairs and availability zones

In plain words

A region is a set of datacentres in one area. Many regions have three availability zones, physically separate locations with independent power and network.

The problem it solves

You must survive the loss of a datacentre or a whole area without losing the service.

What it does

  • AWS equivalent: Region and Availability Zone. Same idea.
  • Main difference: zone names are logical per subscription, so zone 1 in your subscription may map to a different physical zone than in another subscription. Not every region has zones; check the list of regions with zones. Some services are zone-redundant by a flag, others you place per zone.
  • Region pairs exist for geo-redundant storage and some platform failover. Pairs do not mean automatic failover for your apps.
  • Prices and available SKUs differ per region.

Zones and SKUs

bashWhere can I run
az account list-locations --query "[?metadata.regionType=='Physical'].{name:name,pair:metadata.pairedRegion[0].name}" -o table
az vm list-skus --location westeurope --size Standard_D4s_v5 --query '[0].locationInfo[0].zones' -o tsv
Check yourself
Why is zone 1 not a fixed physical place across subscriptions?

Zone numbers are logical and mapped per subscription.

1.8

Tags

In plain words

Tags are name and value pairs on resources, resource groups and subscriptions used for cost reports, ownership and automation.

The problem it solves

A bill that says "compute 40 000" without owner information cannot be acted on.

What it does

  • AWS equivalent: resource tags and cost allocation tags.
  • Main difference: tags are not inherited by default. Use Azure Policy (modify effect, or the built-in "Inherit a tag from the resource group") to copy them down. Also tags are not always shown in cost data for every resource type; check current docs.
  • Up to 50 tags per resource; names are case-insensitive, values case-sensitive.
  • Typical set: app, env, owner, costcenter.

Tag and query

bashTagging
az group update --name rg-shop-prod --set tags.costcenter=1234 tags.owner=shop-team
az resource list --tag app=shop --query '[].{name:name,type:type}' -o table
az tag update --resource-id /subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-shop-prod --operation merge --tags env=prod

Section 2 of 16

Azure service map and AWS equivalents

8 concepts · about 45 minutes

You already know AWS. This page is a translation table with the traps marked. Later pages go deep on each area.

Goals
  • Translate common AWS services into their Azure counterparts
  • Spot the places where the two clouds behave differently
  • Pick the Azure service for each tier of a typical web application
2.1

Compute map

In plain words

Azure has the same compute shapes as AWS: virtual machines, scale groups, containers, functions and managed Kubernetes.

The problem it solves

Searching the Azure catalogue by name alone wastes time because the names differ.

What it does

  • EC2 maps to Virtual Machines; Auto Scaling groups to VM Scale Sets.
  • EKS maps to AKS; ECS and Fargate map loosely to Azure Container Apps and Container Instances.
  • Lambda maps to Azure Functions; Elastic Beanstalk to App Service; AWS Batch to Azure Batch.
  • Main difference: App Service and Container Apps are used far more often as the default web platform than Beanstalk or ECS in many AWS shops.

List what you can run

bashCompute services in your subscription
az provider list --query "[?contains(namespace,'Microsoft.Compute') || contains(namespace,'Microsoft.ContainerService') || contains(namespace,'Microsoft.App')].namespace" -o tsv
Check yourself
Which Azure service is the managed Kubernetes equivalent of EKS?

AKS.

2.2

Networking map

In plain words

A VPC is a VNet, a security group is mostly a network security group, and load balancing is split across four services.

The problem it solves

Network designs carried over from AWS fail on small differences such as subnet scope and route behaviour.

What it does

  • VPC is Virtual Network; Route 53 is Azure DNS and Traffic Manager; ALB is Application Gateway; NLB is Load Balancer; CloudFront is Front Door.
  • NAT gateway is NAT Gateway; Transit Gateway is Virtual WAN or hub VNet with peering; PrivateLink is Private Link; Network Firewall is Azure Firewall.
  • Main difference: subnets span all zones in a region, there are no route-table-per-AZ designs, and NSGs can attach to subnets and to NICs.

Quick inventory

bashNetworks in the subscription
az network vnet list --query '[].{name:name,rg:resourceGroup,space:addressSpace.addressPrefixes[0]}' -o table
2.3

Storage and database map

In plain words

Object, file and block storage all exist, and the managed databases cover SQL, open source engines, NoSQL and cache.

The problem it solves

Choosing the wrong data service early is expensive to reverse.

What it does

  • S3 is Blob Storage inside a storage account; EFS is Azure Files (NFS or SMB); EBS is Managed Disks.
  • RDS SQL Server is Azure SQL; RDS PostgreSQL and MySQL are Flexible Server; DynamoDB is Cosmos DB; ElastiCache is Azure Cache for Redis (check the current Managed Redis offering).
  • Main difference: the storage account is a mandatory wrapper that holds blobs, files, queues and tables with shared settings, so there is no direct equivalent of a bucket as top-level resource.

Data resources

bashWhat data services exist
az storage account list -o table
az postgres flexible-server list -o table
2.4

Identity and security map

In plain words

IAM splits into two systems on Azure: Entra ID for who you are and Azure RBAC for what you can do to resources.

The problem it solves

AWS engineers look for IAM roles and policies and cannot find a single place in Azure.

What it does

  • IAM users and Identity Center map to Entra ID; IAM roles for services map to managed identities; IAM policies map to RBAC role assignments (plus Policy for guardrails).
  • KMS and Secrets Manager map to Key Vault; ACM maps to Key Vault certificates; GuardDuty and Security Hub map to Microsoft Defender for Cloud.
  • Main difference: Azure roles are assigned to a principal at a scope, rather than a policy document attached to an identity.

Who am I

bashCurrent identity
az ad signed-in-user show --query '{upn:userPrincipalName,id:id}' -o json
az role assignment list --assignee $(az ad signed-in-user show --query id -o tsv) --all -o table
2.5

Monitoring and DevOps map

In plain words

CloudWatch is replaced by Azure Monitor with Log Analytics, and the CodeSuite is replaced by Azure DevOps or GitHub Actions.

The problem it solves

Teams re-create observability from scratch when they could use built-in services.

What it does

  • CloudWatch Metrics is Azure Monitor Metrics; CloudWatch Logs is Log Analytics queried with KQL; X-Ray is Application Insights.
  • CloudTrail is the Activity Log; Config is Azure Policy and Resource Graph.
  • CodeBuild, CodePipeline and CodeDeploy map to Azure Pipelines or GitHub Actions; ECR maps to ACR.
  • CloudFormation maps to ARM and Bicep; Terraform works on both.
  • Prometheus and Grafana can be fully managed with Azure Monitor managed service for Prometheus and Azure Managed Grafana.

Resource Graph query

bashCross-subscription inventory
az graph query -q "resources | summarize count() by type | order by count_ desc | take 10" -o table
2.6

Behavioural differences that bite

In plain words

Several defaults differ from AWS even when the service names line up.

The problem it solves

Assuming AWS behaviour leads to open ports, broken routing and surprise bills.

What it does

  • Outbound internet: new VNets give default outbound access, which Microsoft is retiring for new subnets in favour of explicit outbound (NAT Gateway or similar). Check the current announcement for your date.
  • Subnets and zones: a subnet is regional and spans zones. In AWS a subnet lives in one AZ.
  • Public IPs: Standard SKU IPs are secure by default and closed until an NSG allows traffic.
  • Metadata identity: managed identities use an IMDS endpoint, similar to instance profiles.
  • Cost: Azure charges for stopped but allocated VMs until you deallocate them.
  • IAM scope: role assignments propagate down the tree and can take minutes to apply.

Deallocate versus stop

bashStop paying for compute
az vm stop --resource-group rg-lab --name vm1
az vm deallocate --resource-group rg-lab --name vm1
az vm get-instance-view -g rg-lab -n vm1 --query 'instanceView.statuses[].displayStatus' -o tsv
Check yourself
Which command stops compute billing, stop or deallocate?

Deallocate. A stopped but allocated VM is still billed for compute.

2.7

Reading the Azure documentation like an AWS engineer

In plain words

Learn a handful of Azure terms and the documentation becomes easy to navigate.

The problem it solves

Azure docs mix old and new product names, which makes searches confusing.

What it does

  • SKU means a tier or size of a service (for example Basic, Standard, Premium).
  • Provider namespace is the Microsoft.* prefix in resource IDs.
  • Scope is where something is assigned: tenant, management group, subscription, resource group, resource.
  • Azure AD is the old name of Entra ID; commands called az ad still use it.
  • Landing zone is a preconfigured subscription pattern, not an AWS Control Tower account.
  • The Cloud Adoption Framework and Well-Architected Framework are the Azure design guides.

Find the right SKU names

bashDiscover
az aks get-versions --location westeurope -o table
az vm list-sizes --location westeurope --query "[?contains(name,'D4s_v5')].{name:name,cpu:numberOfCores,mem:memoryInMb}" -o table
2.8

Budgets, cost analysis and tags

In plain words

Cost Management shows spend by subscription, group, tag and service. A budget sends alerts, or triggers an action group, at set thresholds.

The problem it solves

Cloud bills surprise teams because nobody sees spend until the invoice.

What it does

  • AWS equivalent: Cost Explorer, AWS Budgets, cost allocation tags.
  • Main difference: Cost Management is built into every scope (management group, subscription, resource group). Budgets alert at actual or forecast thresholds. Cost data can lag by hours, and tag coverage depends on the resource type; check the current docs. Scheduled exports write CSV to storage for FinOps tooling.
  • Allocate shared AKS costs with namespace cost analysis, an AKS add-on; check its current status.
  • Stop dev clusters out of hours with az aks stop.

Budget and stop a dev cluster

bashBudget and AKS stop
az consumption budget create --budget-name shop-prod-monthly --category cost --amount 3000 --time-grain monthly \
  --start-date 2026-11-01 --end-date 2027-10-31 --resource-group rg-shop-prod 2>/dev/null || echo "check az consumption budget help for current parameters"
az aks stop -g rg-shop-dev -n aks-shop-dev
az aks start -g rg-shop-dev -n aks-shop-dev
Note

Budget CLI support changes. If the command fails, create the budget in the portal or with the Bicep resource Microsoft.Consumption/budgets.

Check yourself
Does a budget stop spending by itself?

No. It alerts or triggers an action you define.

Section 3 of 16

Entra ID identities, apps and managed identities

8 concepts · about 55 minutes

Everything in Azure starts with a token issued by Microsoft Entra ID. This page covers the identity types you will meet and when to pick each.

Goals
  • Choose between user, service principal, managed identity and federated credential
  • Create app registrations and service principals from the CLI
  • Remove stored secrets using managed identities and workload identity federation
3.1

Users and groups

In plain words

Users are people (or guests from other tenants). Groups bundle users, devices and other principals so you assign access once.

The problem it solves

Granting roles to individuals does not scale and leaves orphaned access when people move teams.

What it does

  • AWS equivalent: IAM Identity Center users and groups.
  • Main difference: Entra users are tenant-wide and authenticate to Azure, Microsoft 365 and your own apps with the same account. Always assign RBAC to groups, not users.
  • Security groups can be assigned roles; Microsoft 365 groups are for collaboration. Role-assignable groups need to be created as such.
  • Guests (B2B) are external users invited into your tenant.

Create a group and add a member

bashGroups
GID=$(az ad group create --display-name sg-shop-operators --mail-nickname sg-shop-operators --query id -o tsv)
az ad group member add --group "$GID" --member-id $(az ad user show --id alice@contoso.com --query id -o tsv)
az ad group member list --group "$GID" --query '[].userPrincipalName' -o tsv
3.2

App registrations and service principals

In plain words

An app registration is the definition of an application in your tenant. A service principal is its identity inside a tenant, the thing that receives roles.

The problem it solves

Pipelines and services need an identity that is not a person.

What it does

  • AWS equivalent: an IAM role or IAM user used by automation. A service principal is closest to a role with credentials.
