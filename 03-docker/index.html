Section 1 of 28

Containers versus virtual machines

6 concepts · about 45 minutes

A container is not a small virtual machine. It is an ordinary Linux process that the kernel has fenced in with namespaces, limited with cgroups and given its own root filesystem. Everything in Kubernetes pods, ECS tasks and CI runners builds on that idea.

Goals
  • Explain what a container really is on a Linux host and how it differs from a virtual machine
  • Describe the Docker client, daemon, containerd and runc roles at a high level
  • Run, list, stop and clean up containers with the right lifecycle commands
1.1

What a container really is

In plain words

A container is a normal process (or group of processes) started with a restricted view of the machine: its own process list, network, hostname and filesystem. It shares the host kernel with every other container.

The problem it solves

Applications break when the machine differs: a different Python version, a missing library, a conflicting port. Copying a whole operating system per application fixes that but is slow and heavy.

What it does

  • Packages the app together with its libraries and files, so "works on my machine" travels with it.
  • Starts in milliseconds to a second, because no operating system boots; only a process starts.
  • Costs megabytes instead of gigabytes, so one host runs dozens or hundreds.
  • Isolation is weaker than a VM, because the kernel is shared. A kernel bug can affect every container.

See it is just a process

bashA container is a host process
docker run -d --name demo nginx:1.27-alpine        # start a container in the background
docker top demo                                    # the processes as the host sees them
ps -ef | grep "nginx: master" | head -2            # on Linux the same PID is visible on the host
docker exec demo cat /proc/1/cgroup                # the cgroup that limits it
docker rm -f demo                                  # stop and delete
Note

On macOS and Windows, Docker Desktop runs a small Linux VM and your containers live inside it. The host-PID trick above only works on a Linux host or inside that VM.

Check yourself
Do containers have their own kernel?

No. They share the host kernel; only the view of processes, network and files is separate.

1.2

Containers versus virtual machines

In plain words

A virtual machine emulates hardware and runs a complete guest operating system with its own kernel. A container skips all that and uses the host kernel directly.

The problem it solves

Choosing wrongly costs money or security. VMs give strong isolation but boot slowly and waste memory on duplicate kernels. Containers are light but share a kernel.

What it does

  • VM: hypervisor (KVM, Nitro on AWS) plus guest kernel. Boot in tens of seconds, gigabytes per instance.
  • Container: namespaces and cgroups on one kernel. Start in under a second, megabytes per instance.
  • A container image must match the host kernel family: Linux containers need a Linux kernel, and the CPU architecture (amd64 or arm64) must match.
  • For hostile multi-tenant workloads, run containers inside VMs or use microVMs (Firecracker, Kata Containers).

1.3

Docker architecture

In plain words

Docker is several parts. The docker command is a client that talks over a socket to the Docker daemon (dockerd). The daemon builds images and delegates running containers to containerd, which uses runc to create them.

The problem it solves

When something fails, you need to know which layer to blame: the CLI, the daemon, the runtime or the kernel. Kubernetes itself skips dockerd and talks to containerd directly.

What it does

  • docker CLI: sends REST requests to /var/run/docker.sock.
  • dockerd: images, networks, volumes, the build engine (BuildKit).
  • containerd: pulls images, manages snapshots and container lifecycle.
  • runc: the small tool that sets up namespaces and cgroups, then starts your process.
Danger

Access to /var/run/docker.sock is equal to root on the host. Never mount it into an untrusted container, and treat membership of the docker group as root access.

Inspect the pieces

bashClient, server and runtime versions
docker version --format 'client={{.Client.Version}} server={{.Server.Version}}'
docker info --format 'runtime={{.DefaultRuntime}} storage={{.Driver}} cgroup={{.CgroupVersion}}'
ls -l /var/run/docker.sock
docker context ls          # which daemon the CLI is currently talking to
1.4

Container lifecycle

In plain words

A container moves through states: created, running, paused, exited, removed. Its writable data lives only as long as the container exists unless you store it in a volume.

The problem it solves

Engineers lose data by deleting a container that held it, or leave hundreds of stopped containers consuming disk.

What it does

  • docker run = create + start. Add -d for background, --rm to delete on exit, --name to name it.
  • docker stop sends SIGTERM, waits 10 seconds, then SIGKILL. Change the wait with -t.
  • docker ps -a includes exited containers; docker rm deletes them.
  • --restart unless-stopped makes the daemon restart the container after a crash or reboot.

Day one commands

bashLifecycle commands
docker run -d --name web -p 8080:80 --restart unless-stopped nginx:1.27-alpine
docker ps                                  # running only
docker logs --tail 5 web
docker stop -t 5 web                       # SIGTERM, then SIGKILL after 5 seconds
docker ps -a --filter status=exited
docker start web && docker rm -f web
docker container prune -f                  # delete all stopped containers
Check yourself
Why does docker stop sometimes take 10 seconds?

The app ignored SIGTERM (often because the shell is PID 1), so Docker waited the grace period and sent SIGKILL.

1.5

Running options you will use daily

In plain words

docker run has dozens of flags. A small set covers nearly everything: ports, environment, volumes, resource limits and the user.

The problem it solves

Defaults are unlimited: a container can use all host memory, run as root and listen on any port. Production use needs explicit limits.

What it does

  • -p host:container publishes a port. -p 127.0.0.1:8080:80 binds only to localhost.
  • -e KEY=value and --env-file set environment variables.
  • --memory 256m --cpus 0.5 set cgroup limits. Exceeding memory triggers the OOM killer (exit code 137).
  • --user 1000:1000 runs as a non-root user; --read-only makes the root filesystem read-only.

A realistic run

bashLimits and safety in one command
docker run -d --name api \
  -p 127.0.0.1:8000:8000 \
  -e LOG_LEVEL=info \
  --memory 256m --cpus 0.5 --pids-limit 200 \
  --user 1000:1000 --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  python:3.12-slim python -m http.server 8000
docker stats --no-stream api
docker rm -f api
Tip

Exit code 137 means SIGKILL (128 + 9), very often the OOM killer. Check with docker inspect -f '{{.State.OOMKilled}}' api.

1.6

Containers on AWS and Kubernetes

In plain words

The same container image runs on your laptop, in CI, on ECS or Fargate and in a Kubernetes pod. What differs is who starts it and how.

The problem it solves

Engineers often think of Docker as a development tool only, and then are surprised that production uses a different runtime and different defaults.

What it does

  • Kubernetes (EKS, Kyma) uses containerd or CRI-O through the CRI interface; there is no dockerd on the node.
  • A pod is one or more containers sharing a network namespace; the image is the same OCI image.
  • docker run flags map to pod spec fields: --memory to resources.limits.memory, --user to securityContext.runAsUser, -e to env.
  • ECS and Fargate use the same images with a task definition instead.

The mapping

yamldocker run flags as a pod spec
# docker run --memory 256m --cpus 0.5 --user 1000 --read-only -e LOG_LEVEL=info app:1.0
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
    - name: app
      image: app:1.0
      env:
        - {name: LOG_LEVEL, value: info}
      resources:
        limits: {memory: 256Mi, cpu: 500m}
      securityContext:
        runAsUser: 1000
        readOnlyRootFilesystem: true

Images and layers

6 concepts · about 45 minutes

An image is the template a container starts from. Understanding layers explains build speed, image size, pull time and why secrets leak into images.

Goals
  • Describe an image as a stack of read-only layers plus a manifest and config
  • Explain copy on write and why deleting a file in a later layer does not shrink an image
  • Inspect image history, sizes and digests and reduce image size
2.1

What an image is

In plain words

An image is a read-only bundle: a filesystem split into layers, plus a small JSON config that records the default command, environment variables, user and exposed ports.

The problem it solves

Shipping a filesystem as one huge archive wastes bandwidth. Most of a new version is identical to the previous one.

What it does

  • Each layer is a compressed tar of file changes. Layers are identified by a SHA-256 hash of their content.
  • The manifest lists the config and layers by digest; the config holds Entrypoint, Cmd, Env, User.
  • Layers are shared. Ten images based on the same python:3.12-slim store that base only once, and a registry transfers only layers it lacks.
  • A container adds one thin writable layer on top.

Look inside

bashInspect an image
docker pull python:3.12-slim
docker image inspect python:3.12-slim --format '{{.Id}} {{.Architecture}} {{.Os}}'
docker image inspect python:3.12-slim --format '{{json .RootFS.Layers}}' | python3 -m json.tool | head
docker image inspect python:3.12-slim --format '{{json .Config.Cmd}} {{json .Config.Env}}'
docker history python:3.12-slim     # one row per layer with its size
Check yourself
What stores the default command of an image?

The image config JSON (Cmd and Entrypoint), referenced by the manifest.

2.2

Copy on write and the union filesystem

In plain words

Layers are stacked so they look like one directory tree. When a container changes a file from a lower layer, the file is first copied up to the writable layer, then changed there.

The problem it solves

Without this, every container would need a full private copy of the image, and starting one would mean copying gigabytes.

What it does

  • The storage driver is overlay2 on modern Linux (OverlayFS: lowerdirs, upperdir, workdir and a merged view).
  • Deleting a file in a later layer only hides it with a "whiteout" marker; the bytes remain in the earlier layer and still count toward image size.
  • Heavy writes inside the container layer are slower than writes to a volume.
Careful

COPY secrets.txt / followed by RUN rm /secrets.txt leaves the secret in the earlier layer, and anyone who pulls the image can extract it. Use build secrets (covered in the Dockerfile files) instead.

Prove it with a lab

bashWhiteouts keep the bytes
mkdir -p /tmp/wo && cd /tmp/wo
printf 'FROM alpine:3.20\nRUN dd if=/dev/zero of=/big bs=1M count=50\nRUN rm /big\n' > Dockerfile
docker build -q -t whiteout-demo .
docker history whiteout-demo     # the 50MB layer is still listed
docker rmi whiteout-demo
2.3

Content addressable storage

In plain words

Everything in an image is named by the hash of its content. Change one byte and the name changes.

The problem it solves

Tags like latest can move; you need a way to prove two machines run exactly the same bytes.

What it does

  • A digest looks like sha256:3f5a... and identifies a manifest or layer.
  • The same content always gets the same digest, which allows deduplication and verification on pull.
  • A multi-architecture image has an index (manifest list) pointing to one manifest per platform.
  • repo@sha256:... references an image immutably; repo:tag can be repointed.

Read the real manifest

bashDigests and platforms
docker buildx imagetools inspect python:3.12-slim | head -20
docker image ls --digests python
docker manifest inspect nginx:1.27-alpine 2>/dev/null | head -20
2.4

Image size and why it matters

In plain words

Size drives pull time, cold start on a new Kubernetes node, registry cost and attack surface. A 1.2 GB image takes much longer to start on a fresh node than a 60 MB one.

The problem it solves

Images grow because build tools, package caches and source trees end up in the final layers.

What it does

  • Choose a smaller base: alpine (about 8 MB, musl libc), *-slim Debian (about 50 MB), or distroless.
  • Combine install and cleanup in one RUN so the cache is never committed to a layer.
  • Use multi-stage builds so compilers stay in the build stage.
  • Add a .dockerignore so .git, node_modules and local files are not sent or copied.

Measuring

bashCompare sizes
docker pull -q python:3.12 python:3.12-slim python:3.12-alpine 2>/dev/null || true
docker image ls --format 'table {{.Repository}}:{{.Tag}}\t{{.Size}}' | grep -E 'python|REPOSITORY'
docker system df                       # images, containers, volumes, build cache
docker image prune -a --filter "until=168h" -f   # remove unused images older than 7 days
Tip

Alpine uses musl libc. Python wheels and some native Node modules expect glibc and may need compiling, which can make Alpine builds slower and larger. Prefer -slim for Python unless you have tested Alpine.

2.5

Tags, names and references

In plain words

An image reference has the form registry/namespace/repository:tag@digest. Missing parts get defaults: Docker Hub, the library namespace and the latest tag.

The problem it solves

FROM python or image: app:latest resolves differently over time and across machines, making builds and rollbacks unpredictable.

What it does

  • nginx means docker.io/library/nginx:latest.
  • A tag is a mutable pointer. Several tags can point to one digest.
  • Pin both for reproducibility: python:3.12.7-slim@sha256:....
  • docker tag src dst adds a name; it does not copy data.

Practice

bashTagging and pinning
docker pull alpine:3.20
docker tag alpine:3.20 myorg/tools:v1
docker image ls myorg/tools
docker image inspect alpine:3.20 --format '{{index .RepoDigests 0}}'   # the pinnable reference
docker rmi myorg/tools:v1
Check yourself
Why is latest a poor production tag?

It moves whenever someone pushes, so two deployments of the same name may run different code and rollbacks are not reproducible.

2.6

Saving, loading and cleaning images

In plain words

Images can be moved without a registry as a tar file, and disk can fill quickly with unused layers and build cache.

The problem it solves

Air-gapped environments need offline transfer, and CI runners and laptops regularly run out of disk space.

What it does

  • docker save -o app.tar app:1.0 and docker load -i app.tar move images between hosts.

Namespaces, cgroups and container isolation

6 concepts · about 40 minutes

Docker did not invent containers. It packaged two Linux kernel features, namespaces and cgroups, behind a friendly tool. Knowing them explains OOM kills, CPU throttling and why a container sees only its own processes.

Goals
  • Name the Linux namespaces that give a container its own view of the system
  • Explain how cgroups limit CPU, memory and process count
  • Reproduce container isolation by hand with unshare and read cgroup limits
3.1

Namespaces

In plain words

A namespace wraps a global system resource so a process sees its own private copy. Processes in the same namespace see each other; others do not.

The problem it solves

Without namespaces every process sees every other process, every network interface and the whole filesystem, so two apps could not both listen on port 80.

What it does

  • pid: own process tree; your app is PID 1.
  • net: own interfaces, routes, iptables and ports.
  • mnt: own mount table, so a different root filesystem.
  • uts (hostname), ipc (shared memory), user (UID mapping), cgroup and time complete the set.

List a container's namespaces

bashNamespaces of a process

sudo ls -l /proc/$PID/ns                           # one symlink per namespace
lsns -p $PID 2>/dev/null | head
docker rm -f ns
Check yourself
Which namespace lets two containers both listen on port 8080?

The network namespace, because each has its own port space.

3.2

Building a container by hand

In plain words

You can create a mini container with one command: unshare starts a program inside new namespaces. A container runtime does this plus a root filesystem and cgroups.

The problem it solves

Containers feel like magic until you see that the core is a few system calls: clone, unshare, setns and pivot_root.

What it does

  • unshare --pid --fork --mount-proc gives a new PID namespace.
  • chroot or pivot_root swaps the root directory to an image's files.
  • A runtime then applies cgroups, drops capabilities and applies seccomp.

Try it

bashA container without Docker

  hostname isolated
  echo "hostname is $(hostname)"
  ps -ef            # only this shell and ps are visible
  ip link           # only a loopback that is down
'
Note

Needs a Linux host and root. On macOS use a Linux VM such as Colima or Multipass.

3.3

Control groups (cgroups)

In plain words

A cgroup is a kernel group of processes with limits and accounting. Namespaces control what a process can see; cgroups control how much it can use.

The problem it solves

One runaway container could consume all memory or CPU and starve the others, or fill the process table with a fork bomb.

What it does

  • Modern kernels use cgroup v2, one tree under /sys/fs/cgroup.
  • Files such as memory.max, cpu.max, pids.max hold the limits; memory.current and cpu.stat give usage.
  • Docker flags map directly: --memory, --cpus, --pids-limit. Kubernetes resources.limits do the same.

Read the limits

docker rm -f lim
Check yourself
What do the two numbers in cpu.max 50000 100000 mean?

A quota of 50 ms of CPU time per 100 ms period, which equals 0.5 CPU.

3.4

Memory limits and the OOM killer

In plain words

When a container uses more memory than its limit, the kernel kills a process in it. The exit code is 137 and the container is marked OOMKilled.

The problem it solves

Applications that run fine unlimited suddenly restart in production. The cause is usually a limit set too low or a leak, not a Docker fault.

What it does

  • The limit covers heap, stacks, page cache of the container's files and kernel memory it causes.
  • JVMs and Node need tuning: Java reads the cgroup limit; Node needs --max-old-space-size below the limit.
  • In Kubernetes OOMKilled appears in kubectl describe pod, with exit code 137.

Reproduce

3.5

CPU limits and throttling

In plain words

CPU limits do not kill; they pause. A container with --cpus 0.5 may run only 50 ms in each 100 ms window, then waits.

The problem it solves

Latency spikes appear in services that are not using much CPU on average, because bursts hit the quota and the process is frozen until the next period.

What it does

  • --cpus sets a hard quota (cpu.max). --cpu-shares is only a relative weight under contention.
  • cpu.stat fields nr_throttled and throttled_usec show throttling directly.
  • Many teams set CPU requests but omit CPU limits in Kubernetes to avoid throttling; memory limits are always kept.

3.6

Linux features that harden containers

In plain words

Beyond namespaces and cgroups, three features cut what a contained process can do: capabilities, seccomp and LSM profiles (AppArmor or SELinux).

The problem it solves

Root inside a container is still the kernel's idea of root unless restricted. A shared kernel means every allowed syscall is attack surface.

What it does

  • Capabilities split root into about 40 pieces. Docker drops most by default and keeps 14.
  • seccomp filters system calls; Docker's default profile blocks around 44 of over 300 calls.
  • AppArmor/SELinux add mandatory access control rules.
  • no_new_privs prevents setuid programs from gaining privileges.

4.1

Anatomy of a Dockerfile

In plain words

A Dockerfile is a text file of instructions run top to bottom by the builder. The first must be FROM, which names the starting image.

  • COPY brings files from the build context. RUN executes a command at build time.
  • ENV sets variables; ARG is build-time only. EXPOSE documents a port; it does not publish it.
  • CMD or ENTRYPOINT defines what runs at container start.

In plain words

The problem it solves

Without control, node_modules, .git, .env files and test data are uploaded and may be copied into the image, slowing builds and leaking secrets.

Each RUN creates a layer. Splitting install and cleanup into separate layers keeps the junk in the image forever.

  • Override the entrypoint with docker run --entrypoint sh img for debugging.
  • Kubernetes names differ: command replaces ENTRYPOINT, args replaces CMD.

  • Do not run npm start as PID 1; call node directly because npm does not forward signals reliably.

Build cache and multi-stage builds

6 concepts · about 45 minutes

A build that takes ten minutes on every commit wastes a team's day. The cache and multi-stage builds turn it into seconds and shrink the shipped image.

Goals
  • Order Dockerfile instructions so the layer cache is reused
  • Split build and runtime into stages to ship small images
  • Use BuildKit features such as cache mounts and secret mounts
5.1

How the layer cache works

In plain words

For each instruction BuildKit checks whether it already built the same instruction on the same parent layer with the same inputs. If yes, it reuses the result; if not, that step and every step after it run again.

The problem it solves

Reinstalling all dependencies after changing one line of source code is slow and wasteful.

What it does

  • For RUN the cache key is the command text and parent layer. For COPY it is the checksum of the copied files.
  • A change in one layer invalidates all layers below it in the file.
  • So put things that change rarely (OS packages, dependency manifests) first and source code last.
  • ARG values and changed files used by an instruction also invalidate it.

Bad order versus good order

dockerfileSlow order, reinstalls on every edit
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
dockerfileFast order, dependencies cached
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
Check yourself
Why copy requirements.txt before the rest of the code?

Its checksum rarely changes, so the pip install layer stays cached when only source files change.

5.2

Multi-stage builds

In plain words

A Dockerfile can have several FROM lines. Each starts a new stage. The final image contains only the last stage, and you copy chosen files into it from earlier stages.

The problem it solves

Compilers, dev dependencies and test tools are needed to build but are dead weight and attack surface at runtime.

What it does

  • FROM node:22 AS build names a stage; COPY --from=build /app/dist ./dist pulls artifacts.
  • docker build --target build . stops at a stage, useful for running tests.
  • Stages that are not needed by the target are skipped by BuildKit, and independent stages build in parallel.
  • Typical result: a Go or Java service drops from over 800 MB to under 100 MB.

Node example, complete

dockerfileDockerfile (Node, TypeScript)
# syntax=docker/dockerfile:1
FROM node:22-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM deps AS build
COPY . .
RUN npm run build && npm prune --omit=dev

FROM node:22-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

In plain words

What it does

  • Create /opt/venv in the builder and put it first in PATH.

Volumes, bind mounts and tmpfs

6 concepts · about 40 minutes

Goals

7.1

Why containers lose data

In plain words

The writable layer belongs to one container. Remove the container and the layer is deleted with it.

The problem it solves

Teams run a database in a container, recreate it for an upgrade, and find the tables empty.

What it does

  • Data written without a mount stays in the container layer under /var/lib/docker/overlay2.
  • docker rm and docker compose down delete that layer. Named volumes survive unless you add -v to down.
  • Writes to the layer also go through overlayfs, which is slower than a volume.
  • Rule: the image is immutable code, the volume is state.

Prove it

In plain words

The problem it solves

You need durable storage that does not depend on a host path layout and that you can share between containers.

What it does

  • An empty volume is populated from the image's files at that path on first use.
  • docker volume ls, inspect (shows Mountpoint), rm, prune.
  • Drivers allow NFS, EFS or cloud disks through plugins or local driver options.

Container networking basics

6 concepts · about 45 minutes

  • Use user defined networks and built-in DNS so containers find each other by name

8.1

Network drivers

In plain words

A Docker network is a driver plus settings. The common drivers are bridge (single host), host, none, overlay (multi host) and macvlan.

The problem it solves

You need to decide how isolated a container is, and how it reaches the world and its neighbours.

What it does

  • bridge: private subnet behind NAT; the default.
  • host: container shares the host network stack; no isolation, no port mapping needed.
  • none: only loopback.
  • overlay: VXLAN across hosts (Swarm). macvlan: container gets its own MAC and LAN address.

List and inspect

bashDefault networks
docker network ls
docker network inspect bridge --format '{{range .IPAM.Config}}{{.Subnet}} {{end}}'
docker run --rm --network host alpine:3.20 ip -br addr | head -3

8.2

The default bridge and veth pairs

In plain words

Docker creates a Linux bridge (docker0). Each container gets a virtual cable (veth pair): one end inside as eth0, the other plugged into the bridge.

The problem it solves

Packets between container and outside need a path. Knowing it lets you use tcpdump and iptables to find where they die.

What it does

  • Containers on one bridge talk by IP directly at layer 2.
  • Outbound traffic is source-NATed (masqueraded) to the host IP.
  • Inbound published ports use DNAT rules in the DOCKER iptables chain.
  • The default bridge network has no name resolution; user-defined bridges do.

Look at the plumbing

bashOn a Linux host
ip -br link show type bridge
ip -br link | grep veth | head
sudo iptables -t nat -S DOCKER | head      # DNAT rules for published ports
sudo iptables -t nat -S POSTROUTING | grep -i masq
8.3

Publishing ports

In plain words

-p 8080:80 asks Docker to forward host port 8080 to container port 80. Without it nothing outside the host can reach the container.

The problem it solves

EXPOSE in a Dockerfile is only documentation. People expect it to open the port and it does not.

What it does

  • -p 8080:80 binds all interfaces. -p 127.0.0.1:8080:80 limits to localhost.
  • -P publishes all EXPOSEd ports to random high ports.
  • Published ports bypass ufw and firewalld rules on Linux because Docker edits iptables directly; bind to 127.0.0.1 or add rules in the DOCKER-USER chain.
  • Within one user-defined network containers reach each other on the container port, no publishing needed.

Try it

bashPublish and verify

Danger

-p 5432:5432 for a database exposes it to every network the host sits on, bypassing the host firewall. Use 127.0.0.1:5432:5432 or no publishing at all.

In plain words

On a network you create yourself, Docker runs an embedded DNS server at 127.0.0.11. Containers resolve each other by container name or service alias.

The problem it solves

Container IPs change on every restart, so hardcoding them breaks. The default bridge offers no names.

What it does

  • docker network create app-net, then --network app-net for each container.
  • Name lookup of db returns the container IP; multiple containers with the same --network-alias are returned round-robin.
  • Different networks are isolated: a container in frontend cannot reach one only in backend.
  • Unknown names are forwarded to the host's DNS servers.

Registries, tags and digests

6 concepts · about 45 minutes

A registry is where CI puts images and where clusters pull them from. Tag discipline and registry hygiene decide whether you can answer the question "exactly what is running in production".

11.1

How a registry works

In plain words

A registry is an HTTP server that stores image manifests and layer blobs, addressed by repository name and by digest. Docker Hub, ECR, GHCR, Harbor and Quay all speak the same OCI Distribution API.

The problem it solves

Machines that build an image are rarely the machines that run it. You need a shared, access controlled store that transfers only missing layers.

What it does

  • docker push uploads each missing layer blob (/v2/<repo>/blobs/uploads/), then the manifest (/v2/<repo>/manifests/<tag>).
  • docker pull fetches the manifest, then only layers not already cached locally.
  • Authentication is a token flow: a 401 response names the auth realm, the client gets a bearer token and retries.
  • Layer blobs are deduplicated by digest within a registry.

Tags are mutable, digests are not

In plain words

A tag is a label that a push can move to different content. A digest is the SHA-256 of the manifest, so it names exactly one set of bytes.

The problem it solves

If production uses shop-api:1.4 and someone re-pushes that tag, pods created after the push run different code than pods created before, with no change in Git.

What it does

  • Tags are good for humans and promotion (1.4.2, main, prod).
  • Digests are good for deploys: shop-api@sha256:ab12... cannot change.
  • Immutable tags (an ECR and GHCR option) make re-pushing an existing tag fail.
  • In Kubernetes, image: repo:tag@sha256:... uses the digest and shows the tag for humans.

Check yourself
Why deploy by digest even when you also keep a version tag?

What it does

In plain words

14.1

The three OCI specifications

In plain words

The OCI publishes three specifications: the Image spec (what an image is), the Runtime spec (how to run a container from a filesystem bundle) and the Distribution spec (how registries serve images).

The problem it solves

In 2014 only Docker's own formats existed. Orchestrators and registries needed neutral standards so no single vendor controlled how containers are packaged and run.

What it does

  • Image spec: index, manifest, config JSON, layers as tar archives, all addressed by digest.
  • Runtime spec: a config.json plus a root filesystem directory (a bundle); implemented by runc, crun, youki, runsc (gVisor), kata-runtime.
  • Distribution spec: the /v2/ HTTP API for push and pull.
  • Docker image format v2 is nearly identical and still widely served alongside OCI media types.

Anatomy of an image on disk

In plain words

An OCI layout is a folder with an index.json, an oci-layout marker and a blobs/sha256/ directory. Every file in blobs/ is named by the SHA-256 of its contents.

The problem it solves

"Images are magic archives" blocks debugging. Once you see that an image is JSON files and tarballs, you can verify, diff or repair them with ordinary tools.

What it does

  • index.json points to a manifest digest (or to a multi-platform index).
  • The manifest lists the config blob and ordered layer blobs, each with mediaType, digest and size.
  • The config holds architecture, os, config.Cmd/Env/User, rootfs.diff_ids and the build history.
  • Layers are tar (optionally gzip or zstd) with whiteout files .wh.<name> for deletions.

Walk the tree with jq

bashFrom index to files

MANIFEST=$(jq -r '.manifests[0].digest' index.json | cut -d: -f2)
jq '.config.digest, (.layers[] | .digest, .size)' blobs/sha256/$MANIFEST
LAYER=$(jq -r '.layers[0].digest' blobs/sha256/$MANIFEST | cut -d: -f2)
tar -tzf blobs/sha256/$LAYER | head -8          # the files that layer adds
CONFIG=$(jq -r '.config.digest' blobs/sha256/$MANIFEST | cut -d: -f2)
jq '.config.Cmd, .architecture, .rootfs' blobs/sha256/$CONFIG
Check yourself
What is the difference between a layer digest and a diff_id?

The digest is the hash of the compressed blob as stored; the diff_id is the hash of the uncompressed tar, used to identify content independent of compression.

In plain words

What it does

  • containerd-shim-runc-v2 stays alive as the container's parent, so containerd can restart without killing containers.
  • runc creates namespaces, cgroups, mounts, drops capabilities, then execs your process and exits.
  • Dockershim was removed from Kubernetes in 1.24; Docker built images still run unchanged.

In plain words

When a container stops, its exit code says why. Codes above 128 mean the process was killed by signal number code minus 128.

BuildKit and CI build caching

6 concepts · about 45 minutes

On a laptop the Docker cache just works. On a fresh CI runner every build starts cold, so a two minute local build can take ten minutes in the pipeline. The fix is to move the cache somewhere that outlives the runner.

Goals
  • Explain how BuildKit schedules builds as a graph and why that is faster than the legacy builder
  • Persist build cache across CI runs with registry, GitHub Actions and S3 cache backends
  • Measure and reduce build time with context trimming, ordering and parallel stages
18.1

BuildKit

In plain words

BuildKit is the build engine behind docker build and docker buildx build. It turns a Dockerfile into a dependency graph and runs independent steps in parallel.

The problem it solves

The legacy builder executed instructions one after another, sent the whole context every time and could not share cache between machines.

What it does

  • Skips stages the target does not need and builds independent stages concurrently.
  • Sends only the files that COPY actually reads, instead of the whole context.
  • Offers RUN --mount for cache, secret and SSH, and exports cache to external storage.
  • Default since Docker 23; on older engines set DOCKER_BUILDKIT=1.
  • Plain progress output for CI logs: --progress=plain.

18.2

Why CI builds are slow

In plain words

A CI runner is usually a fresh virtual machine. It has no layers, no pip or npm cache, and no previous build to compare with, so every step runs.

The problem it solves

Pull request feedback takes ten minutes when it should take two, developers batch their changes, and the runner minutes bill grows.

What it does

  • Cold layer cache: every RUN re-executes, every base image is pulled.
  • Cold package caches: all dependencies download again.
  • Large build contexts: uploading .git or node_modules.
  • Serial pipelines: build, test and scan run one after another.
  • Fixes: external cache backend, cache mounts, small context, parallel jobs, a pull through registry mirror.

Cache backends

In plain words

--cache-to exports the build cache and --cache-from imports it. The backend decides where the cache lives.

The problem it solves

Without export, the cache is destroyed with the runner. You need storage reachable from every runner.

What it does

  • type=registry: cache stored as an image in a registry (for example :buildcache tag). Works anywhere; use mode=max to include intermediate layers.
  • type=gha: GitHub Actions cache service; no extra infrastructure, 10 GB per repository limit.
  • type=s3: S3 bucket, good for self-hosted runners on AWS.
  • type=local: directory, pairs with actions/cache or a CI cache volume.
  • type=inline: embeds cache in the pushed image; simple but only caches the final stage.

6 concepts · about 40 minutes

Why multi-arch

In plain words

CPU architectures run different machine code. An amd64 binary cannot run on an arm64 node. A multi-arch image bundles one variant per platform behind a single tag.

The problem it solves

Images built on an M-series Mac and deployed to amd64 EKS nodes crash with exec format error, and teams that run Graviton nodes for cost savings need arm64 images.

  • containerd picks the manifest that matches the node when pulling; the user sees one tag.
  • Common platforms: linux/amd64, linux/arm64, sometimes linux/arm/v7.
  • Graviton instances typically cost about 20 percent less than comparable x86 instances for the same work; verify for your workload and region.

Three ways to build for another architecture

In plain words

You can emulate the other CPU, cross compile on your own CPU, or build natively on a machine of each architecture.

The problem it solves

  • Native builders: separate arm64 and amd64 runners, each build pushes by digest and a final job merges them into an index. GitHub offers arm64 hosted runners.
  • Interpreted languages (pure Python or Node without native modules) are architecture independent in your code but their dependencies may include compiled wheels.

Rootless containers and user namespaces

6 concepts · about 50 minutes

Root inside a container is not meant to be root on the host. User namespaces make that true by remapping user IDs, which limits the damage of an escape.

Goals
  • Explain how user namespaces map container root to an unprivileged host user
  • Run Docker and Podman rootless and know their limits
  • Use user namespaces for Kubernetes Pods
22.1

User namespaces

In plain words

A user namespace gives a process its own view of user and group IDs. UID 0 inside can map to an ordinary UID outside.

The problem it solves

Without remapping, container root is host root with fewer capabilities, so any escape bug yields full control.

What it does

  • A mapping line has three numbers: inside ID, outside ID, length. 0 100000 65536 maps inside 0 to outside 100000, up to 65536 IDs.
  • Files owned by inside UID 0 appear as outside UID 100000 on disk.
  • Capabilities granted inside the namespace apply only to resources owned by that namespace, not to the host.
  • Mappings come from /etc/subuid and /etc/subgid for rootless tools.

See it

bashInspect a user namespace
unshare --user --map-root-user sh -c 'id; cat /proc/self/uid_map'
grep "$USER" /etc/subuid /etc/subgid
podman unshare cat /proc/self/uid_map
Check yourself
What does the mapping 0 100000 65536 mean?

Inside IDs 0 to 65535 correspond to outside IDs 100000 to 165535.

In plain words

Rootless means the container engine itself runs as a normal user. Rootful engines have a root daemon but can still run non-root containers.

The problem it solves

A compromise of a root daemon or a socket mounted into a container is a compromise of the host.

What it does

  • Rootless: daemon and containers belong to your user; storage under ~/.local/share; no host root needed to install (after one-time setup of subuid).
  • Rootful with userns-remap: dockerd setting "userns-remap": "default" maps container root to a subordinate range.
  • Do not confuse with USER app in the image: that is non-root inside a container which may still map to host root in rootful mode.
  • Best combination: non-root user in the image and a rootless or remapped runtime.

Limits and workarounds

In plain words

Rootless mode cannot do everything root can. Knowing the limits avoids surprises.

The problem it solves

Teams enable rootless and then find ports, networking or volumes behaving differently.

What it does

  • Ports below 1024 need sysctl net.ipv4.ip_unprivileged_port_start=80 or a proxy.
  • Networking uses slirp4netns or pasta in user space, so throughput is lower and source IPs may be masked. Newer setups use pasta, which is faster; check your version.
  • No --privileged in the traditional sense; cgroup v2 delegation is needed for resource limits (systemd user sessions).
  • Overlay storage requires kernel support for rootless overlayfs (kernel 5.11+) or fuse-overlayfs.
  • Bind-mount ownership: files appear owned by a high UID; use --userns=keep-id (Podman) to map your user.

The bridge network and NAT

In plain words

Docker's default bridge connects containers on a private subnet. iptables NAT rules translate their addresses when they talk outward and forward published ports in.

The problem it solves

Private addresses are not routable outside, and a client outside must still reach published container ports.

What it does

  • Outbound: MASQUERADE rule in the nat table POSTROUTING chain rewrites the source to the host address.
  • Inbound -p 8080:80: a DNAT rule in the DOCKER chain rewrites destination host:8080 to container:80.
  • A userland proxy (docker-proxy) may also listen for local traffic unless disabled.
  • Docker inserts rules in the DOCKER-USER chain hook: put your own filtering there, since Docker rewrites its own chains.
  • Newer Docker releases are adding nftables support; check your version's docs.

Section 26 of 28

Container security case studies and escape techniques

9 concepts · about 65 minutes

Containers are isolated by the shared kernel plus configuration, not by a hypervisor. Almost every real escape starts with a dangerous setting or a kernel or runtime bug. This page describes the techniques at a conceptual level so you can recognise and prevent them. Test only in your own lab.

Goals
  • Explain the main container escape paths and the misconfigurations behind them
  • Map each technique to concrete mitigations
  • Review a runtime configuration with an attacker's checklist
26.1

The threat model

In plain words

A container shares the host kernel. Isolation comes from namespaces, cgroups, capabilities, seccomp, LSMs and the runtime. An attacker in a container tries to cross one of these boundaries.

The problem it solves

Teams assume "it is in a container, so it is safe" and then grant extra rights for convenience.

What it does

  • Attack surfaces: kernel (syscalls), runtime (runc, containerd), configuration (privileged, mounts, capabilities), orchestration (API, service account tokens), and the supply chain.
  • Layers of defence: non-root user, dropped capabilities, seccomp, AppArmor or SELinux, read-only filesystem, user namespaces, sandboxed runtimes (gVisor, Kata) for hostile code.
  • Assume breach: limit what a compromised container can reach.
Check yourself
Why is a container weaker than a VM as a security boundary?

It shares the host kernel, so a kernel or runtime flaw can cross the boundary.

26.2

Case 1, privileged containers

In plain words

--privileged (or privileged: true in Kubernetes) removes most isolation: all capabilities, all devices, no seccomp, no AppArmor.

The problem it solves

It is used to make something work quickly (Docker-in-Docker, mounting disks), and then stays.

What it does

  • Technique (conceptual): with all devices visible, the container can mount the host's disk device or write to the host's kernel interfaces, giving access to the host filesystem.
  • Mitigation: never allow privileged in application namespaces. Enforce Pod Security baseline or restricted. Use admission policy to deny privileged, hostPID, hostNetwork.
  • Alternatives: add only the one capability needed, use rootless BuildKit or Kaniko instead of Docker-in-Docker, use device plugins for devices.

26.3

Case 2, the Docker socket

In plain words

Mounting /var/run/docker.sock into a container hands that container control of the Docker daemon, which runs as root on the host.

The problem it solves

CI jobs and tools (monitoring, build agents) mount the socket to run or inspect containers.

What it does

  • Technique (conceptual): whoever can talk to the daemon can start a new container with the host filesystem mounted, which is equivalent to root on the host.
  • Same risk applies to the containerd socket and Podman's socket.
  • Mitigation: do not mount the socket; use rootless builders, a socket proxy that allows read-only endpoints, or remote build services. In Kubernetes block hostPath of /var/run with policy.
  • If unavoidable, isolate such workloads on dedicated, disposable nodes.

Why is access to the Docker socket equal to root on the host?

The daemon runs as root and can create containers that mount the host filesystem.

Case 3, dangerous capabilities and host mounts

In plain words

Individual capabilities such as SYS_ADMIN, SYS_PTRACE, NET_ADMIN, DAC_READ_SEARCH and SYS_MODULE enable specific attacks. Mounts of host paths expose host data.

The problem it solves

Granting one capability "just for the app" can be nearly as bad as privileged.

What it does

  • SYS_ADMIN allows mounting and many namespace operations; combined with weak seccomp it has led to escapes.
  • SYS_PTRACE with hostPID allows inspecting host processes; SYS_MODULE allows loading kernel modules; DAC_READ_SEARCH was used in the "shocker" file-handle technique to read host files.
  • Host mounts: /, /etc, /proc, /sys, /var/lib/kubelet, /var/lib/docker expose secrets and runtime state; writable hostPath allows persistence.
  • Mitigation: cap_drop: ALL and add back only what is proven needed; deny hostPath except for approved paths and read-only; keep default seccomp.

In plain words

The runtime that sets up containers (runc, containerd) is code running as root. Bugs there can let a malicious image or container overwrite host files.

The problem it solves

You cannot fix these with configuration alone; they need patching.

What it does

  • Notable history: CVE-2019-5736 (container could overwrite the host runc binary through /proc/self/exe), and CVE-2024-21626 "Leaky Vessels" (a leaked file descriptor allowed access to the host filesystem through a crafted working directory). Several 2025 runc advisories concerned mount handling. Read the current advisories for exact versions.
  • Mitigation: patch runc, containerd and the kernel promptly (node image rotation), run images from trusted sources, use user namespaces and sandboxed runtimes for untrusted workloads.
  • Track: subscribe to vendor security feeds (Gardener, EKS AMI release notes, Bottlerocket).

In plain words

Because the kernel is shared, a kernel bug reachable from a container can break out of it. Some classic escapes abuse cgroup v1 release agents when the container is privileged.

A single unpatched kernel affects every container on the node.

What it does

  • Examples: Dirty COW (2016), Dirty Pipe (CVE-2022-0847), and cgroup v1 release_agent abuse (CVE-2022-0492 required missing checks combined with certain capabilities).
  • Mitigation: keep nodes patched, use seccomp default (blocks risky syscalls), AppArmor/SELinux, cgroup v2, user namespaces, and a minimal host OS.
  • For hostile code (multi-tenant platforms, CI for untrusted pull requests) use gVisor, Kata Containers or Firecracker microVMs, which put another kernel boundary in place.

Scenario 1, container exits immediately

In plain words

Scenario 3, port already allocated or unreachable

In plain words

docker run -p 8080:80 fails with "port is already allocated", or the port is published but nothing answers.

The problem it solves

Two layers use ports: the host and the container, and the app may listen on the wrong interface.

What it does

  • Symptom A: Bind for 0.0.0.0:8080 failed: port is already allocated - another container or process uses it. Confirm with lsof -i :8080 or docker ps.
  • Symptom B: connection reset or empty reply - the app listens on 127.0.0.1 inside the container. It must bind 0.0.0.0.
  • Symptom C: published port works locally but not from other machines - host firewall or binding to 127.0.0.1:8080:80.
  • Fix: choose another host port, bind the app to all interfaces, adjust firewall.

Commands

bashPort checks
lsof -nP -iTCP:8080 -sTCP:LISTEN
docker port web
docker exec web ss -tlnp
curl -v http://localhost:8080/
Check yourself
Why can an app listening on 127.0.0.1 inside a container be unreachable?

Published ports forward to the container's own IP, not its loopback, so the app must listen on 0.0.0.0.

Scenario 4, DNS and name resolution inside containers

In plain words

Containers cannot resolve external names, or cannot resolve other containers by name.

The problem it solves

Behaviour differs between the default bridge, user-defined networks, VPNs and corporate resolvers.

What it does

  • Symptom: Temporary failure in name resolution, could not resolve host.
  • Confirm: docker exec c cat /etc/resolv.conf; nslookup name inside; test the host resolver; on user-defined networks the embedded DNS is 127.0.0.11.
  • Causes: host DNS is 127.0.0.53 (systemd-resolved), VPN changes resolvers, container on the default bridge using names, corporate DNS blocks.
  • Fix: set "dns": ["10.0.0.2"] in /etc/docker/daemon.json or --dns, use a user-defined network for name resolution, restart Docker after VPN changes.

Commands

bashDNS checks
docker exec web cat /etc/resolv.conf
docker run --rm busybox nslookup example.com
docker network inspect bridge --format '{{.Options}}'
docker run --rm --dns 1.1.1.1 busybox nslookup example.com
27.5

Scenario 5, permission denied on volumes

In plain words

The app cannot write to a mounted directory: permission denied, even though it works without the mount.

The problem it solves

Numeric user IDs inside the container do not match the file owner on the host or volume.

What it does

  • Symptom: EACCES, permission denied on bind mounts or new volumes; SELinux hosts show Permission denied despite correct ownership.
  • Confirm: docker exec c id, ls -ln on the mount path from inside, host ls -ln.
  • Fix: run with --user $(id -u):$(id -g), chown the host path to the container UID, in Dockerfile create the directory with the right owner before VOLUME; on SELinux add :z or :Z to the mount; rootless Podman uses --userns=keep-id.
  • Named volumes copy image ownership on first use; bind mounts never do.

Commands

bashOwnership checks
docker exec web id
docker exec web ls -ln /data
ls -ln ./data
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD/data:/data" alpine touch /data/ok
Check yourself
Which mount type copies image ownership into a new volume?

Named volumes do on first use when empty. Bind mounts keep the host's ownership.

27.6

Scenario 6, disk full and image bloat

In plain words

Builds or pulls fail with no space left on device, or the Docker data directory grows without bound.

The problem it solves

Old images, stopped containers, build cache and large container logs accumulate.

What it does

  • Symptom: no space left on device, slow builds, /var/lib/docker large.
  • Confirm: docker system df -v, du -sh /var/lib/docker/*, docker ps -s for container layers, and large JSON logs in /var/lib/docker/containers/*/*-json.log.
  • Fix: docker system prune, docker builder prune --keep-storage 10GB, docker image prune -a --filter until=168h; set log rotation (max-size, max-file) in daemon.json or use another log driver.
  • Careful: docker volume prune deletes unused volumes including data.

Commands

bashFree space safely
docker system df
docker builder prune --keep-storage 10GB -f
docker image prune -a --filter "until=168h" -f
cat /etc/docker/daemon.json
jsonLog rotation in daemon.json
{
  "log-driver": "json-file",
  "log-opts": {"max-size": "10m", "max-file": "3"}
}
Careful

27.7

Scenario 7, build fails with cache or context problems

In plain words

Builds are slow because the context is huge, or they pick up stale layers, or fail with file not found for a COPY.

The problem it solves

The build context (the directory sent to the builder) differs from what you expect.

What it does

  • Symptom: "Sending build context" of hundreds of MB; COPY failed: file not found in build context.
  • Confirm: size of the context (du -sh .), .dockerignore content, relative paths (COPY paths are relative to the context, not the Dockerfile) and -f usage.
  • Fix: add .dockerignore (node_modules, .git, build outputs), run the build from the right directory, use --no-cache only to diagnose stale layers, and docker build --progress=plain to see each step.
  • Remember that a base image tag like latest may have changed; pin it.

Commands

bashDiagnose a build

docker build --no-cache --pull -t app:fresh .
docker buildx du | head
Check yourself
Relative to what are COPY source paths resolved?

The build context directory, not the location of the Dockerfile.

Scenario 8, cannot pull or push images

In plain words

docker pull or docker push fails with unauthorized, denied, manifest unknown or TLS errors.

The problem it solves

Credentials, repository names, tags, certificates and platform architectures all matter.

What it does

  • unauthorized or denied: run docker login REGISTRY; check that the credential helper holds a current token (ECR tokens expire after 12 hours); confirm repository permissions.
  • manifest unknown: tag or name does not exist; list tags. no matching manifest for linux/arm64: the image is amd64 only; use --platform linux/amd64 or build multi-arch.

  • Rate limits: authenticate or mirror.

28.1

Scenario 9, Compose service starts before its dependency is ready

In plain words

The app container starts, tries the database, fails and exits, though the database container is "up".

The problem it solves

depends_on waits for the container to start, not for the service to be ready.

What it does

  • Symptom: connection refused at start; works if restarted later.
  • Confirm: logs of both services, timing of startup, the db's own readiness (Postgres takes seconds to accept connections).
  • Fix: add a healthcheck to the dependency and depends_on with condition: service_healthy; add retry logic in the app; use restart: on-failure as a safety net.
  • Verify with docker compose ps showing healthy.

Compose example

yamlcompose.yaml with health-based ordering
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: example
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10
  app:
    image: registry.example.com/shop/api:1.8.3
    depends_on:
      db:
        condition: service_healthy
    restart: on-failure
Check yourself
What does plain depends_on guarantee?

Only that the dependency container has been started, not that its service is ready.

Scenario 10, container is unhealthy or stuck restarting

In plain words

docker ps shows (unhealthy) or Restarting. A healthcheck fails, or the restart policy keeps relaunching a crashing process.

The problem it solves

It is hard to see why the check fails because its output is hidden by default.

What it does

  • Symptom: status unhealthy; Restarting (1) 5 seconds ago.
  • Confirm: docker inspect --format '{{json .State.Health}}' shows the last check outputs; run the check command manually with docker exec.
  • Causes: curl not installed in the image, wrong port or path, too short start_period, process needs more time.
  • Fix: install or use a tool that exists, adjust start_period, interval, retries; for restart loops fix the crash first (see scenario 1) and set a restart limit (on-failure:5).

Commands

docker events --since 10m --filter container=web --filter event=health_status
28.3

Scenario 11, container ignores stop and takes 10 seconds

In plain words

docker stop waits ten seconds and then kills the container. The main process does not handle SIGTERM.

The problem it solves

Slow deployments, lost in-flight requests and in Kubernetes slow rollouts and hung terminations.

What it does

  • Cause 1: shell form CMD npm start runs /bin/sh -c, so the shell is PID 1 and does not forward signals. Use exec form CMD ["node","server.js"] or exec in scripts.
  • Cause 2: the process as PID 1 ignores default signal actions; use --init (tini) or init: true in Compose.
  • Cause 3: the app has no SIGTERM handler; add graceful shutdown.
  • Fix and verify: time docker stop should be quick; also set STOPSIGNAL if the app expects another signal.

Compare forms

dockerfileShell form versus exec form
# Bad: sh is PID 1 and swallows SIGTERM
CMD npm start
# Good: node receives SIGTERM directly
CMD ["node", "server.js"]
bashTest shutdown time
docker run -d --name t --init registry.example.com/shop/api:1.8.3
time docker stop t
Check yourself
Why use exec form for CMD?

The application runs as PID 1 and receives signals directly instead of a shell that does not forward them.

Scenario 12, slow file access on macOS bind mounts

In plain words

Builds and tests are slow when the project directory is bind mounted into a container on macOS.

The problem it solves

Files cross a VM boundary, so many small file operations are expensive.

What it does

  • Symptom: npm install or test runs are several times slower in a bind mount than inside the container.
  • Confirm: time the same command in a named volume or the container's own filesystem.
  • Fix: keep node_modules or build output in a named volume or anonymous volume rather than the bind mount; use virtiofs (Docker Desktop, Colima --vm-type vz); use file sync (Compose watch, docker compose watch) instead of mounting; develop inside the container or on a remote Linux host.
  • Mount read-only when possible and exclude heavy folders.

          target: /app/src
        - action: rebuild
          path: package.json

Scenario 13, wrong architecture: exec format error

In plain words

A container fails with exec format error or a warning about platform mismatch.

The problem it solves

Apple silicon (arm64) and cloud servers (often amd64) need images built for the right CPU.

What it does

  • Symptom: exec /app: exec format error, or The requested image's platform (linux/amd64) does not match the detected host platform.
  • Confirm: docker image inspect --format '{{.Os}}/{{.Architecture}}', uname -m on the host, and the manifest list of the tag.
  • Fix: build multi-arch with docker buildx build --platform linux/amd64,linux/arm64, or choose the platform at run time with --platform; emulation (QEMU or Rosetta) works but is slower and can crash some binaries.
  • In Kubernetes, make sure node architecture matches the image or use a multi-arch manifest.

Commands

bashInspect and rebuild

docker buildx imagetools inspect registry.example.com/shop/api:1.8.3
docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/shop/api:1.8.4 --push .
Check yourself
What is a manifest list?

An image index that points to one image per platform, so each host pulls the matching architecture.

28.6

Scenario 14, high CPU or a runaway container

In plain words

One container takes all CPU or memory on a shared Docker host and other services slow down.

The problem it solves

Without limits, one process can starve the host.

What it does

  • Symptom: load average high, docker stats shows one container at several hundred percent CPU, swap in use.
  • Confirm: docker stats, docker top c, and top on the host; check for a loop, a crypto miner (compare with the expected process list) or a busy retry loop against a failing dependency.
  • Fix: set --cpus, --memory, --pids-limit limits; fix the loop; if compromised, stop and isolate the container, preserve it for analysis (docker export or docker commit to an offline image), and rotate secrets.
  • Prevent: resource limits in Compose and Kubernetes, monitoring, alerts on CPU throttling.

Commands

bashFind and limit
docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.PIDs}}'
docker top worker -eo pid,user,pcpu,args
docker update --cpus 1 --memory 512m --pids-limit 200 worker
28.7

Scenario 15, the Docker daemon will not start or hangs

In plain words

docker ps reports Cannot connect to the Docker daemon or hangs. The daemon failed to start or is stuck.

The problem it solves

Everything depending on Docker stops: builds, deployments on that host and local development.

What it does

  • Symptom: Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?; wrong context; socket permission denied for your user.
  • Confirm: docker context ls (wrong context or DOCKER_HOST set), systemctl status docker, journalctl -u docker -n 100, dockerd --validate on the config.
  • Causes: invalid daemon.json, full disk, corrupted storage, port or bridge IP conflict with VPN, user not in the docker group.
  • Fix: correct the JSON, free disk, remove the conflicting setting (bip), add the user to the group and re-login; on Docker Desktop or Colima restart the VM (colima restart). Last resort: stop Docker and move /var/lib/docker aside (this loses local images and volumes).

Commands

bashDaemon checks
docker context ls
systemctl status docker --no-pager | head -15
journalctl -u docker -n 50 --no-pager
python3 -m json.tool /etc/docker/daemon.json
df -h /var/lib/docker
Check yourself
Name two quick checks when docker cannot connect to the daemon.

Whether the current context or DOCKER_HOST points to the right socket, and whether the docker service is running (systemctl status docker or colima status).
