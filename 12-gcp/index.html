Section 1 of 16

Service map, gcloud and the resource hierarchy

8 concepts · about 50 minutes

If you know AWS, Google Cloud is mostly familiar with a few structural differences. The biggest one is the project, which replaces the AWS account as the unit of isolation, and a global VPC that spans regions.

Goals
  • Map common AWS services to their Google Cloud equivalents and name the key differences
  • Set up gcloud configurations and Application Default Credentials correctly
  • Explain organization, folders, projects and billing accounts and how they differ from AWS accounts
1.1

Service map from AWS to Google Cloud

In plain words

Almost every AWS building block has a Google Cloud counterpart. The names differ and a few designs differ in important ways.

The problem it solves

Engineers who know AWS lose time hunting for the right product name, and then misjudge how it behaves.

What it does

  • Compute: EC2 is Compute Engine, ECS/Fargate is Cloud Run, EKS is GKE, Lambda is Cloud Run functions (formerly Cloud Functions).
  • Network: VPC is a global VPC, ALB is the Application Load Balancer, Route 53 is Cloud DNS, WAF/Shield is Cloud Armor, Transit Gateway is Network Connectivity Center.
  • Data: S3 is Cloud Storage, RDS is Cloud SQL, Aurora is AlloyDB, DynamoDB is Bigtable or Firestore, ElastiCache is Memorystore, Redshift is BigQuery.
  • Ops: CloudWatch is Cloud Logging and Cloud Monitoring, X-Ray is Cloud Trace, ECR is Artifact Registry, Secrets Manager is Secret Manager, KMS is Cloud KMS, SQS/SNS is Pub/Sub.
  • Main difference: the mapping is approximate. Spanner has no direct AWS equivalent, and BigQuery is serverless with no cluster to size.

Quick lookup table

AWS Google Cloud Main difference
Account Project Projects sit in folders and are cheap to create
VPC (regional) VPC (global) One VPC, subnets are regional
ALB Global external Application LB One anycast IP serves all regions
IAM role on EC2 Service account A service account is both identity and resource
Organizations SCP Organization Policy Constraints plus IAM deny policies
Check yourself
Which Google Cloud object is closest to an AWS account?

The project.

1.2

The gcloud CLI and named configurations

In plain words

gcloud is the main command line tool. A configuration stores the account, project, region and zone so you can switch context quickly.

The problem it solves

Running commands against the wrong project is the most common and costly mistake, just as with AWS profiles.

What it does

  • gcloud config configurations create makes a named set of properties, similar to an AWS CLI profile.
  • gcloud auth login signs you in as a user; gcloud config set project selects the default project.
  • Every command accepts --project to override, which is safer in scripts.
  • Output formats --format=json, value(...) and table(...) plus --filter replace most jq use.
  • AWS equivalent: aws configure --profile and AWS_PROFILE. Main difference: gcloud also has a built-in filter and projection language.

Set up and inspect

bashNamed configurations
gcloud config configurations create shop-dev
gcloud config set account you@example.com
gcloud config set project shop-dev-123456
gcloud config set compute/region europe-west1
gcloud config set compute/zone europe-west1-b
gcloud config configurations list
gcloud projects list --format="table(projectId,name,lifecycleState)" --filter="labels.env=dev"
Tip

Show the active project in your shell prompt. Many teams also add a confirmation step for production configurations.

1.3

Application Default Credentials

In plain words

Application Default Credentials (ADC) is how Google client libraries and tools such as Terraform find credentials automatically.

The problem it solves

Code should not contain keys, yet it must run the same on a laptop, on GKE and in CI.

What it does

  • Lookup order: the GOOGLE_APPLICATION_CREDENTIALS file, then the local ADC file created by gcloud auth application-default login, then the attached service account from the metadata server.
  • gcloud auth login and ADC are separate. Logging in to gcloud does not set up ADC for your code.
  • For local use of a service account, prefer impersonation over downloaded keys.
  • AWS equivalent: the default credential provider chain. Main difference: on Google Cloud the final fallback is the metadata server of the VM, pod or Cloud Run service.

Local ADC with impersonation

bashADC for development
gcloud auth application-default login
gcloud auth application-default set-quota-project shop-dev-123456
# Use a service account without a key file
gcloud auth application-default login \
  --impersonate-service-account=tf-deployer@shop-dev-123456.iam.gserviceaccount.com
Check yourself
Does gcloud auth login configure ADC for your Python code?

No. You need gcloud auth application-default login.

1.4

Regions, zones and multi-region locations

In plain words

A region is a geographic area such as europe-west1. A zone is an isolated location inside it, such as europe-west1-b. Some services also offer multi-region locations such as EU or US.

The problem it solves

You need to place workloads for latency, data residency and failure isolation.

What it does

  • Regions typically have three zones. Zone names are per project, so do not assume letters mean the same hardware.
  • Zonal resources: VMs, zonal disks. Regional: subnets, regional MIGs, regional GKE clusters. Global: VPC, global load balancers, images.
  • Multi-region buckets and BigQuery datasets replicate across regions inside one geography.
  • AWS equivalent: regions and AZs. Main difference: many more resource types are global, and Google does not charge for traffic between zones of a region in the same way as AWS; check current pricing.

List locations

bashRegions and zones
gcloud compute regions list --format="value(name)"
gcloud compute zones list --filter="region:europe-west1" --format="value(name,status)"
1.5

Enabling APIs

In plain words

Each Google Cloud service is an API that must be enabled in a project before use.

The problem it solves

A new project has almost nothing turned on, so first calls fail with a "has not been used in project" error.

What it does

  • gcloud services enable turns on an API per project. Billing must be linked for most.
  • gcloud services list --enabled shows what is active; disabling APIs reduces attack surface.
  • Automation should enable APIs explicitly (Terraform google_project_service).
  • AWS equivalent: none, as AWS services are available by default (opt-in regions aside). Main difference: this is a deliberate extra step.

Enable what the Shop needs

bashEnable APIs
gcloud services enable container.googleapis.com compute.googleapis.com \
  artifactregistry.googleapis.com secretmanager.googleapis.com \
  sqladmin.googleapis.com redis.googleapis.com servicenetworking.googleapis.com \
  --project=shop-dev-123456
gcloud services list --enabled --project=shop-dev-123456 --format="value(config.name)"
Note

Enabling an API can take a minute. Retry loops in automation help.

1.6

Organization and folders

In plain words

The organization is the root of your company's resources, tied to a Cloud Identity or Google Workspace domain. Folders group projects beneath it.

The problem it solves

You need one place to apply policy, access and audit across hundreds of projects.

What it does

  • IAM allow policies, deny policies and organization policies set on a node are inherited by everything below.
  • Folders can nest (the current limit is about ten levels; check the docs). Typical layout is folders by environment or business unit.
  • Without an organization (a standalone project) you lose central policy, so create one early.
  • AWS equivalent: AWS Organizations with OUs. Main difference: IAM itself is inherited down the hierarchy, whereas in AWS you use SCPs as guardrails and per-account IAM.

Create folders and projects

bashFolders and projects
gcloud organizations list
gcloud resource-manager folders create --display-name="Production" --organization=123456789012
gcloud projects create shop-prod-123456 --folder=111122223333 --labels=env=prod,app=shop
Check yourself
Where do you attach a policy that must apply to every project?

On the organization node.

1.7

Projects

In plain words

A project is the container for resources, APIs, IAM and billing. It has three identifiers: a name, a globally unique ID and a number.

The problem it solves

You need blast-radius isolation, clear ownership and per-team cost tracking.

What it does

  • Project ID is permanent and unique across Google Cloud; the project number is used inside service account names.
  • Deleting a project schedules removal (about 30 days to restore). Use a lien to prevent accidental deletion.
  • Quotas and API enablement are per project, so a project per environment per app is common.
  • AWS equivalent: the account. Main difference: projects are lightweight, created in seconds, and you do not need a separate login or role chain to enter them.

Liens and inspection

bashProtect a project
gcloud projects describe shop-prod-123456 --format="value(projectNumber,parent.id)"
gcloud alpha resource-manager liens create --project=shop-prod-123456 \
  --restrictions=resourcemanager.projects.delete --reason="Production shop"
Careful

The lien command is in the alpha group at the time of writing. Check the current docs.

1.8

Billing accounts

In plain words

A billing account pays for the usage of the projects linked to it. A project has exactly one billing account at a time.

The problem it solves

Finance wants a clean invoice, while engineering wants separate projects.

What it does

  • Roles roles/billing.admin, roles/billing.user (link projects) and roles/billing.viewer control access, and are separate from project roles.
  • Unlinking billing stops paid resources, which is a quick way to stop runaway cost in a sandbox.
  • Billing export to BigQuery gives line-level data; budgets and alerts are set per billing account.
  • AWS equivalent: the management account payer with consolidated billing. Main difference: you can link and unlink any project freely, and a billing account is its own resource with its own IAM.

Link a project

bashBilling link
gcloud billing accounts list
gcloud billing projects link shop-dev-123456 --billing-account=0A1B2C-3D4E5F-6A7B8C
gcloud billing projects describe shop-dev-123456

Section 2 of 16

IAM, service accounts and workload identity

8 concepts · about 55 minutes

Google Cloud IAM answers who can do what on which resource. The policy is attached to a resource and inherited downward, which differs from the per-account model in AWS.

Goals
  • Grant access with principals, roles and allow policies at the right level of the hierarchy
  • Replace service account keys with impersonation and workload identity federation
  • Restrict access further with IAM conditions, deny policies and the IAM recommender
2.1

Principals, roles and allow policies

In plain words

An allow policy is a list of bindings. Each binding gives a role (a set of permissions) to one or more principals on one resource.

The problem it solves

You need to grant people and workloads just enough access, and manage it at scale without per-user policies everywhere.

What it does

  • Principals: Google accounts, groups, Cloud Identity domains, service accounts, workforce and workload identity pool identities, and allUsers (public).
  • Roles come as basic (owner, editor, viewer, avoid these), predefined (roles/storage.objectViewer) and custom.
  • A policy on a folder applies to all projects below it. Effective access is the union of inherited and local bindings, then reduced by deny policies.
  • AWS equivalent: identity and resource policies attached to users, roles and resources. Main difference: in Google Cloud you attach roles to the resource, and groups are the preferred way to give people access.

Grant and read a policy

bashBindings
gcloud projects add-iam-policy-binding shop-dev-123456 \
  --member="group:shop-devs@example.com" --role="roles/container.developer"
gcloud projects get-iam-policy shop-dev-123456 --format=json
gcloud iam roles describe roles/container.developer --format="value(includedPermissions)" | head
Danger

Do not use roles/owner or roles/editor for workloads. Editor alone allows changes to nearly every service.

Check yourself
Where should you grant a role that every project in a folder needs?

On the folder, to a group.

2.2

Predefined and custom roles

In plain words

A predefined role is maintained by Google. A custom role is a list of permissions you define yourself at the project or organization level.

The problem it solves

Predefined roles are sometimes too broad, yet writing exact permission lists for everything is tedious to maintain.

What it does

  • Prefer predefined roles first; look at gcloud iam roles list and the permissions reference.
  • Custom roles need maintenance because new permissions are not added automatically. Check each permission's launch stage.
  • Permissions name pattern: service.resource.verb, for example storage.objects.get.
  • AWS equivalent: managed policies versus customer managed policies. Main difference: roles are named permission sets that you bind, not documents containing resources and conditions.

Create a custom role

bashCustom role
gcloud iam roles create shopDeployer --project=shop-dev-123456 \
  --title="Shop deployer" \
  --permissions=container.deployments.update,container.pods.list,container.pods.get \
  --stage=GA
gcloud iam roles list --project=shop-dev-123456 --format="table(name,title)"
2.3

Service accounts

In plain words

A service account is an identity for software. It is also a resource, so you can grant roles to it and grant others the ability to use it.

The problem it solves

Applications need an identity that is not a person, with limited permissions and no password.

What it does

  • Email form: name@PROJECT_ID.iam.gserviceaccount.com.
  • Attached to a VM, Cloud Run service or build, it supplies tokens through the metadata server.
  • Using one needs iam.serviceAccounts.actAs (via roles/iam.serviceAccountUser). Treat that as a powerful permission, since it lets someone run code as the account.
  • Create one per workload. The default Compute Engine service account carries the editor role in old projects; avoid it.
  • AWS equivalent: an IAM role with an instance profile. Main difference: a service account is a principal that exists permanently, while an AWS role is assumed and gives temporary credentials.

Create and grant

bashService account for the Shop API
gcloud iam service-accounts create shop-api --display-name="Shop API" --project=shop-dev-123456
gcloud projects add-iam-policy-binding shop-dev-123456 \
  --member="serviceAccount:shop-api@shop-dev-123456.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
Check yourself
What permission lets a user run a workload as a service account?

iam.serviceAccounts.actAs, included in roles/iam.serviceAccountUser.

2.4

Service account impersonation

In plain words

Impersonation lets an authorised principal obtain short-lived credentials for a service account without ever holding a key.

The problem it solves

Downloaded JSON keys leak, never expire by default and are hard to track.

What it does

  • Needs roles/iam.serviceAccountTokenCreator on the target service account.
  • gcloud --impersonate-service-account=SA runs one command as that account; Terraform supports impersonate_service_account.
  • Audit logs show both the caller and the service account.
  • The organization policy iam.disableServiceAccountKeyCreation blocks keys entirely.
  • AWS equivalent: sts:AssumeRole. Main difference: very similar idea; the call is generateAccessToken and the token lasts up to an hour by default.

Use it

bashImpersonation
gcloud iam service-accounts add-iam-policy-binding \
  tf-deployer@shop-dev-123456.iam.gserviceaccount.com \
  --member="group:platform@example.com" --role="roles/iam.serviceAccountTokenCreator"
gcloud storage ls gs://shop-dev-state \
  --impersonate-service-account=tf-deployer@shop-dev-123456.iam.gserviceaccount.com
2.5

Workload identity federation for external workloads

In plain words

Workload Identity Federation lets a workload outside Google Cloud (GitHub Actions, AWS, Azure, on-premises OIDC) exchange its own token for Google credentials.

The problem it solves

CI systems and other clouds used to hold service account keys, which is a standing secret that can leak.

What it does

  • You create a workload identity pool and a provider (OIDC or AWS or SAML), with an attribute mapping and a condition.
  • External token goes to the Security Token Service, and returns a federated token; it can be used directly or to impersonate a service account.
  • Always set an attribute condition, otherwise any identity from that provider may match.
  • AWS equivalent: an IAM OIDC identity provider with AssumeRoleWithWebIdentity. Main difference: since the pool is defined per provider with CEL mapping and conditions rather than a trust policy on the role.

Pool and provider for one repository

bashWorkload identity pool
gcloud iam workload-identity-pools create github --location=global --project=shop-dev-123456
gcloud iam workload-identity-pools providers create-oidc github-oidc \
  --location=global --workload-identity-pool=github \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository" \
  --attribute-condition="assertion.repository=='example-org/shop'" \
  --project=shop-dev-123456
Check yourself
Why must you set an attribute condition on a GitHub provider?

Otherwise any repository on GitHub could match the provider.

2.6

IAM conditions

In plain words

A condition is an expression that makes a role binding apply only in some circumstances.

The problem it solves

You want time-boxed access, access limited to certain resource names, or access only until a date.

What it does

  • Written in Common Expression Language (CEL), for example request.time < timestamp("2027-01-01T00:00:00Z") or resource.name.startsWith("projects/_/buckets/shop-").
  • Attributes depend on the service; not every service supports every attribute. Check the current docs.
  • Bindings with conditions require policy version 3.
  • AWS equivalent: the Condition block in IAM policies. Main difference: the condition is attached to a single binding, not to a policy statement.

Temporary access

bashTime limited binding
gcloud projects add-iam-policy-binding shop-prod-123456 \
  --member="user:oncall@example.com" --role="roles/container.admin" \
  --condition='expression=request.time < timestamp("2027-02-01T00:00:00Z"),title=oncall-feb,description=Temporary access'
2.7

IAM deny policies

In plain words

A deny policy blocks specific principals from specific permissions, regardless of what allow policies grant.

The problem it solves

Allow policies are additive, so inherited grants are hard to take away at a lower level.

What it does

  • Deny is evaluated first and wins over allow. Attach to organization, folder or project.
  • Rules list denied principals, optional exceptions and permissions in the form service.googleapis.com/resource.verb.
  • Typical use: block deleting audit sinks or creating service account keys for all but a break-glass group.
  • AWS equivalent: explicit Deny in SCPs or identity policies. Main difference: deny policies are a separate policy type, not statements inside the allow policy.

Deny file

jsondeny-sa-keys.json
{
  "displayName": "Deny SA key creation",
  "rules": [
    {
      "denyRule": {
        "deniedPrincipals": ["principalSet://goog/public:all"],
        "exceptionPrincipals": ["principalSet://goog/group/breakglass@example.com"],
        "deniedPermissions": ["iam.googleapis.com/serviceAccountKeys.create"]
      }
    }
  ]
}
bashAttach to the organization
gcloud iam policies create deny-sa-keys --attachment-point="cloudresourcemanager.googleapis.com/organizations/123456789012" \
  --kind=denypolicies --policy-file=deny-sa-keys.json
Check yourself
If an allow policy grants a permission and a deny policy denies it, what happens?

The request is denied.

2.8

IAM Recommender and Policy Troubleshooter

In plain words

The IAM Recommender suggests removing roles that were not used, using about 90 days of activity. The Policy Troubleshooter explains why a principal can or cannot do something.

The problem it solves

Permissions grow over time and nobody knows which are still needed. Debugging a "403" is slow without a tool.

What it does

  • Recommendations include role removal or replacement with a narrower role; review before applying.
  • Policy Analyzer answers "who can access this resource" across the hierarchy.

VPC networking, connectivity, DNS and Cloud Armor

8 concepts · about 60 minutes

Google Cloud networking is software defined and global. One VPC network spans every region, which removes a lot of the peering and gateway plumbing that AWS needs.

Goals
  • Design a global VPC with regional subnets, firewall rules and hierarchical firewall policies

4.1

Global VPC and subnets

In plain words

A VPC network is a global virtual network. It contains subnets, and each subnet belongs to one region and spans all zones in it.

The problem it solves

Multi-region applications need private connectivity between regions without building tunnels or peering for every region pair.

What it does

  • Create the VPC in custom mode (you define subnets). The auto mode network creates a subnet per region and is not recommended for production.
  • Routes and firewall rules belong to the VPC, not to a subnet. VMs in different regions of the same VPC talk over internal IPs by default routes.
  • Subnets can have secondary ranges, which GKE uses for Pods and Services.
  • Subnets can be expanded but not shrunk or moved.
  • AWS equivalent: VPC with subnets. Main difference: the VPC is global and a subnet is regional, not tied to one AZ.

  --secondary-range=pods=10.64.0.0/14,services=10.68.0.0/20

Firewall rules

In plain words

VPC firewall rules allow or deny traffic to and from VM network interfaces. They are stateful and enforced at the instance, not at the subnet edge.

The problem it solves

You need to control east-west and north-south traffic at the workload without a network appliance.

What it does

  • Each network has implied rules: deny all ingress and allow all egress at the lowest priority.
  • A rule has direction, priority (0 highest to 65535 lowest), action, source or destination ranges and targets (all instances, network tags or service accounts).
  • Prefer service account targets over network tags, because tags can be set by anyone with VM edit rights.
  • Health check ranges (130.211.0.0/22, 35.191.0.0/16) must be allowed for load balancers.
  • AWS equivalent: security groups and NACLs. Main difference: rules support deny and priorities, and target by tag or service account rather than being attached to a group.

In plain words

Cloud KMS creates and manages cryptographic keys inside key rings at a location. Keys hold versions; the key material never leaves the service unless you choose to export under policy.

In plain words

A Gateway creates the global load balancer, an HTTPRoute sends /api to the API and everything else to the web, and a policy attaches Cloud Armor.

The problem it solves

Users need HTTPS on one hostname with routing, a managed certificate, and edge protection.

What it does

16.7

Verify, observe and roll out

In plain words

After deployment, check health end to end, enable monitoring, and roll out new versions with a rolling update and a canary.

The problem it solves

A deployed app is not a healthy app. You need proof and a safe update path.

What it does

  • Check the LB: kubectl -n shop describe gateway shop-gw, then curl -I https://shop.example.com/api/healthz.
  • Managed Prometheus scrapes /metrics through PodMonitoring; create the alert from the observability file.
  • Roll out with kubectl set image and kubectl rollout status; undo with kubectl rollout undo.
  • For canary, add a second backend with weights on the HTTPRoute.
  • AWS equivalent: the same kubectl workflow on EKS. Main difference: Gateway weights replace ALB weighted target groups.

16.8

Upgrades, cost and teardown for the Shop

In plain words

Day-two work is keeping the cluster current, watching cost, and removing the stack cleanly when finished.

The problem it solves

Demo stacks left running cost money, and unplanned upgrades surprise teams.

What it does

  • Upgrades: the release channel upgrades the control plane and Autopilot nodes. Use maintenance windows, exclusions and PDBs for the Shop Pods.
  • Cost: Autopilot bills per Pod requests; Cloud SQL HA doubles instance cost; Memorystore Standard bills per GB. Use budgets and labels (app=shop).
  • Teardown: delete the cluster, Memorystore, Cloud SQL (remove deletion protection), the private services connection, then the network. Terraform destroy handles the order.
  • AWS equivalent: EKS upgrades and Terraform destroy. Main difference: Google upgrades automatically, and the peering must be removed before deleting the VPC.

Cleanup commands

bashTeardown
kubectl delete namespace shop
gcloud container clusters delete shop-auto --region=$REGION --quiet
gcloud redis instances delete shop-cache --region=$REGION --quiet
gcloud sql instances patch shop-pg --no-deletion-protection --quiet
gcloud sql instances delete shop-pg --quiet
gcloud services vpc-peerings delete --service=servicenetworking.googleapis.com --network=shop-net --quiet
gcloud compute addresses delete google-managed-services --global --quiet
gcloud compute networks delete shop-net --quiet
Danger

These commands delete data. Confirm the project and take a backup first.
