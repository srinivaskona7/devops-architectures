Section 1 of 18

The Shop - requirements and scope

8 concepts · about 45 minutes

The Shop is one worked example that ties the whole curriculum together. It is a small e-commerce system with a catalog, a cart, orders, payments (including a mock UPI gateway) and a plain HTML frontend. Every other folder teaches a tool; this folder shows those tools working as one project, from the first requirement to the handover pack. We refer to the other folders by name instead of repeating them: Docker, Kubernetes, Terraform, CI/CD, Monitoring and ELK.

Goals
  • Turn a business idea into functional and non-functional requirements with numbers
  • Size the system from order volume and derive request rates and storage
  • Record scope, risks and success measures before any code exists
1.1

What we are building and why

In plain words

An online shop for an Indian retailer. Customers browse products, fill a cart, place an order and pay by UPI. Staff manage products and watch orders.

The problem it solves

Tool tutorials in isolation never show how decisions interact: the Dockerfile shapes the pipeline, the pipeline shapes the cluster, the cluster shapes the alerts. A single project shows the whole chain.

What it does

  • Defines five runtime parts: catalog, cart, orders, payments and a web frontend, plus upi-mock in non-production.
  • Uses PostgreSQL for catalog, orders and payments data, and Redis for carts.
  • Runs on AWS EKS in region ap-south-1, built with Terraform, deployed with Argo CD.
  • Is deliberately small so every file fits on a screen, yet complete enough to build, test, scan, deploy, break and recover.
1.2

Personas and user journeys

In plain words

A persona is a short description of a type of user. A journey is the ordered list of things that persona does.

The problem it solves

Without journeys, teams build endpoints nobody calls and miss the one flow that earns money.

What it does

  • Shopper: browse products, add to cart, checkout, pay with UPI, see order status.
  • Store admin: create or update products, adjust stock.
  • Operator (us): deploy, watch dashboards, answer alerts, restore from backup.
  • The shopper checkout journey is the critical path. Later chapters attach the main SLO, load test and runbooks to it.
Check yourself
Which journey becomes the basis of the SLO?

Checkout, because a failure there loses revenue directly.

1.3

Functional requirements

In plain words

A list of what the system must do, written so each line can be tested.

The problem it solves

Vague wishes such as "support payments" cannot be tested, estimated or accepted.

What it does

  • FR1 List and search products with price in paise (integer, 1 rupee = 100 paise).
  • FR2 A cart holds sku and quantity per user and expires after 7 days of inactivity.
  • FR3 An order reserves stock, records items and prices at purchase time, and has a status of pending, paid, failed or cancelled.
  • FR4 A payment is created once per order (idempotent) and settled by a UPI collect request to a gateway.
  • FR5 A slow gateway reports PENDING and later calls a signed webhook with the final result.
  • FR6 Failed payment releases the reserved stock.
1.4

Non-functional requirements with numbers

In plain words

Non-functional requirements describe how well the system works: speed, availability, security, cost, recoverability.

The problem it solves

"Fast and reliable" has no value to an engineer. A number can be measured, alerted on and paid for.

What it does

  • Availability SLO for checkout 99.9 percent over 30 days (error budget 43.2 minutes, shown in the observability file).
  • Latency: 95th percentile of POST /orders under 800 ms; catalog reads under 200 ms.
  • Recovery: RPO 5 minutes (RDS point-in-time restore), RTO 60 minutes.
  • Security: no long-lived cloud keys in CI, secrets from a secret manager, images scanned, pods non-root.
  • Cost: production under about 600 USD per month at launch scale (worked later).
1.5

Capacity estimate with the arithmetic

In plain words

Turn the business forecast into requests per second and storage so that replica counts and instance sizes are not guesses.

The problem it solves

Over-provisioning wastes money; under-provisioning fails on the first sale day.

What it does

  • Forecast 20,000 orders per day. Assume 15 percent of them fall in the busiest hour: 20,000 x 0.15 = 3,000 orders per hour = 0.83 orders per second.
  • Assume 30 API requests per order across browse, cart and checkout: 0.83 x 30 = 25 requests per second.
  • Apply a 3x headroom factor for spikes: 75 requests per second.
  • One uvicorn worker handles roughly 150 requests per second for these light handlers (measure with k6 before trusting), so 75 / 150 = 0.5 workers. Three replicas are chosen for availability, not for throughput.
  • Storage: 20,000 orders per day x 365 days x 2 KB per order and items = about 14.6 GB per year. A 50 GB gp3 volume is ample for the first year.

Check the numbers

pythoncapacity.py
orders_per_day = 20_000
busy_hour_share = 0.15
requests_per_order = 30
headroom = 3
per_worker_rps = 150

orders_per_sec = orders_per_day * busy_hour_share / 3600
rps = orders_per_sec * requests_per_order
target = rps * headroom
print(f"orders/s={orders_per_sec:.2f} rps={rps:.0f} target={target:.0f}")
print(f"workers needed={target / per_worker_rps:.2f}")
print(f"storage GB/year={orders_per_day * 365 * 2 / 1e6:.1f}")
1.6

Constraints, assumptions and risks

In plain words

Constraints are fixed facts, assumptions are things we believe but have not proven, risks are things that could hurt.

The problem it solves

Unwritten assumptions turn into surprises in production.

What it does

  • Constraint: AWS only at launch, EKS for compute, existing GitHub organisation.
  • Assumption: traffic is mostly India daytime; the per-worker 150 rps figure holds (verify with k6).
  • Risk: payment gateway latency stalls checkout. Mitigation: timeouts, PENDING state, webhook completion.
  • Risk: stock oversell under concurrency. Mitigation: atomic conditional update in SQL.
  • Keep a short register in the repo and review it each release.

Architecture decisions and repository layout

8 concepts · about 50 minutes

This file fixes the architecture and the repository that all later files build on. For the general method of weighing options see the Architecture Decisions folder (13).

Goals
  • Draw the Shop architecture at context and container level
  • Record decisions as short architecture decision records
  • Organise a mono-repo with services, infrastructure and deployment folders
2.1

System context and containers

In plain words

A context view shows the system and who talks to it. A container view shows the deployable parts inside it.

The problem it solves

Without a shared picture, every engineer holds a different model of the system.

What it does

  • External actors: shopper browser, admin, the UPI gateway (mock in staging, a payment provider in production).
  • Inside: web (nginx), catalog, cart, orders, payments, plus PostgreSQL (RDS) and Redis (ElastiCache).
  • Orders calls catalog and payments over HTTP inside the cluster. Payments calls the gateway outside.
  • Only web is exposed through the load balancer. It proxies /api/<service>/ to the Services.
2.2

Sequence of a successful checkout

In plain words

The order of calls between services for one purchase.

The problem it solves

Hidden call chains cause hidden failure modes: each arrow is a place where a timeout can happen.

What it does

  • Orders checks prices and reserves stock in catalog, then writes a pending order.
  • Orders asks payments to collect. Payments creates a payment row first, then calls the gateway.
  • Success marks the order paid. Failure releases stock. PENDING waits for the webhook.
2.3

Technology choices at a glance

In plain words

The stack, with one line of reason for each part.

The problem it solves

Choices made by habit are hard to defend or change later.

What it does

  • Python 3.12 and FastAPI: fast to write, typed models, built-in OpenAPI docs.
  • PostgreSQL on RDS: transactions for orders and payments. Redis on ElastiCache: cheap expiring carts.
  • Containers on EKS: the stack your organisation already runs. Managed node groups keep node patching simple.
  • Kustomize plus Argo CD: plain YAML with overlays, pull-based deploys.
  • GitHub Actions with OIDC to AWS: no stored keys. A Jenkinsfile is included for teams that use Jenkins.
2.4

In plain words

An ADR is a half-page file that records one decision: context, the decision, and consequences. It lives in the repo next to the code.

The problem it solves

Six months later nobody remembers why the team chose X, so they either fear changing it or change it blindly.

What it does

  • One file per decision in docs/adr/, numbered, never edited after acceptance; a new ADR supersedes an old one.
  • Status values: proposed, accepted, superseded.
  • Review ADRs in pull requests like code.

2.5

ADR 1 - services split by domain, not by layer

In plain words

Each business domain (catalog, cart, orders, payments) is its own small service with its own data.

The problem it solves

One big service is simple but deploys together, scales together and fails together. Splitting by technical layer (an "API service", a "DB service") creates chatty coupling.

What it does

  • Decision: four services, each owning its tables or keys; no service reads another service's tables.
  • Payments is separate because it needs stricter security, its own scaling and its own on-call attention.
  • Consequence: cross-service calls need timeouts and idempotency, which later files implement.
  • Rejected: a single modular monolith. It would be a fair choice for a team of two; revisit if the team stays small.

The record

markdowndocs/adr/0001-service-per-domain.md
# ADR 0001 Split by business domain
Status: accepted
Context: 4 domains, different scaling and security needs. Team of 6.
Decision: one service per domain, each owns its data.
Consequences: network timeouts, idempotency keys, per-service pipelines.
2.6

ADR 2 - one RDS instance, a database per service

In plain words

Catalog, orders and payments each get their own database and database user, but share one RDS instance at launch.

The problem it solves

One RDS instance per service would cost four times as much; one shared schema would let services read each other's data.

What it does

  • Decision: one multi-AZ PostgreSQL instance, three databases, three users with access only to their own database.
  • Cart uses Redis, not Postgres, because carts are temporary and read often.
  • Consequence: the instance is a shared failure point and a noisy-neighbour risk. Split payments to its own instance when load or compliance requires.
  • Credentials are different per service and come from Secrets Manager (see the Kustomize files).
2.7

ADR 3 - GitOps with Argo CD and Kustomize

In plain words

The cluster state is described in Git. A controller in the cluster pulls and applies it.

The problem it solves

CI pipelines holding cluster-admin credentials are a large attack surface and drift silently when someone runs kubectl edit.

What it does

  • Decision: CI builds and pushes an image, then commits the new image tag into the deploy folder; Argo CD syncs it.
  • Kustomize overlays hold per-environment differences, so there is no template language to learn.
  • Consequence: rollback is a Git revert; the CI role needs only ECR push, not cluster access.
  • See the CI/CD folder for Argo CD internals and the Kubernetes folder for Kustomize basics.
2.8

Repository layout

In plain words

One mono-repo holds services, infrastructure and deployment so that one pull request can change code and manifests together.

Scattered repositories make cross-cutting changes hard and let versions drift.

What it does

  • web/ holds the static frontend and nginx config.
  • infra/ holds Terraform modules and environment roots.
  • deploy/ holds Kustomize base/ and overlays/.
  • .github/workflows/ and Jenkinsfile hold pipelines; docs/ holds ADRs and runbooks; loadtest/ holds k6.

Application core and the catalog service

7 concepts · about 55 minutes

The Shop services share one skeleton. Each service is a small FastAPI app of fewer than 150 lines. The code below is complete; copy it into services/catalog/app/ to follow along. Python 3.12 is assumed.

Goals
  • Build the shared service skeleton with config, logging, health and metrics
  • Write the catalog service with an atomic stock reservation
  • Understand the 12-factor choices that make the service easy to operate
3.1

Service skeleton and dependencies

In plain words

Every service has the same shape: a settings object read from environment variables, a database engine, health endpoints, a metrics endpoint and a JSON log line per request.

The problem it solves

Services that each invent their own config, health checks and logging are painful to deploy, probe and monitor.

What it does

  • Configuration comes only from environment variables (12-factor), so the same image runs in every environment.
  • /healthz says the process is alive. /readyz says it can reach its dependencies. Kubernetes probes use them.
  • /metrics exposes Prometheus counters and histograms.
  • Pinned dependencies make builds repeatable.

3.2

Settings from the environment

In plain words

A small class that reads every setting from environment variables with safe defaults for local work.

The problem it solves

Hard-coded database URLs and secrets force a rebuild per environment and leak into Git.

What it does

  • Uses a frozen dataclass, so settings cannot change at runtime.
  • DATABASE_URL defaults to in-memory SQLite, which makes unit tests need no database.
  • Secrets arrive as env vars from a Kubernetes Secret (see the Kustomize files), never from the image.

config.py

pythonservices/catalog/app/config.py
import os
from dataclasses import dataclass


@dataclass(frozen=True)
class Settings:
    database_url: str = os.getenv("DATABASE_URL", "sqlite+pysqlite:///:memory:")
    service_name: str = os.getenv("SERVICE_NAME", "catalog")
    log_level: str = os.getenv("LOG_LEVEL", "INFO")


settings = Settings()
3.3

Structured JSON logging

In plain words

Each log line is one JSON object with a timestamp, level, message and request fields.

The problem it solves

Free text logs cannot be filtered by field in Loki or Elasticsearch, and multi-line stack traces break log shippers.

What it does

  • A tiny formatter writes JSON to stdout; the container runtime and the log agent collect it (see the ELK folder).
  • A middleware logs method, path, status and duration for every request.
  • Never log card numbers, UPI IDs in full or tokens.

import sys

Metrics and request middleware

In plain words

One middleware times every request, counts it by route and status, and writes the JSON log line.

The problem it solves

Without request metrics there is nothing to alert on, no SLO and no dashboard (see the Monitoring folder).

What it does

  • http_requests_total{service,method,path,status} is a counter. http_request_duration_seconds is a histogram.
  • The path label uses the route template such as /products/{sku}, never the raw URL. Raw URLs with IDs would create unlimited label values and overload Prometheus (cardinality).
  • The same file is copied into every service.

import logging
import time

from fastapi import FastAPI, Request, Response
from prometheus_client import CONTENT_TYPE_LATEST, Counter, Histogram, generate_latest

REQS = Counter("http_requests_total", "HTTP requests", ["service", "method", "path", "status"])
LAT = Histogram("http_request_duration_seconds", "HTTP latency", ["service", "path"])
log = logging.getLogger("shop")


def install(app: FastAPI, service: str) -> None:
    @app.middleware("http")
    async def observe(request: Request, call_next):
        start = time.perf_counter()
        response = await call_next(request)
        took = time.perf_counter() - start
        route = request.scope.get("route")
        path = route.path if route else "unmatched"
        REQS.labels(service, request.method, path, str(response.status_code)).inc()
        LAT.labels(service, path).observe(took)
        log.info("request", extra={"fields": {
            "service": service, "method": request.method, "path": path,
            "status": response.status_code, "ms": round(took * 1000, 1)}})
        return response

    @app.get("/metrics", include_in_schema=False)
    def metrics() -> Response:
        return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

Catalog routes and atomic stock reservation

In plain words

Endpoints to create, list and read products, and to reserve or release stock.

The problem it solves

Two shoppers buying the last item at the same moment must not both succeed. A read-then-write in Python has a race.

What it does

  • Reservation is one SQL statement: UPDATE products SET stock = stock - :qty WHERE sku = :sku AND stock >= :qty. The database applies it atomically; zero rows changed means not enough stock.
  • Returns 404 for an unknown SKU and 409 for insufficient stock.
  • Release adds the quantity back when a payment fails.
  • /readyz runs SELECT 1; /healthz does not touch the database, so a database outage does not restart every pod.

4.1

Cart service with Redis

In plain words

A cart is a Redis hash per user: field is the SKU, value is the quantity. The key expires 7 days after the last change.

The problem it solves

Carts are temporary, read often and written often. Putting them in the orders database wastes transactions and storage on data most shoppers abandon.

What it does

  • Key cart:<user> is a hash. HSET changes a line, HDEL removes it, EXPIRE refreshes the 7 day TTL (604,800 seconds).
  • A MemoryStore with the same four methods is used when REDIS_URL is empty, so tests and local runs need no Redis.
  • The user comes from the X-User-Id header. In real life an auth gateway sets it after verifying a token.

store.py

import os

TTL_SECONDS = 7 * 24 * 3600


class MemoryStore:
    def __init__(self) -> None:
        self.data: dict[str, dict[str, str]] = {}

    def hset(self, key: str, field: str, value: str) -> None:
        self.data.setdefault(key, {})[field] = value

    def hgetall(self, key: str) -> dict[str, str]:
        return dict(self.data.get(key, {}))

    def hdel(self, key: str, field: str) -> None:
        self.data.get(key, {}).pop(field, None)

    def delete(self, key: str) -> None:
        self.data.pop(key, None)

    def expire(self, key: str, seconds: int) -> None:
        return None


def make_store():
    url = os.getenv("REDIS_URL", "")
    if not url:
        return MemoryStore()
    import redis

    return redis.Redis.from_url(url, decode_responses=True, socket_timeout=1.0)

Service clients with timeouts

In plain words

Small functions wrap the HTTP calls to catalog and payments. Each has a timeout and turns failures into one clear exception.

The problem it solves

A call without a timeout can hang a worker forever. A slow dependency then takes down the caller too (cascading failure).

What it does

  • A shared httpx.Client timeout of 3 seconds (CALL_TIMEOUT_SECONDS).
  • Upstream is raised for network errors and 5xx answers, so the route returns 502 and compensates.
  • Keeping calls in one module lets tests replace them without any network.

clients.py

pythonservices/orders/app/clients.py
import httpx

from .config import settings


class Upstream(Exception):
    pass


class OutOfStock(Exception):
    pass


def _client() -> httpx.Client:
    return httpx.Client(timeout=settings.call_timeout)


def get_product(sku: str) -> dict | None:
    try:
        with _client() as c:
            r = c.get(f"{settings.catalog_url}/products/{sku}")
    except httpx.HTTPError as e:
        raise Upstream(str(e)) from e
    if r.status_code == 404:
        return None
    if r.status_code >= 500:
        raise Upstream(f"catalog {r.status_code}")
    return r.json()


def reserve(sku: str, qty: int) -> None:
    try:
        with _client() as c:
            r = c.post(f"{settings.catalog_url}/products/{sku}/reserve", json={"qty": qty})
    except httpx.HTTPError as e:
        raise Upstream(str(e)) from e
    if r.status_code == 409:
        raise OutOfStock(sku)
    if r.status_code >= 400:
        raise Upstream(f"catalog {r.status_code}")


def release(sku: str, qty: int) -> None:
    try:
        with _client() as c:
            c.post(f"{settings.catalog_url}/products/{sku}/release", json={"qty": qty})
    except httpx.HTTPError:
        pass  # best effort; a reconciliation job repairs leftovers


def collect(order_id: int, amount_paise: int, vpa: str) -> dict:
    try:
        with _client() as c:
            r = c.post(f"{settings.payments_url}/payments",
                       json={"order_id": order_id, "amount_paise": amount_paise, "vpa": vpa})
    except httpx.HTTPError as e:
        raise Upstream(str(e)) from e
    if r.status_code >= 500:
        raise Upstream(f"payments {r.status_code}")
    return r.json()

Creating an order with idempotency and compensation

In plain words

The order route checks prices, reserves stock, saves a pending order, asks payments to collect, and then marks the order paid, failed or pending.

The problem it solves

Several services are involved and there is no distributed transaction. If payment fails after stock was reserved, stock must be given back, and a retried request must not create a second order.

What it does

  • Same Idempotency-Key returns the existing order (HTTP 200).
  • Reservations made so far are released if a later step fails (compensation, a simple saga).
  • Payment answers: SUCCESS gives status paid, FAILURE gives failed and releases stock, PENDING leaves the order pending until the webhook arrives.
  • Payments calls POST /internal/orders/{id}/payment-result to finish pending orders.

@app.post("/orders", status_code=201)
def create_order(body: NewOrder, response: Response, x_user_id: str = Header(default=""),
                 idempotency_key: str | None = Header(default=None)) -> dict:
    if not x_user_id:
        raise HTTPException(401, "X-User-Id required")
    if idempotency_key:
        with SessionLocal() as s:
            existing = s.scalar(select(Order).where(Order.idem_key == idempotency_key))
            if existing:
                response.status_code = 200
                return to_dict(existing)

    priced, reserved = [], []
    try:
        for line in body.items:
            product = clients.get_product(line.sku)
            if product is None:
                raise HTTPException(404, f"unknown sku {line.sku}")
            clients.reserve(line.sku, line.qty)
            reserved.append(line)
            priced.append((line, product["price_paise"]))
    except clients.OutOfStock as e:
        _release(reserved)
        raise HTTPException(409, f"out of stock {e}") from e
    except clients.Upstream as e:
        _release(reserved)
        raise HTTPException(502, "catalog unavailable") from e
    except HTTPException:
        _release(reserved)
        raise

    total = sum(line.qty * price for line, price in priced)
    with SessionLocal.begin() as s:
        order = Order(user_id=x_user_id, status="pending", total_paise=total, idem_key=idempotency_key)
        order.items = [OrderItem(sku=l.sku, qty=l.qty, price_paise=p) for l, p in priced]
        s.add(order)
        s.flush()
        order_id = order.id

    try:
        result = clients.collect(order_id, total, body.vpa)
    except clients.Upstream as e:
        _finish(order_id, "failed", reserved)
        raise HTTPException(502, "payments unavailable") from e

    status = result.get("status")
    if status == "SUCCESS":
        _finish(order_id, "paid", [])
    elif status == "FAILURE":
        _finish(order_id, "failed", reserved)
        raise HTTPException(402, "payment failed")
    with SessionLocal() as s:
        return to_dict(s.get(Order, order_id))

Payments, the mock UPI gateway and the web frontend

8 concepts · about 60 minutes

Payments is the service that earns the most attention from security and on-call. UPI (Unified Payments Interface) lets a customer approve a payment from a bank app using a virtual payment address (VPA) such as asha@okbank. In a real launch you integrate a licensed payment provider; the rules for collect requests change over time, so check the current provider and NPCI documentation. Here a mock gateway stands in so every failure mode can be rehearsed.

Goals
  • Model a UPI collect payment with idempotency and signed webhooks
  • Build a mock gateway that can succeed, fail or answer late
  • Serve a plain HTML frontend through nginx that proxies the services
5.1

Payment states and the UPI flow

In plain words

A payment starts as PENDING and ends as SUCCESS or FAILURE. UPI is asynchronous by nature: the customer must approve on their phone, which can take seconds or never happen.

The problem it solves

Treating a payment as a single synchronous call loses money: a timeout does not mean the customer did not pay.

What it does

  • Payments writes its own row first, then calls the gateway with the payment id as the reference.
  • A gateway timeout leaves the payment PENDING; the signed webhook or a reconciliation job later settles it.
  • One payment per order (unique order_id), so a retry returns the same payment.
  • Amounts are integer paise. The VPA is stored but masked in logs.
5.2

Payments data model and settings

In plain words

One table keyed by order, plus settings for the gateway address and the webhook secret.

The problem it solves

Without a unique order key a double click or client retry charges the customer twice.

What it does

  • order_id is unique, so the database refuses a second payment for the same order.
  • GATEWAY_URL, WEBHOOK_SECRET and ORDERS_URL come from the environment; the secret comes from a Kubernetes Secret.
  • gateway_ref stores the provider's reference for reconciliation.

5.3

Signed webhooks

In plain words

The gateway sends the final result to us by an HTTP call. It signs the body with a shared secret so we know it is genuine.

The problem it solves

A webhook URL is public to the internet. Anyone could post "SUCCESS" and get free goods.

What it does

  • Signature is HMAC-SHA256 of the raw request body, hex encoded, sent in X-Signature.
  • We compute our own and compare with hmac.compare_digest, which takes constant time and prevents timing attacks.
  • Reject with 401 if it differs. The secret is rotated by changing the Kubernetes Secret and restarting; providers usually support two active secrets during rotation.
  • The webhook handler is idempotent: a repeated event for a settled payment changes nothing.

import hashlib
import hmac


def sign(secret: str, body: bytes) -> str:
    return hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()


def verify(secret: str, body: bytes, signature: str) -> bool:
    return hmac.compare_digest(sign(secret, body), signature or "")
5.4

The gateway client and the payments routes

In plain words

Payments calls the gateway with a timeout and maps every outcome to a payment status.

The problem it solves

A hung gateway call would hold a worker and make checkout slow for everyone.

What it does

  • Timeout or network error leaves the payment PENDING and returns it; the order stays pending too.
  • A repeated POST /payments for the same order returns the stored row without calling the gateway again.
  • After a webhook, payments tells orders the final result (best effort; reconciliation catches failures).
  • Logs use mask(vpa) so only the first two characters appear.

        if not p:
            raise HTTPException(404, "unknown payment")
        if p.status != "PENDING":
            return to_dict(p)
        p.status = status
        order_id, out = p.order_id, to_dict(p)
    gateway.notify_orders(order_id, status)
    return out

Smoke test script

In plain words

A short shell script that places an order through the web tier and checks the three outcomes: success, failure and late success.

The problem it solves

Unit tests prove each service alone; they do not prove that the pieces are wired together.

What it does

  • Seeds one product through the catalog API, then posts orders with VPAs ending in okbank, okfail and okslow.
  • Waits three seconds, then checks that the slow order became paid.
  • Exit code is non-zero on any failure, so CI and the post-deploy step reuse it by changing BASE.

scripts/smoke.sh

bashscripts/smoke.sh
#!/usr/bin/env bash
set -euo pipefail
BASE="${BASE:-http://localhost:8080}"
H=(-H "X-User-Id: smoke" -H "Content-Type: application/json")

curl -fsS "${H[@]}" -X POST "$BASE/api/catalog/products" \
  -d '{"sku":"SMOKE","name":"Smoke item","price_paise":10000,"stock":100}' >/dev/null || true

order() {
  curl -sS "${H[@]}" -H "Idempotency-Key: $(uuidgen)" -X POST "$BASE/api/orders/orders" \
    -d "{\"items\":[{\"sku\":\"SMOKE\",\"qty\":1}],\"vpa\":\"$1\"}" -w ' HTTP %{http_code}\n'
}

ok=$(order a@okbank);   echo "$ok";   grep -q '"paid"' <<<"$ok"
bad=$(order a@okfail);  echo "$bad";  grep -q 'HTTP 402' <<<"$bad"
slow=$(order a@okslow); echo "$slow"; grep -q '"pending"' <<<"$slow"
id=$(sed -E 's/.*"id":([0-9]+).*/\1/' <<<"$slow")
sleep 3
final=$(curl -fsS "${H[@]}" "$BASE/api/orders/orders/$id"); echo "$final"
grep -q '"paid"' <<<"$final"
echo "smoke ok"

In plain words

The problem it solves

What it does

  • readinessProbe uses /readyz (dependency check). livenessProbe uses /healthz (process only). startupProbe gives slow starts 30 seconds before liveness applies.

  • topologySpreadConstraints spreads replicas across zones with maxSkew: 1.
  • Security context: non-root UID 10001, read-only root filesystem, no privilege escalation, all capabilities dropped, seccomp RuntimeDefault.
  • Configuration from a ConfigMap (plain values) and a Secret (database URL) through envFrom.

10.4

Why those probe choices matter

In plain words

Readiness decides whether a pod receives traffic. Liveness decides whether it is restarted. They must check different things.

The problem it solves

If liveness checks the database, a database outage restarts every pod at once, making recovery slower. If readiness checks nothing, pods receive traffic they cannot serve.

What it does

  • Readiness (/readyz) fails when the database or Redis is unreachable: pods leave the Service but keep running, then return by themselves.
  • Liveness (/healthz) only proves the process answers; failure means restart.
  • maxUnavailable: 0 with maxSurge: 1 keeps full capacity during a rollout.
  • The preStop sleep of 5 seconds lets endpoint removal propagate before SIGTERM, avoiding dropped requests; uvicorn drains on SIGTERM within the 30 second grace.
Check yourself
What happens to a pod when the database is down?

Readiness fails, so it stops receiving traffic; liveness still passes, so it is not restarted.

11.1

HorizontalPodAutoscaler

In plain words

The HPA adds or removes pod replicas when average CPU use crosses a target.

The problem it solves

A fixed replica count is either too low on sale day or wasteful at night.

What it does

  • Targets 70 percent of the CPU request. With a 100m request, scaling starts when average use passes 70m.
  • Bounds are set per overlay: dev 1 to 2, staging 2 to 4, prod 3 to 9.
  • Formula: desired = ceil(current x currentUsage / target). For 3 pods at 140m average against a 70m target, desired = ceil(3 x 140 / 70) = 6.
  • Requires metrics-server (an EKS add-on or Helm chart). Scale-down waits 5 minutes by default (stabilization) to avoid flapping.

In plain words

A PDB tells Kubernetes how many pods of an app may be down at once during voluntary disruptions like node drains.

The problem it solves

12.5

Capacity arithmetic for the prod nodes

In plain words

Check that the requests of all pods fit on three nodes with room for a node loss and for the platform pods.

The problem it solves

Requests that add up to more than the nodes can offer leave pods Pending; requests that are far too small waste nothing but hide risk.

What it does

  • An m6i.large has 2 vCPU and 8 GiB; allocatable for pods is lower (system reservations, around 1.9 vCPU and about 7 GiB; check kubectl describe node).
  • Assume each service has an HPA with the same bounds (the base file shows two; the rest follow the same pattern). Prod requests per replica set: catalog 3 x 100m, cart 3 x 100m, orders 3 x 200m, payments 3 x 200m, web 3 x 50m = 3 x 650m = 1,950m CPU in total at minimum replicas. If every service scaled to its HPA maximum of 9: 9 x 650m = 5,850m.
  • Three nodes provide about 3 x 1,900m = 5,700m allocatable, and platform pods (CoreDNS, Argo CD, Prometheus, External Secrets) take roughly 1,500m. At the HPA maximum the total is 5,850m + 1,500m = 7,350m, which needs ceil(7,350 / 1,900) = 4 nodes, so the autoscaler must add one (node group max is 6).
  • Losing one node (N+1): 1,950m + 1,500m = 3,450m of requests on 2 nodes (3,800m) still fits, which is why the minimum node count is 3.

Verify the numbers

12.6

Prove that overlays differ only where allowed

In plain words

Render all three overlays and compare them with a script that lists the fields that differ.

The problem it solves

Silent drift, such as a probe removed only in prod, is the cause of many "works in staging" incidents.

What it does

  • The script loads each rendered YAML, strips allowed fields (replicas, image, resources, host, labels) and compares what remains.
  • Any difference outside the allowed list fails the build.
  • Run it on every pull request that touches deploy/.

drift_check.py

pythonscripts/drift_check.py
import subprocess
import sys

import yaml

ALLOWED = {"replicas", "image", "resources", "host", "minReplicas", "maxReplicas",
           "minAvailable", "maxUnavailable", "value", "key", "name"}


def render(env: str) -> dict:
    out = subprocess.run(["kubectl", "kustomize", f"deploy/overlays/{env}"],
                         check=True, capture_output=True, text=True).stdout
    return {(d["kind"], d["metadata"]["name"]): d for d in yaml.safe_load_all(out) if d}


def strip(node):
    if isinstance(node, dict):
        return {k: strip(v) for k, v in node.items() if k not in ALLOWED}
    if isinstance(node, list):
        return [strip(v) for v in node]
    return node


def main() -> int:
    envs = {e: render(e) for e in ("staging", "prod")}
    bad = []
    for key, prod_doc in envs["prod"].items():
        stage_doc = envs["staging"].get(key)
        if stage_doc is None:
            bad.append(f"{key} exists only in prod")
        elif strip(prod_doc) != strip(stage_doc):
            bad.append(f"{key} differs outside allowed fields")
    if any(k[1] == "upi-mock" for k in envs["prod"]):
        bad.append("upi-mock must not exist in prod")
    for line in bad:
        print("DRIFT:", line)
    return 1 if bad else 0


if __name__ == "__main__":
    sys.exit(main())
Note

The metadata hash of the ConfigMap name differs between environments; the allowed set includes name for that reason. Tighten the script in your own repository.

13.1

Pipeline overview

In plain words

Three workflows: ci.yml on pull requests, build.yml on merges to main, and promote.yml for staging and prod.

The problem it solves

One giant workflow mixes untrusted pull request code with push credentials, which is both slow and unsafe.

What it does

  • build.yml: runs only on main; assumes the OIDC role, builds, scans, pushes, commits the new tag to the dev overlay.

Build, scan and push with OIDC

In plain words

On a merge to main, the workflow asks GitHub for an ID token, exchanges it for temporary AWS credentials and pushes images tagged with the commit SHA.

The problem it solves

Long-lived access keys in repository secrets are the most common cloud credential leak from CI.

What it does

  • permissions: id-token: write lets the job request the token. aws-actions/configure-aws-credentials with role-to-assume does the exchange.
  • Build uses Buildx with GitHub cache (cache-from: type=gha).
  • Trivy scans each image and fails on HIGH or CRITICAL fixed vulnerabilities, before push.
  • The image tag is sha- plus the full commit SHA. ECR tags are immutable, so re-running the push for the same commit fails with a tag-exists error; make the push step skip when aws ecr describe-images already finds the tag.

13.4

Tags: full SHA versus short SHA

In plain words

A tag must be unique and traceable to a commit. The full 40 character SHA is unambiguous; the short form is easier to read.

The problem it solves

Short SHAs can collide in large repositories, and an ambiguous tag makes the audit trail unclear.

What it does

  • The workflow above uses the full SHA in the tag. For humans, dashboards and release notes show the first 7 characters.
  • A release tag such as v1.4.0 is a Git tag only; images are never re-tagged. This keeps the digest the same from dev to prod.
  • Argo CD shows the tag per Deployment, so any pod can be traced back to a commit in one lookup.
  • For stricter pinning use the digest (@sha256:...) in the overlay; the build job can output it.

In plain words

The declarative Jenkinsfile

In plain words

The problem it solves

What it does

pipeline {
  agent {
    kubernetes {
      yamlFile 'ci/jenkins-agent.yaml'
      defaultContainer 'python'
    }
  }
  options {
    timeout(time: 30, unit: 'MINUTES')
    disableConcurrentBuilds(abortPrevious: true)
    buildDiscarder(logRotator(numToKeepStr: '30'))
  }
  environment {
    REGISTRY = '111111111111.dkr.ecr.ap-south-1.amazonaws.com'
    TAG      = "sha-${env.GIT_COMMIT}"
  }
  stages {
    stage('Test') {
      parallel {
        stage('catalog')  { steps { sh 'pip install -r services/catalog/requirements.txt  && cd services/catalog  && python -m pytest -q' } }
        stage('cart')     { steps { sh 'pip install -r services/cart/requirements.txt     && cd services/cart     && python -m pytest -q' } }
        stage('orders')   { steps { sh 'pip install -r services/orders/requirements.txt   && cd services/orders   && python -m pytest -q' } }
        stage('payments') { steps { sh 'pip install -r services/payments/requirements.txt && cd services/payments && python -m pytest -q' } }
      }
    }
    stage('Build and push') {
      when { branch 'main' }
      steps {
        container('kaniko') {
          sh '''
            for svc in catalog cart orders payments; do
              /kaniko/executor --context services/$svc --dockerfile services/$svc/Dockerfile \
                --destination $REGISTRY/shop/$svc:$TAG --no-push-metadata=false
            done
          '''
        }
      }
    }
    stage('Scan') {
      when { branch 'main' }
      steps {
        container('trivy') {
          sh 'for svc in catalog cart orders payments; do trivy image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 $REGISTRY/shop/$svc:$TAG; done'
        }
      }
    }
    stage('Bump dev overlay') {
      when { branch 'main' }
      steps { sh 'python scripts/bump_overlay.py dev $TAG' }
    }
    stage('Approve prod') {
      when { tag 'v*' }
      steps { input message: 'Promote to production?', submitter: 'shop-release' }
    }

Rolling update behaviour and what can go wrong

In plain words

A rolling update replaces pods gradually. With maxSurge 1 and maxUnavailable 0 a new pod must be Ready before an old one is removed.

A bad version with a passing readiness probe still receives traffic; a bad probe blocks the rollout and looks like a hang.

  • minReadySeconds: 10 makes a pod stay Ready for 10 seconds before the next replaced one, catching early crashes.
  • Argo CD shows the Application as Progressing then Degraded when a Deployment fails.

In plain words

EKS upgrade runbook - plan

In plain words

EKS upgrades one minor version at a time: control plane first, then add-ons, then nodes. Staging goes first.

The problem it solves

An unplanned upgrade breaks workloads that used removed APIs or older add-on versions, and cannot be undone: the control plane does not downgrade.

What it does

  • Read the release notes of the target version and the EKS upgrade guide; check the EKS Upgrade Insights and kubectl get --raw /metrics for deprecated API usage (or tools such as pluto and kubent).

  • Window: low traffic, staff available, no release in progress, a rollback plan for workloads (not for the control plane).

  • Version skew: nodes may lag the control plane by a small number of minor versions (check the current Kubernetes version skew policy).

In plain words

16.4

The checkout SLO and its error budget

In plain words

An SLO is a target for a user-visible measure over a period. The error budget is the amount of failure the target still allows.

The problem it solves

"As reliable as possible" has no end and ignores cost. A number lets the team decide between shipping features and fixing reliability.

What it does

  • SLO: 99.9 percent of checkout requests succeed over 30 days.
  • Budget fraction: 1 - 0.999 = 0.001, which is 0.1 percent of requests.
  • In time: 30 days x 24 hours x 60 minutes = 43,200 minutes; 43,200 x 0.001 = 43.2 minutes of total outage equivalent.
  • In requests: at 20,000 orders a day plus retries, 600,000 order attempts a month; budget = 600 failed orders (600,000 x 0.001).
  • Policy: if more than 50 percent of the budget is gone, pause risky releases; if gone, only reliability work ships.

16.5

Multi-window burn-rate alerts

In plain words

A burn rate is how fast the budget is being spent compared with the pace that would exactly use it up in 30 days. Burn rate 1 means just on target.

The problem it solves

An alert on "error rate above 0.1 percent for 5 minutes" fires on harmless blips and misses slow leaks. Multi-window burn-rate alerts page only when a meaningful amount of budget is at stake.

What it does

  • Page (fast): burn rate 14.4 over 1 hour and over 5 minutes. 14.4 x 1 hour of 720 hours = 2 percent of the budget in one hour. Error ratio threshold 14.4 x 0.001 = 0.0144.
  • Page (slower): burn rate 6 over 6 hours and 30 minutes: 5 percent of the budget. Threshold 0.006.
  • Ticket: burn rate 3 over 24 hours (10 percent) and burn rate 1 over 3 days (10 percent). Thresholds 0.003 and 0.001.
  • The short window must also exceed the threshold, so the alert resets quickly after a fix.
  • This is the pattern from the Google SRE workbook; the Monitoring folder shows the general version.

Threat model of the payment path

In plain words

List who could attack the payment flow, how, and which control stops it. Use STRIDE headings as a prompt.

The problem it solves

Payments are the highest-value target; a gap here is a financial loss.

What it does

17.4

Load test design with k6

In plain words

k6 is a load testing tool that runs JavaScript scenarios. It sends the same journey as a shopper: browse, add to cart, check out.

The problem it solves

Guesses about capacity fail on the first big sale. A test shows where the system bends before real customers do.

What it does

  • Target from the capacity estimate: 25 requests per second normal, 75 with headroom. In a closed model the virtual users needed follow Little's law: users = rate x time per iteration. At 2.5 orders per second (3x the 0.83 busy-hour rate) and 6 seconds per full journey (about 30 requests with think time) that is 2.5 x 6 = 15 users.
  • Scenario types: smoke (1 user, 1 minute), load (target for 10 minutes), stress (increase until errors), soak (target for hours to find leaks).
  • Thresholds turn the test into a pass/fail gate: http_req_failed < 0.001 and http_req_duration p(95) < 800.
  • Always test staging with the mock gateway, never prod and never a real payment provider.

17.5

The k6 script

In plain words

One scenario with a ramping arrival rate, a journey function and thresholds.

The problem it solves

A constant-VU test hides latency problems: when the server slows, fewer requests are sent, so the test looks better than reality (coordinated omission). An arrival-rate executor keeps sending at the planned rate.

What it does

  • ramping-arrival-rate goes from 1 to 2.5 iterations per second in 2 minutes, holds for 10, and ramps down.
  • Each iteration lists products, adds one to the cart and posts an order with a random VPA suffix mix: 90 percent okbank, 5 percent okfail, 5 percent okslow.
  • check counts expected statuses: 201 for paid, 402 for the failing VPA.
  • Run with k6 run -e BASE=https://shop-staging.example.com loadtest/checkout.js.

loadtest/checkout.js

javascriptloadtest/checkout.js
import http from 'k6/http';
import { check, sleep } from 'k6';
import { uuidv4 } from 'https://jslib.k6.io/k6-utils/1.4.0/index.js';

const BASE = __ENV.BASE || 'http://localhost:8080';

export const options = {
  scenarios: {
    checkout: {
      executor: 'ramping-arrival-rate',
      startRate: 1, timeUnit: '1s',
      preAllocatedVUs: 30, maxVUs: 100,
      stages: [
        { target: 2.5, duration: '2m' },
        { target: 2.5, duration: '10m' },
        { target: 0, duration: '1m' },
      ],
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.01'],
    'http_req_duration{name:order}': ['p(95)<800'],
  },
};

function pickVpa() {
  const r = Math.random();
  if (r < 0.90) return 'load@okbank';
  if (r < 0.95) return 'load@okfail';
  return 'load@okslow';
}

export default function () {
  const user = `u${__VU}-${__ITER}`;
  const h = { headers: { 'X-User-Id': user, 'Content-Type': 'application/json' } };

  http.get(`${BASE}/api/catalog/products`, h);
  http.put(`${BASE}/api/cart/cart/items/SMOKE`, JSON.stringify({ qty: 1 }), h);
  sleep(1);

  const res = http.post(`${BASE}/api/orders/orders`,
    JSON.stringify({ items: [{ sku: 'SMOKE', qty: 1 }], vpa: pickVpa() }),
    { headers: { ...h.headers, 'Idempotency-Key': uuidv4() }, tags: { name: 'order' }, responseCallback: http.expectedStatuses(201, 402) });
  check(res, { 'order accepted or declined': (r) => r.status === 201 || r.status === 402 });
}

Database trouble and payment inconsistencies are rare, high-impact and unfamiliar to most responders.

What it does

  • RDS saturation: check DatabaseConnections against the limit, top queries in Performance Insights, long transactions; mitigate by reducing HPA max (fewer connections), killing a runaway query, or scaling the instance class (a short failover in multi-AZ). Total connections = pods x pool size (up to 10), for example 9 pods x 10 = 90 per service.
  • Stuck PENDING: a CronJob or the runbook query lists payments older than 15 minutes and asks the gateway for the status by reference, then calls the same settlement code path as the webhook.
  • Stock leak: reservations with no order after 15 minutes are released by a reconciliation query (see the orders chapter).
  • Every manual data change is done by a second person watching, inside a transaction, with the SQL saved in the incident ticket.

Reconciliation query

sqldocs/runbooks/stuck-payments.sql
-- run read-only first, then settle each row through the service, not by UPDATE
SELECT p.id, p.order_id, p.amount_paise, p.gateway_ref, p.status
FROM payments p
WHERE p.status = 'PENDING'
  AND p.id IN (SELECT id FROM payments ORDER BY id DESC LIMIT 5000)
ORDER BY p.id;
Note

The sample table has no timestamp column. Add created_at in a migration (expand step) before the 15 minute filter can be written. This is a good first exercise.

18.3

Incident drills (game days)

In plain words

A drill breaks something on purpose in staging and the on-call person fixes it using only the runbooks.

The problem it solves

The first time you use a runbook should not be during a real incident. Untested runbooks have wrong commands.

What it does

  • Schedule one drill per month, 60 minutes, in staging, with a facilitator who knows the answer and a person who does not.
  • Scenarios: bad release (rollback), gateway down (mock returns 500, expect PENDING and an alert), database failover (RDS reboot with failover), node loss (terminate an instance, watch PDB and HPA), expired certificate or secret rotation.
  • Record time to detect, time to mitigate, and every unclear step; fix the runbook the same day.
  • After a real incident write a blameless post-mortem: timeline, impact in budget minutes, causes, actions with owners.

18.4

Disaster recovery targets and test

In plain words

Disaster recovery (DR) is getting the Shop back after losing a database, a zone or a whole region. RPO is how much data you can lose; RTO is how long you can be down.

The problem it solves

Backups that were never restored are hopes, not backups.

What it does

  • Targets: RPO 5 minutes, RTO 60 minutes (stated in the requirements).
  • Layers: multi-AZ RDS covers an instance or zone failure in about 1 to 2 minutes without data loss. Automated backups and point-in-time restore cover bad data or deletion: RPO about 5 minutes. A cross-region copy of snapshots (and a Terraform-ready second region) covers a region loss: RPO is then the snapshot interval, which is larger than 5 minutes; accept it or add a cross-region read replica.
  • Quarterly restore test: restore the prod database to a new instance at a point in time, run the smoke checks against it, record the time.
  • Time budget for a point-in-time restore: decision 5, restore 15 to 30, repoint secrets 5, restart 5, verify 10 = about 40 to 55 minutes against the 60 minute RTO; there is little slack.
  • Everything else is rebuilt from Git: Terraform for infrastructure, Argo CD for workloads. Redis carts are disposable.

18.6

The same Shop on Azure (AKS)

In plain words

The design does not change; each AWS piece has an Azure counterpart. Containers, Kustomize overlays, probes, policies and metrics stay identical.

The problem it solves

Customers and acquisitions bring a second cloud. Knowing which parts are portable shows how much really has to change.

What it does

  • Compute: AKS replaces EKS; node pools replace managed node groups; the upgrade flow is the same idea (control plane, then node pools), with surge upgrades on pools.
  • Data: Azure Database for PostgreSQL flexible server with zone-redundant HA; Azure Cache for Redis (check the current product and naming).
  • Registry: Azure Container Registry. CI auth: GitHub OIDC federated credential on a Microsoft Entra application, no secrets; AKS pulls from ACR with its managed identity.
  • Secrets: Key Vault with the External Secrets operator and Azure Workload Identity (the AKS counterpart of IRSA).
  • Ingress: Application Gateway for Containers or the NGINX ingress with a managed certificate; check which your platform standard is.
  • Terraform uses the azurerm provider (version 5.12.0 at the time of writing) with the same module split: network, aks, database, cache, registry, identity. See the Azure folder (11) for details.

18.7

The same Shop on GCP (GKE)

In plain words

Again the application and Kustomize base are unchanged; the infrastructure modules and identity wiring change.

The problem it solves

Moving clouds should mean rewriting modules and overlays, not the application.

What it does

  • Compute: GKE (Standard with node pools, or Autopilot where you pay per pod request; the HPA and PDB behave the same, but Autopilot enforces its own resource rules, check the current docs).
  • Data: Cloud SQL for PostgreSQL with high availability; Memorystore for Redis.
  • Registry: Artifact Registry. CI auth: GitHub OIDC to Workload Identity Federation with a service account limited to Artifact Registry writer.
  • Secrets: Secret Manager through the External Secrets operator and GKE Workload Identity.
  • Ingress: the GKE Gateway or Ingress controller creates a Google Cloud load balancer; managed certificates for HTTPS.
  • Terraform uses the google provider (8.9.0 at the time of writing). See the GCP folder (12). NetworkPolicy is enforced on GKE when network policy or Dataplane V2 is enabled.
  • Portable pieces: containers, probes, HPA, PDB, Prometheus rules, Grafana JSON, the k6 test. Cloud-specific: Terraform modules, ingress annotations, identity wiring, the secret store object.
