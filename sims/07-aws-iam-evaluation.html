        Evaluation order used here (from the AWS documentation)

        1. Default is an implicit deny. Scan every applicable policy for an explicit Deny; one match gives a final Deny.
        2. SCP (principal's account): needs an Allow, otherwise implicit deny. It limits; it never grants.
        3. Same account: a resource-based policy that names the IAM user, or the role session, directly grants on its own, even if identity policy, boundary or session policy would implicitly deny. A resource policy that names the role ARN or the account is still limited by the boundary and session policy.
        4. Identity-based policy needs an Allow (or an Allow from the resource policy as above). Permissions boundary needs an Allow. Session policy (role sessions only, if one was passed) needs an Allow. Boundaries and session policies limit; they never grant.
        5. Cross-account: two evaluations. The principal's account needs identity-based Allow within its SCP, boundary and session limits; the resource's account needs a resource-based Allow naming the principal. Both must Allow.

        Source: AWS IAM User Guide, “Policy evaluation logic”, “How AWS enforcement code logic evaluates requests…”, “Policy evaluation for requests within a single account” and “Cross-account policy evaluation logic”.

        Simplifications

        • Policy grammar is reduced: Effect, Action, Resource, Principal (resource policy only) and Condition. NotAction, NotResource, NotPrincipal, policy variables and multi-value set operators are not supported (such statements are ignored with a warning).
        • Condition operators: StringEquals, StringNotEquals, StringLike, StringNotLike, IpAddress, NotIpAddress (IPv4 only). Keys: aws:SourceIp, aws:PrincipalAccount, aws:PrincipalTag/<key>. A missing key makes positive operators false and negated operators true.
        • Resource control policies (RCPs), VPC endpoint policies, ACLs, KMS key policies, role trust policies and service-specific rules are not modelled. SCPs are modelled for the principal's account only. One policy per layer.
        • Principal "*" in a resource policy is honoured for Deny statements only; a public Allow is ignored with a warning. The account root principal is treated like a role ARN (limited by boundary and session policy).
        • The explicit-Deny layer is a stand-alone list of Deny statements applied in the deny scan, standing in for a Deny written in any policy. Deny statements typed into the other layers are also found by the scan.
        • The root user, anonymous requests and the authentication step are not covered. The account IDs, ARNs and addresses are examples.
