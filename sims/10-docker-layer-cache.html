The documented rules

  • Each instruction is checked against cached layers built from the same parent. If none matches, that layer is rebuilt.
  • Once a layer changes, all downstream layers have to be rebuilt as well.
  • For RUN, the cache key is the command string; the command is not re-run to see if its output would differ.
  • For COPY and ADD, the cache key includes a checksum of the copied files' contents (modification times are ignored).
  • Order from least to most frequently changing: base, tooling, dependency manifest, install, source, build.

Simplifications

  • One Node.js example Dockerfile. Durations and sizes are illustrative example numbers, not measurements; real times depend on network, hardware and package set.
  • Time on a cache hit is shown as 0.0 s (real hits cost a little). Only the changes offered here are modelled: no ARG/ENV changes, build secrets, .dockerignore effects, ADD from URL, or --no-cache / --pull.
  • A FROM tag such as node:20 can move upstream; the simulator assumes the same image is resolved. A RUN that fetches changing data (for example apt-get update) stays cached until a layer above it changes.
  • In the naive order, COPY . . also copies package.json, so a dependency change invalidates it. Layer and cache behaviour follows classic and BuildKit builds; export and storage details are not modelled.
