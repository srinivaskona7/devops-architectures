Section 1 of 14

Logging architecture and structured logs

7 concepts · about 45 minutes

Logs are the detailed record of what happened. Once you run more than a few servers or pods, reading files on each machine stops working, so you ship them to one searchable place.

Goals
  • Describe the stages of a centralised logging pipeline
  • Write structured JSON logs with consistent fields
  • Decide where to collect logs on Kubernetes and AWS
1.1

Why centralise logs

In plain words

Centralised logging copies the logs of every host, pod and service into one system where you can search, filter and graph them together.

The problem it solves

Pods are deleted and replaced, taking their local logs with them. Debugging one request that crossed six services would need six shell sessions.

What it does

  • Logs survive the death of the pod or node that wrote them.
  • One query can follow a request ID across services.
  • Access control, retention and alerting can be applied in one place.
1.2

The ELK stack and the Elastic Stack

In plain words

ELK means Elasticsearch (store and search), Logstash (process) and Kibana (view). Beats and Elastic Agent were added to collect data, so the whole family is now called the Elastic Stack.

The problem it solves

Each job in the pipeline is different. Searching terabytes needs a distributed engine, parsing needs a flexible processor, and collection needs a very light agent.

What it does

  • Elasticsearch: distributed search and analytics engine built on Apache Lucene.
  • Logstash: server-side pipeline for heavy parsing and routing.
  • Kibana: web interface for search, dashboards and alerts.
  • Beats / Elastic Agent: lightweight shippers running on each host.
1.3

Structured logging

In plain words

A structured log line is data, not prose: usually one JSON object per line with named fields such as level, service, trace_id and message.

The problem it solves

Free text such as User bob failed login from 10.1.2.3 after 3 tries must be parsed with fragile regular expressions, and any wording change breaks the parser.

What it does

  • JSON lines can be indexed field by field with no parsing step.
  • Fields enable exact filters (level: error, http.status >= 500) and aggregations.
  • Use the same names in every service. Elastic Common Schema (ECS) is a ready-made naming standard.

Python example

pythonstructured_logging.py
import json, logging, sys, time

class JsonFormatter(logging.Formatter):
    def format(self, record):
        doc = {
            "@timestamp": time.strftime("%Y-%m-%dT%H:%M:%S", time.gmtime(record.created)) + "Z",
            "log.level": record.levelname.lower(),
            "message": record.getMessage(),
            "service.name": "checkout",
        }
        doc.update(getattr(record, "fields", {}))
        return json.dumps(doc)

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(JsonFormatter())
log = logging.getLogger("checkout")
log.addHandler(handler)
log.setLevel(logging.INFO)
log.info("login failed", extra={"fields": {"user.name": "bob", "client.ip": "10.1.2.3", "event.outcome": "failure"}})
1.4

Elastic Common Schema

In plain words

ECS is a published list of standard field names, such as @timestamp, log.level, host.name, http.response.status_code, trace.id and kubernetes.pod.name.

The problem it solves

If one team logs status and another httpCode, a single dashboard cannot cover both.

What it does

  • Field names use dotted paths, which Elasticsearch treats as nested objects.
  • Beats, Elastic Agent integrations and ingest pipelines emit ECS fields.
  • OpenTelemetry semantic conventions are being aligned with ECS; check the current docs for details.
Check yourself
Why use ECS names even for your own services?

Dashboards, alerts and detection rules written once work for every source that follows the schema.

1.5

What to log, and what not to

In plain words

Log events that explain behaviour: requests, errors, state changes, security decisions. Do not log secrets or personal data.

The problem it solves

Too little logging leaves incidents unexplained; too much costs money and hides the signal. Leaked tokens in logs become a security incident.

What it does

  • Levels: error for failures needing attention, warn for recoverable problems, info for normal milestones, debug only when needed.
  • Always include timestamp, service, version, environment, request or trace ID.
  • Never log passwords, tokens, full card numbers or personal data. Mask them in the application or in the pipeline.
  • One event per line. Multi-line stack traces should go inside a single JSON field.
1.6

Container logging on Kubernetes

In plain words

Containers should write logs to stdout and stderr. The container runtime saves them as files on the node, and a collector reads those files.

The problem it solves

Writing log files inside a container fills its writable layer and the files vanish when the pod does.

What it does

  • On the node, files appear under /var/log/pods/<namespace>_<pod>_<uid>/<container>/ with symlinks in /var/log/containers/.
  • The kubelet rotates them (containerLogMaxSize, default 10Mi, and containerLogMaxFiles, default 5).
  • A DaemonSet collector tails these files and adds pod metadata (namespace, labels).
  • kubectl logs reads the same files, so it only shows recent data.

Look at the node files

bashWhere the logs live
kubectl get pods -n shop -o wide
kubectl logs deploy/checkout -n shop --tail=5
# on a node (via SSH or a debug pod)
ls /var/log/containers | head
tail -n 2 /var/log/containers/checkout-*.log
1.7

Collection patterns on Kubernetes and AWS

In plain words

There are four common ways to get logs out: a node-level agent, a sidecar, direct push from the app, and a cloud service such as CloudWatch Logs.

The problem it solves

The right pattern depends on cost, isolation and how much control you need.

What it does

  • Node agent (DaemonSet): one collector per node. Cheapest and the default.
  • Sidecar: a collector per pod. Needed when the app writes files you cannot change, at the price of more resources.
  • Direct push: the app sends to Logstash or Elasticsearch. Couples the app to the logging backend; avoid unless required.
  • AWS: EKS can send control plane logs to CloudWatch Logs; Fluent Bit or Firehose can forward CloudWatch to Elasticsearch or OpenSearch.

Section 2 of 14

Elasticsearch core - index, shards and mappings

7 concepts · about 55 minutes

Elasticsearch is a distributed document store that is built for search. This section covers how it stores and spreads your data.

Goals
  • Explain the inverted index and why search is fast
  • Choose primary and replica shard counts
  • Define mappings and avoid mapping explosions
2.1

Documents and indices

In plain words

A document is a JSON object. An index is a named collection of documents, similar to a table. A log event is one document.

The problem it solves

You need to find a few events among billions by any field or by words in the text.

What it does

  • Each document gets an _id and is stored in one index.
  • Fields have types (keyword, text, date, long, ip and so on).
  • Queries are sent over a REST API in JSON.

Index and search a document

textDev Tools console
PUT logs-demo/_doc/1
{ "@timestamp": "2026-10-31T12:00:00Z", "service.name": "checkout", "log.level": "error", "message": "payment timeout after 3000 ms" }

GET logs-demo/_search
{ "query": { "match": { "message": "timeout" } } }
2.2

The inverted index

In plain words

For each word, Lucene stores the list of documents that contain it. Looking up a word is a quick dictionary lookup, not a scan of every document.

The problem it solves

Searching text by reading every document is far too slow for large data.

What it does

  • Text is cut into terms by an analyzer, then each term points to a postings list of document IDs.
  • Multiple terms are combined by intersecting their lists.
  • Fields also get doc values, a column-oriented store used for sorting and aggregations.
  • Segments are immutable files; deletes are marks that are removed during merges.
Check yourself
Query for payment and timeout returns which docs?

Intersect lists for payment (1, 2) and timeout (1), giving doc 1 only.

2.3

Segments, refresh and near real-time

In plain words

New documents go to an in-memory buffer and the translog. A refresh (default every second) makes them searchable by writing a new small segment. A flush later persists segments to disk.

The problem it solves

Writing each event straight into an optimised on-disk structure would be very slow.

What it does

  • Search is near real-time: a new document is visible within about a second.
  • The translog guarantees durability after a crash.
  • Background merges combine small segments into larger ones.
  • For bulk loading set a longer refresh_interval (for example 30s) to reduce overhead.
2.4

Shards and replicas

In plain words

An index is split into primary shards, each a complete Lucene index. Each primary can have replica shards, copies on other nodes.

The problem it solves

One machine cannot hold or search all your data, and one disk failure must not lose it.

What it does

  • Primaries spread data and indexing work across nodes. Replicas give high availability and extra read capacity.
  • A replica is never on the same node as its primary. With 1 replica you can lose one node without losing data.
  • Primary count is fixed when an index is created (changing it needs split, shrink or reindex). Replica count can change any time.
  • Each document goes to a shard by hash of its routing value (default the _id).

Settings and checks

json
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  }
}

2.5

Choosing the number of shards

In plain words

Shards are the unit of scaling, but each one has overhead. The aim is a moderate number of shards, each between roughly 10 GB and 50 GB.

The problem it solves

Too many small shards waste memory and slow the cluster. A few huge shards are slow to recover and move.

What it does

  • Rule of thumb from Elastic: aim for shard size of 10 to 50 GB, and keep fewer than about 20 shards per GB of heap on a node; check the current docs for updated guidance.
  • Worked example: 220 GB of primary data a day and a 50 GB target gives 220 ÷ 50 = 4.4, so use 4 or 5 primaries, or let ILM roll over at 50 GB.
  • A node with a 30 GB heap should hold at most 30 × 20 = 600 shards.
  • Use data streams with rollover instead of picking a shard count per day.

Check the arithmetic

pythonshards.py
daily_primary_gb = 200 * 1.1          # 200 GB raw, about 10 percent index overhead
target_gb = 50
print("primaries per day", round(daily_primary_gb / target_gb, 1))
heap_gb = 30
print("max shards per node", heap_gb * 20)
2.6

Mappings and field types

In plain words

A mapping says what type each field is. text is analysed for full-text search; keyword is stored whole for exact match, sorting and aggregations.

The problem it solves

If Elasticsearch guesses wrong, you cannot aggregate on a field or you waste space indexing it twice.

What it does

  • keyword: IDs, status, service names, hostnames. text: free messages. date, long, double, boolean, ip for the rest.
  • Dynamic mapping creates fields from the first document; it often maps strings as text plus a .keyword subfield.
  • A field type cannot be changed in place; you must reindex.
  • Setting dynamic: strict rejects unknown fields, while dynamic: false keeps them in _source but does not index them.

Explicit mapping

json
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "@timestamp": { "type": "date" },
      "service": { "properties": { "name": { "type": "keyword" } } },
      "log": { "properties": { "level": { "type": "keyword" } } },
      "message": { "type": "text" },
      "client": { "properties": { "ip": { "type": "ip" } } },
      "http": { "properties": { "response": { "properties": { "status_code": { "type": "short" } } } } },
      "trace": { "properties": { "id": { "type": "keyword" } } }
    }
  }
}
2.7

Mapping explosion and index templates

In plain words

A mapping explosion is when a huge number of different field names (for example one per user ID) makes the cluster state enormous. Index templates apply settings and mappings to new indices automatically.

The problem it solves

Dynamic mapping of unbounded keys can bring a cluster down, and hand-creating each daily index is error-prone.

What it does

  • The limit index.mapping.total_fields.limit defaults to 1000 and protects you; do not simply raise it.
  • Model variable keys as values: {"attribute": "plan", "value": "gold"} instead of {"plan": "gold"} for thousands of keys.
  • Use flattened type for arbitrary key-value maps.
  • Composable templates combine component templates and match index patterns.

Component and index template

json
{
  "index_patterns": ["logs-app-*"],
  "data_stream": {},
  "priority": 200,
  "template": {
    "settings": { "number_of_shards": 1, "number_of_replicas": 1 },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "message": { "type": "text" },
        "labels": { "type": "flattened" }
      }
    }
  }
}

Searching Elasticsearch - analyzers, Query DSL, aggregations and ES|QL

7 concepts · about 55 minutes

Search is where the index pays off. Knowing how analysis and scoring work saves you from queries that look right but return the wrong results.

Goals
  • Explain how analyzers turn text into terms
  • Write bool queries with filters and time ranges
  • Build aggregations and an ES|QL query for log analysis
3.1

Analyzers

In plain words

An analyzer converts text into terms in three steps: character filters clean the text, a tokenizer splits it, and token filters change the tokens (lowercase, remove stop words, stem).

The problem it solves

Users search for Timeout and expect to find timeout; raw text matching would miss it.

What it does

  • The same analyzer runs at index time and, by default, at query time, so terms line up.
  • standard is the default: splits on word boundaries and lowercases.
  • Use _analyze to see the tokens of any text.
  • keyword fields skip analysis entirely.

Try it

textDev Tools
POST _analyze
{ "analyzer": "standard", "text": "Payment TIMEOUT after 3000ms" }
3.2

Query DSL basics

In plain words

Queries are JSON. Full-text queries such as match analyse the input and are scored. Term-level queries such as term and range match exact values.

The problem it solves

Using a match on a keyword or a term on a text field gives surprising results.

What it does

  • match: full-text on text fields. match_phrase: words in order.
  • term / terms: exact value on keyword, numbers, dates, IPs.
  • range: numbers and dates. exists: field present.
  • Results include _score relevance; logs are usually sorted by time instead.
3.3

The bool query and filters

In plain words

A bool query combines clauses: must (and, scored), filter (and, not scored, cached), should (or) and must_not (not).

The problem it solves

Log searches combine a time window, a service and a text condition. Scoring everything wastes CPU.

What it does

  • Put time range and exact conditions in filter so they are cached and skip scoring.
  • Put free-text in must.
  • Use must_not to exclude noise such as health checks.
  • Always bound queries with a @timestamp range.

Example

json
{
  "size": 20,
  "sort": [{ "@timestamp": "desc" }],
  "query": {
    "bool": {
      "filter": [
        { "range": { "@timestamp": { "gte": "now-15m" } } },
        { "term": { "service.name": "checkout" } }
      ],
      "must": [{ "match": { "message": "timeout" } }],
      "must_not": [{ "term": { "url.path": "/health" } }]
    }
  }
}
3.4

Pagination and search_after

In plain words

from plus size pages are limited to 10 000 hits by default. To read more, use search_after with a sort, optionally with a point in time (PIT).

The problem it solves

Deep pagination makes every shard sort and return from + size hits, which hurts the whole cluster.

What it does

  • from/size: fine for the first few pages in a UI.
  • search_after: continue after the last sort values; needs a stable sort (add a tie-breaker field).
  • PIT keeps a consistent view while you page.
  • For exports use tools built for it, not deep paging.

Example

json
{
  "size": 100,
  "pit": { "id": "PASTE_PIT_ID_HERE", "keep_alive": "1m" },
  "sort": [{ "@timestamp": "asc" }, { "_shard_doc": "asc" }],
  "search_after": ["2026-10-31T12:00:00.000Z", 4521]
}
3.5

Aggregations

In plain words

Aggregations compute statistics over matching documents: counts per value (buckets), time histograms, percentiles and sums (metrics).

The problem it solves

Search returns individual documents. Operations need totals such as errors per service per minute.

What it does

  • Bucket aggs group documents: terms, date_histogram, range.
  • Metric aggs calculate numbers: avg, max, percentiles, cardinality.
  • Aggs nest, for example errors per minute per service.
  • They use doc values, so they run on keyword, number and date fields. Set size: 0 to skip returning hits.

Errors per service per minute

json
{
  "size": 0,
  "query": {
    "bool": { "filter": [
      { "range": { "@timestamp": { "gte": "now-1h" } } },
      { "term": { "log.level": "error" } }
    ] }
  },
  "aggs": {
    "per_minute": {
      "date_histogram": { "field": "@timestamp", "fixed_interval": "1m" },
      "aggs": { "by_service": { "terms": { "field": "service.name", "size": 5 } } }
    }
  }
}
3.6

ES|QL

In plain words

ES|QL is a piped query language. You start with FROM, then pass results through commands such as WHERE, STATS, SORT and LIMIT, much like a shell pipeline.

The problem it solves

Query DSL JSON is verbose for analysis tasks, and joins of ideas such as "count by service then sort" take nested JSON.

What it does

  • Runs in Kibana Discover (ES|QL mode), Dev Tools or the _query API.
  • Core commands: FROM, WHERE, EVAL, STATS ... BY, SORT, LIMIT, KEEP, DROP.
  • Time bucketing with BUCKET(@timestamp, 1 minute) (older versions used AUTO_BUCKET).
  • It is evolving fast; check the current docs for supported commands and functions in your version.

Example

textES|QL in Discover or Dev Tools
FROM logs-*
| WHERE @timestamp > NOW() - 1 hour AND log.level == "error"
| STATS errors = COUNT(*) BY service.name
| SORT errors DESC
| LIMIT 5
bashSame query by API
curl -s -u elastic:$ES_PASSWORD -H 'Content-Type: application/json' \
  "$ES_URL/_query?format=txt" -d '{"query":"FROM logs-* | WHERE log.level == \"error\" | STATS errors = COUNT(*) BY service.name | LIMIT 5"}'
3.7

Query performance habits

In plain words

Fast log search comes from a few habits: narrow the time range, search a small set of indices, filter before text, and avoid costly queries.

The problem it solves

One careless wildcard query over a year of data can slow every other user.

What it does

  • Use data streams and time-based indices so Elasticsearch skips indices outside the time range.
  • Avoid leading wildcards (*error), script queries and regexes on large fields.
  • Use keyword for exact matches and filter context for caching.
  • Check slow queries with the search slow log and _search?profile=true; cancel long tasks through the tasks API.

Section 4 of 14

Data streams, ILM, tiers and snapshots

7 concepts · about 55 minutes

Logs arrive forever and become less valuable with age. Lifecycle management moves data to cheaper storage and finally deletes it, automatically.

Goals
  • Use data streams with rollover for append-only logs
  • Write an ILM policy with hot, warm, cold and delete phases
  • Back up with snapshots to S3 and restore them
4.1

Data streams

In plain words

A data stream is a single name you write to and search, backed by hidden time-ordered indices. New documents always go to the newest backing index.

The problem it solves

Hand-managing daily indices and aliases is error-prone, and old indices need to be handled one by one.

What it does

4.2

Index Lifecycle Management

In plain words

ILM is a policy that moves an index through phases (hot, warm, cold, frozen, delete) using conditions on age and size, and runs actions at each step.

The problem it solves

Without lifecycle rules, storage grows until the cluster is full, and queries slow down over ever bigger data.

What it does

  • Hot: actively written. Action rollover creates a new backing index when it reaches a size, document count or age.
  • Warm: no longer written but still searched; shrink, force-merge, move to cheaper nodes.
  • Cold / frozen: rarely searched; may use searchable snapshots.
  • Delete: remove the index.
  • min_age counts from rollover, not from creation.
4.3

Writing an ILM policy

In plain words

A policy is JSON listing phases, when each starts (min_age), and the actions to perform.

The problem it solves

You need a repeatable retention rule, reviewed in Git, matching a business requirement such as "30 days searchable".

What it does

  • Rollover at 50gb primary shard size or 1d, whichever comes first, keeps shards in the target size range.
  • Warm phase after 2 days; set replicas or force-merge to 1 segment to save space.
  • Delete after 30 days.
  • Attach with index.lifecycle.name in the index template.

4.4

Data tiers

In plain words

Nodes can have roles: data_hot, data_warm, data_cold, data_frozen. ILM moves indices between tiers by changing their allocation.

The problem it solves

Fast NVMe disks for everything is expensive, yet old data rarely needs that speed.

What it does

  • Hot: newest data, fast disks, most CPU. Warm: larger, cheaper disks (gp3 on AWS). Cold: even cheaper, or searchable snapshots with a local cache. Frozen: data kept only in object storage (S3) and cached on demand.
  • Example ratios (disk to RAM): hot about 1:30, warm 1:80 and up; check Elastic's sizing guidance for your version.
  • Content tier holds non-time-series data.
4.5

Rollover and shrink in practice

In plain words

Rollover starts a new write index; shrink reduces the number of primary shards of an old index; force merge reduces segments.

The problem it solves

Even with good planning, quiet indices end up with too many tiny shards.

What it does

  • Rollover conditions are evaluated periodically (default every 10 minutes), so indices may slightly pass the limit.
  • Shrink needs all shards on one node and a target shard count that is a factor of the original.
  • Force merge is heavy; run it only on indices no longer written.
  • Check ILM progress with GET <index>/_ilm/explain.

Searchable snapshots

In plain words

The problem it solves

Keeping 90 days of logs on replicated SSD costs several times more than S3.

What it does

Cluster sizing, capacity and cost

7 concepts · about 55 minutes

Most Elasticsearch pain comes from sizing: too little disk, too few nodes for the shard count, or logs that were never worth keeping. The arithmetic is simple when you do it before buying.

Goals
  • Estimate storage from daily ingest, replicas and retention
  • Size node counts and heap using documented rules of thumb
  • Reduce cost with mappings, compression and tiering
5.1

Node roles in a cluster

In plain words

Production clusters separate jobs. Master-eligible nodes manage cluster state, data nodes store and search, ingest nodes run pipelines, and coordinating nodes route requests.

The problem it solves

When one node does everything, a heavy query can starve the master and the whole cluster becomes unstable.

What it does

  • Run exactly 3 dedicated master-eligible nodes (small, e.g. 2-4 vCPU, 8 GB RAM) so a majority survives one failure.
  • Data nodes per tier carry most of the cost.
  • Add dedicated coordinating or ingest nodes only when profiling shows they help.
  • Never set an even number of master-eligible nodes.
5.2

Heap and memory

In plain words

Elasticsearch runs on the JVM. The heap holds caches and cluster state; the rest of RAM is used by the operating system file cache, which Lucene relies on.

The problem it solves

Giving the JVM all the RAM starves the file cache, and too large a heap loses compressed object pointers and suffers long garbage collection.

What it does

  • Set heap to about half of RAM, and no more than about 30 GB (check the current docs for the compressed-pointers threshold).
  • Example: a 64 GB node gets a 30 GB heap and 34 GB for the file cache.
  • Set -Xms and -Xmx equal. Elasticsearch sizes the heap automatically in recent versions; override only with reason.
  • On Kubernetes set container memory limit about 2x the heap.
5.3

Estimating storage

In plain words

Total disk = daily raw volume × index overhead × (1 + replicas) × retention days ÷ target disk fill.

The problem it solves

Disk full is the most common production failure. Elasticsearch stops allocating at the low watermark (85 percent by default) and blocks writes at the flood stage (95 percent).

What it does

  • Index size relative to raw JSON varies from about 0.5 to 1.5 times; measure with your own data (a first estimate of 1.1 is common).
  • Worked example: 200 GB per day raw × 1.1 = 220 GB primary data per day; with 1 replica that is 440 GB per day.
  • 30 days retention: 440 × 30 = 13 200 GB. To keep disks at no more than 85 percent: 13 200 ÷ 0.85 = 15 529 GB of provisioned disk.
  • Split by tier: 7 days hot = 3 080 GB; 23 days warm = 10 120 GB.

Check the numbers

pythonstorage.py

per_day = raw_gb * overhead * (1 + replicas)
total = per_day * days
print("per day", round(per_day), "total", round(total), "provisioned", round(total / fill))
print("hot 7d", round(per_day * 7), "warm 23d", round(per_day * 23))
Check yourself
If you drop to zero replicas on warm, what is the warm storage?

5.4

Sizing the node count

In plain words

Work out nodes from disk per node and the shard budget, then check indexing throughput.

The problem it solves

Buying disk without checking RAM and shard limits gives a cluster that has space but is slow or unstable.

What it does

  • Memory-to-disk ratios (rule of thumb): hot about 1:30, warm about 1:160. Check Elastic's current guidance.
  • Hot example: 3 080 GB ÷ 0.85 = 3 624 GB provisioned. At a 1:30 ratio a 64 GB node serves 64 × 30 = 1 920 GB, so 3 624 ÷ 1 920 = 1.9, which rounds up to 2; use 3 nodes for resilience.
  • Warm example: 10 120 GB ÷ 0.85 = 11 906 GB. At 1:160 a 64 GB node serves 10 240 GB, so you need 2 nodes minimum; use 3.
  • Shard check: 7 days × 5 primary shards × 2 (replica) = 70 hot shards; far below 600 per 30 GB heap.
  • Always load test with your real queries.
5.5

Reducing cost

In plain words

Most savings come from storing less, not from cheaper disks: remove unused fields, shorten retention for noisy logs and move data to cheaper tiers sooner.

The problem it solves

Log volume grows faster than budget. Debug logs from a chatty service can double the bill.

What it does

  • Drop health-check and debug logs at the agent before they leave the node.
  • Disable indexing for fields you never search ("index": false) and avoid duplicate text plus keyword mapping where not needed.
  • Use best_compression codec on warm indices and force-merge to one segment.
  • Use zero replicas on cold data backed by snapshots, searchable snapshots for long retention, and sample verbose logs.
  • Separate retention by data type: security audit 1 year, app info 14 days, debug 3 days.

5.6

Monitoring the cluster

In plain words

Monitor Elasticsearch itself: cluster health, disk, heap, indexing rejections and shard counts.

The problem it solves

A full disk or a growing queue shows up in logs only when it is already an incident.

What it does

  • GET _cluster/health: green (all shards allocated), yellow (replicas missing), red (a primary missing).
  • Watch disk watermarks, JVM heap above 85 percent for long periods, write thread pool rejections and pending tasks.
  • Use Elastic's Stack Monitoring or the Prometheus elasticsearch_exporter.

5.7

Retention policy as a business decision

In plain words

Retention is how long each kind of log stays searchable. It is a trade between cost, legal duty and usefulness.

The problem it solves

"Keep everything forever" is the default when nobody decides, and it is the most expensive choice.

What it does

  • Ask: how far back do incidents get investigated (usually 7 to 30 days)? What do audits or regulations require (often 90 days to 7 years for security and finance)?

  • Document retention per data stream and implement it with ILM.
  • Review quarterly against actual query patterns.

Collectors - Beats, Filebeat, Elastic Agent and Fluent Bit

6.1

Beats family

In plain words

Beats are small single-purpose shippers written in Go: Filebeat (log files), Metricbeat (metrics), Packetbeat (network), Auditbeat (audit and file integrity), Heartbeat (uptime probes).

The problem it solves

Running Logstash or a JVM on every server is too heavy. You need a tiny agent that reads data and forwards it.

What it does

  • Each Beat reads data, adds metadata, and sends to Elasticsearch or Logstash.
  • They remember where they stopped (a registry), so a restart does not lose or repeat data.
  • Beats apply back-pressure: if the output is slow, they slow down reading instead of dropping data.
6.2

In plain words

The problem it solves

Files rotate, grow and are truncated. A naive tail -f loses lines or repeats them.

What it does

  • Input types: filestream (recommended for files, replaces the older log input), container, syslog, tcp, aws-s3, and more.
  • Multi-line settings (parsers) join stack traces to one event.
  • ndjson parser decodes JSON lines into fields.
  • The registry holds the offset and file identity, so rotation is followed correctly.

Storage, scheduling and upgrades

In plain words

Elasticsearch needs fast, persistent volumes, spread over failure zones, and careful maintenance.

The problem it solves

A pod rescheduled to another zone cannot attach its EBS volume, and draining nodes carelessly can take two copies of a shard offline at once.

What it does

  • EBS volumes are zone-bound (WaitForFirstConsumer storage class). Use topology spread or anti-affinity so replicas of a shard live in different zones; set cluster.routing.allocation.awareness.attributes: k8s_node_name,zone through ECK podTemplate and node labels (see the ECK docs).
  • Use a StorageClass with allowVolumeExpansion: true so volumes can grow.
  • Changing the version field triggers a rolling upgrade. ECK waits for cluster health between nodes.
  • Use PodDisruptionBudgets (ECK creates a default) so node drains do not break quorum.
  • After maintenance remember to uncordon nodes, since a cordoned node blocks the scheduling of ES pods.

Securing the Elastic Stack

7 concepts · about 45 minutes

Logs contain tokens, personal data and the details attackers want. An open Elasticsearch has repeatedly been the cause of public data leaks, so security is not optional.

Goals
  • Enable TLS and authentication across nodes, collectors and Kibana
  • Use API keys, roles and audit logging with least privilege

10.1

Threats to a logging platform

In plain words

A logging cluster is a rich target: it stores everything your systems say, it accepts data from many hosts, and it can be searched and deleted through an API.

The problem it solves

Teams often secure applications and forget that the log store holds copies of their secrets and user data.

What it does

  • Exposure: an Elasticsearch port open to the internet without authentication.
  • Data leakage: passwords, tokens and personal data written into logs.
  • Tampering: an attacker with a compromised host deletes or alters logs to hide tracks.
  • Over-broad access: every developer a superuser.
10.2

TLS and authentication by default

In plain words

Since Elasticsearch 8, security is on by default: the first start generates certificates and a password for the elastic user. Transport (between nodes) and HTTP (clients) are encrypted with TLS.

The problem it solves

Plain-text traffic can be read or modified on the network, and unauthenticated access means anyone reachable can read and delete.

What it does

  • xpack.security.enabled: true, xpack.security.transport.ssl and xpack.security.http.ssl are enabled with auto-generated certificates on first start of a self-managed install.
  • ECK manages the CA and per-node certificates for you; you can replace the HTTP certificate with your own (cert-manager).
  • Clients (Filebeat, Kibana, Logstash) must trust the CA: set ssl.certificate_authorities.
  • Never disable security to "make it work"; fix the certificate trust instead.

ELK versus Loki, OpenSearch and CloudWatch Logs

7 concepts · about 45 minutes

There is no best log store, only a best fit. The key differences are what gets indexed, where the data lives, and who runs the thing.

Goals
  • Compare Elasticsearch, Loki, OpenSearch and CloudWatch Logs on index model, cost and query power
  • Choose a log backend for a given workload
  • Plan a migration or a hybrid setup
11.1

Two indexing philosophies

In plain words

Elasticsearch builds a full-text inverted index over the contents of every log line. Loki indexes only labels (like pod, namespace, app) and keeps the log text compressed in chunks, scanning it at query time.

The problem it solves

Indexing every word gives fast arbitrary search, but the index can be as large as the data. Indexing only labels is cheap, but searching for a word in a large time range scans a lot of data.

What it does

  • Elasticsearch: higher CPU, RAM and disk per GB ingested; very fast text search, aggregations and analytics on fields.
  • Loki: low index cost and S3 storage; cheap ingest; queries select streams by labels first, then filter lines (|= "error").
  • Rule of thumb: Elasticsearch storage is roughly the size of raw data or more; Loki's compressed chunks are often several times smaller than raw. Measure with your data.
11.2

Elasticsearch strengths

In plain words

Elasticsearch is a general search and analytics engine. Logs are one use; it also serves security analytics (SIEM), application search and metrics.

The problem it solves

Some teams need rich queries on log fields, such as top 10 users by error count with percentile latency, joined across large datasets.

What it does

  • Powerful aggregations, ES|QL, machine learning anomaly detection (licence dependent), SIEM and APM in the same product.
  • Mature lifecycle tooling: ILM, tiers, searchable snapshots, cross-cluster search.
  • Costs: operating a stateful cluster, shard planning, licence considerations (Elastic licence and SSPL/AGPL options in recent versions; check the current licence terms).
11.3

Loki strengths

In plain words

Loki is a log system from Grafana Labs designed like Prometheus: labels as identity, simple operations, object storage.

The problem it solves

Many teams want logs next to metrics in Grafana at a fraction of the price, and mostly search by service and time.

What it does

  • Same label model as Prometheus, so switching from a metric to the logs of that pod is one click.
  • Stores chunks in S3, GCS or Azure Blob, so retention is cheap; operation is simpler (single binary mode to microservices mode).
  • LogQL supports line filters, parsers (| json, | logfmt) and metric queries (rate, count_over_time).
  • Weak spots: high-cardinality labels destroy performance (do not label by user ID), and heavy full-text over long ranges is slow.

11.4

OpenSearch

In plain words

OpenSearch is a community-driven fork of Elasticsearch 7.10 and Kibana, created by AWS and others under the Apache 2.0 licence. Amazon OpenSearch Service is the managed AWS offering.

The problem it solves

After Elastic changed its licence in 2021, AWS and others wanted a permissively licensed engine; AWS customers also wanted a managed service integrated with IAM and VPC.

What it does

  • API and concepts are similar to older Elasticsearch: indices, shards, query DSL, aggregations. Dashboards replaces Kibana.
  • Built-in plugins for security, alerting, anomaly detection, ISM (Index State Management, similar to ILM) and SQL/PPL queries.
  • Managed service: domains with data nodes, dedicated masters, UltraWarm and cold storage tiers, Serverless option; integrates with IAM, CloudWatch Logs subscription and Firehose.
  • Divergence: newer Elasticsearch features (ES|QL, Elastic Agent, newer Lens) are not in OpenSearch, and client libraries are separate.
11.5

CloudWatch Logs

In plain words

CloudWatch Logs is AWS's native log service. Services like Lambda, ECS, RDS and EKS control plane write to it with no setup.

The problem it solves

Running your own log cluster for a handful of AWS-managed services is overkill.

What it does

Most Elasticsearch trouble comes from a few causes: too many shards, uneven shards, heap pressure and slow disks. This section shows how to see each one and what to do.

12.1

Reading cluster health and allocation

In plain words

Cluster health is green (all shards assigned), yellow (primaries assigned, some replicas not) or red (some primary shard is not assigned, so data is unavailable).

The problem it solves

A yellow or red status tells you something is wrong but not what. The allocation explain API tells you why.

What it does

  • GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason lists problem shards.
  • GET _cluster/allocation/explain explains why a shard is not assigned: disk watermark, no matching node, allocation filter, too many shards per node, or a failed allocation count.
  • Always start here before changing settings.

What does red mean?

At least one primary shard is unassigned, so some data cannot be read or written.

12.2

Hot shards and uneven load

In plain words

A hot node does more work than its peers, usually because it holds more shards of busy indices or because the busiest data stream writes to few shards.

The problem it solves

One node at 95 percent CPU while the others idle makes indexing slow and queries time out, even though total capacity is plentiful.

What it does

  • Check GET _cat/nodes?v&h=name,cpu,heap.percent,load_1m,disk.used_percent and GET _cat/allocation?v for imbalance.
  • Cause 1: a write index with 1 primary shard receives all writes on one node. Use more primaries (sized for the write rate) or more rollover shards.
  • Cause 2: routing or a custom _routing value sends most documents to one shard.
  • Cause 3: a few nodes hold the big, frequently searched indices. Use shard allocation awareness and index.routing.allocation.total_shards_per_node to spread them.
  • Note: replicas also do searches, so more replicas spread read load, not write load.

12.3

Shard sizing and count arithmetic

In plain words

Each shard is a Lucene index with memory and file overhead. Too many small shards waste heap; a few huge shards recover and move slowly.

The problem it solves

Oversharding is the most common cause of unstable clusters: thousands of tiny shards and a heap full of overhead.

What it does

  • Target shard size: roughly 10 to 50 GB for most time series use; check the current Elastic sizing guidance.
  • Rule of thumb: keep the shard count per node within about 20 shards per GB of heap, so a 30 GB heap suits up to about 600 shards.
  • Example: 120 GB a day, 30 GB target, gives 4 primary shards a day; 30 days gives 120 primaries, or 240 shards with one replica.
  • Daily indices of 1 GB each with 5 shards waste the budget; use ILM rollover by size (for example max_primary_shard_size: 30gb) rather than by day.
Check yourself
How many shards for 30 days if each day has 4 primaries and 1 replica?

4 × 30 = 120 primaries, doubled by replicas is 240 shards.

12.4

Circuit breakers and heap pressure

In plain words

Circuit breakers stop a request that would use too much memory, returning an error instead of letting the node run out of heap.

The problem it solves

Without breakers one heavy aggregation could trigger an OutOfMemoryError and take the node down, causing shard movement for everyone.

What it does

  • Breakers: parent (total), request, fielddata, in-flight requests and accounting. The parent defaults to about 95 percent of heap with real memory tracking (check current defaults for your version).
  • Symptom: circuit_breaking_exception ... Data too large. See GET _nodes/stats/breaker.
  • Heap should be at most half of RAM and under about 31 GB so compressed object pointers stay enabled.
  • Causes: huge aggregations over high cardinality fields, large size values, bulk requests too big, fielddata on text fields.
  • Fixes: reduce request size, use composite aggregation paging, add nodes, fix mappings (use keyword plus doc values instead of fielddata).

Check yourself
Why keep heap under about 31 GB?

Above that the JVM stops using compressed object pointers, so more heap can hold fewer objects.

12.5

Thread pools and rejected requests

In plain words

Elasticsearch handles work in thread pools with bounded queues. When a queue is full the request is rejected with HTTP 429.

The problem it solves

A 429 on bulk indexing or searches means the node is saturated. Retrying immediately makes it worse.

What it does

  • GET _cat/thread_pool/write,search?v&h=node_name,name,active,queue,rejected shows pressure.
  • Write rejections: reduce bulk concurrency, increase bulk size moderately (5 to 15 MB per request is common), or add data nodes.
  • Search rejections: expensive queries, too many concurrent users, or slow disks.
  • Clients must back off exponentially on 429; Filebeat and Logstash do this automatically.
  • Do not just raise queue sizes; it hides the problem and uses more heap.
12.6

Indexing performance

In plain words

Indexing speed depends on bulk size, refresh interval, replicas during load, mappings and storage speed.

The problem it solves

Ingest cannot keep up, and lag grows in Kafka or Filebeat.

What it does

  • Use the bulk API with several parallel workers.
  • refresh_interval of 30s or more instead of 1s for log data reduces segment churn.
  • For a large initial load set number_of_replicas: 0, then restore it after.
  • Disable dynamic mapping explosion: use explicit templates, set index.mapping.total_fields.limit sensibly and dynamic: strict or runtime where suitable.
  • Use SSD or NVMe on hot nodes, and keep the translog on the same fast disk.

Search performance

  • Set a sensible search.max_buckets and make sure the data view uses the proper time field.
  • Make sure frozen or cold data is not queried by default; scope dashboards to hot data.
14.10

Scenario 10, certificates, TLS and authentication failures

In plain words

Kibana cannot reach Elasticsearch, Beats get x509: certificate signed by unknown authority, or users see 401 and 403.

The problem it solves

Security is on by default in recent versions, so a wrong CA, expired certificate or role causes access errors that look like outages.

What it does

  • Check certificate expiry: openssl s_client -connect es:9200 </dev/null | openssl x509 -noout -dates.
  • On ECK, the operator creates the CA and certs and stores the CA in a secret named <cluster>-es-http-certs-public; mount that CA into clients (Filebeat ssl.certificate_authorities).
  • 401 means bad credentials; 403 means the role lacks a privilege. Use GET _security/_authenticate and the role mappings.
  • Rotate service account tokens or API keys and update the secrets; expired API keys are a frequent cause after a long time.
  • Prevent: alert on certificate expiry and keep API keys in External Secrets.

Get the ECK CA

bashRead the CA from the secret
kubectl get secret quickstart-es-http-certs-public -n logging -o jsonpath='{.data.ca\.crt}' | base64 -d > ca.crt
openssl x509 -in ca.crt -noout -dates
