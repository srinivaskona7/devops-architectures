Section 1 of 22

CI/CD concepts and pipeline design

7 concepts · about 45 minutes

A pipeline is the automated path from a commit to a running service. Good pipeline design makes shipping boring, fast and safe, and it is the backbone of every other practice in this folder.

Goals
  • Distinguish continuous integration, continuous delivery and continuous deployment
  • Design a pipeline with fast feedback and a build once deploy many artifact flow
  • Place tests, scans and approvals at the right stage of a pipeline
1.1

Continuous integration

In plain words

Continuous integration (CI) means every developer merges small changes into the shared branch often, and every change is built and tested automatically by a server within minutes.

The problem it solves

When people work for weeks on private branches, merging becomes a painful event full of conflicts and surprises. Bugs are found long after the change that caused them, so they are expensive to trace.

What it does

  • Triggers a build and test run on each push and each pull request.
  • Gives a pass or fail signal that blocks merging when it fails.
  • Keeps the main branch always in a releasable state.
  • Produces the first trusted artifact, for example a container image, from a known commit.

What a minimal CI trigger looks like

yaml.github/workflows/ci.yml (minimal)
name: ci
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make test
Check yourself
What is the one rule that makes CI work?

The shared branch is merged into often and every merge is verified automatically, so it never stays broken for long.

1.2

Continuous delivery versus continuous deployment

In plain words

Continuous delivery means every change that passes the pipeline is ready to release at the push of a button. Continuous deployment goes one step further and releases it automatically with no human click.

The problem it solves

Teams confuse the two terms and either ship too slowly because of manual gates, or ship automatically without the tests and monitoring that make that safe.

What it does

  • Delivery: the artifact is built, tested and deployable to production, but a person approves the release.
  • Deployment: passing the pipeline is the approval. Needs strong tests, canary checks and fast rollback.
  • Both rely on the same pipeline. The difference is a single approval gate.

A manual gate is one setting

yamlDelivery adds an approval, deployment removes it
deploy-prod:
  needs: deploy-staging
  environment: production   # required reviewers configured on this environment means delivery
  # remove the reviewers rule and the job runs by itself, which is deployment
Note

Many organisations use deployment for staging and delivery for production. That is a normal middle path.

1.3

Stages of a pipeline

In plain words

A pipeline is a list of stages, and each stage is a group of jobs that must pass before the next group starts. A common order is build, test, scan, package, deploy and verify.

The problem it solves

Without a clear order, expensive or risky steps run too early or too late. Slow end to end tests block quick feedback, and deployments may run on code that was never scanned.

What it does

  • Cheap checks run first (lint, unit tests) so failures show in seconds.
  • Expensive checks (integration, end to end, load) run later or in parallel.
  • Only a build that passed all earlier stages is allowed to reach a deploy stage.
  • Every stage has a clear input and output, so a failure points to one place.

Stages as GitLab CI shows them

yaml.gitlab-ci.yml (stage order)
stages: [lint, build, test, publish, deploy]
unit:
  stage: test
  script: [make test]
build-image:
  stage: build
  script: [docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" .]
Check yourself
Why run lint before integration tests?

It fails in seconds, so developers learn about trivial problems without waiting for slow stages.

1.4

Fast feedback and the test pyramid

In plain words

The test pyramid says write many fast unit tests, fewer integration tests and very few end to end tests. Pipelines should be ordered the same way so the quickest signal arrives first.

The problem it solves

Suites made mostly of slow browser tests take an hour, fail randomly, and teach people to ignore or retry red builds.

What it does

  • Aim for a pull request check under ten minutes. Many teams hold a budget and treat breaches as bugs.
  • Unit tests: milliseconds each, no network. Integration tests: real database in a container. End to end: a handful covering critical journeys.
  • Run the fast layer on every push and the slow layer on merge or on a schedule if needed.

Splitting by speed

yamlFast job gates the slow job
jobs:
  unit:
    runs-on: ubuntu-latest
    steps: [{uses: actions/checkout@v4}, {run: make unit}]
  integration:
    needs: unit          # only starts when the quick job is green
    runs-on: ubuntu-latest
    steps: [{uses: actions/checkout@v4}, {run: make integration}]
Check yourself
What should you do about a flaky test?

Quarantine or fix it quickly. Retrying hides the problem and trains people to distrust the pipeline.

1.5

Build once, deploy many

In plain words

Build the artifact a single time, give it an immutable identity such as a digest, and move that exact artifact through dev, staging and production. Only configuration differs between environments.

The problem it solves

Rebuilding for each environment means production runs something that was never tested. A different base image or dependency version can slip in between the staging build and the production build.

What it does

  • Tag the image with the commit SHA and record the digest (sha256:...).
  • Promotion means updating which digest an environment points at, not rebuilding.
  • Environment settings come from ConfigMaps, Secrets or Helm values, never from build arguments.

Promote by digest

bashGet the digest and deploy that, not a tag
docker buildx imagetools inspect 111122223333.dkr.ecr.eu-west-1.amazonaws.com/shop:abc1234 \
  --format '{{json .Manifest.Digest}}'
# deploy using the digest, which cannot change underneath you
helm upgrade shop ./chart --set image.digest=sha256:0123abcd --namespace shop
Careful

A mutable tag such as latest can point at a different image tomorrow. Deploy by digest or by an immutable tag.

1.6

Pipeline as code

In plain words

The pipeline definition lives in the same repository as the application, in a text file such as .github/workflows/*.yml, Jenkinsfile or .gitlab-ci.yml, and is reviewed like any other code.

The problem it solves

Pipelines configured by clicking in a web UI cannot be reviewed, rolled back, copied or recreated after a disaster. Nobody knows who changed what.

What it does

  • Changes to the pipeline go through pull requests, with history and blame.
  • A branch can carry its own pipeline change and test it before merge.
  • The same definition can be reused across repositories through templates, reusable workflows or shared libraries.

Keep pipeline logic thin

bashPipeline calls the same scripts a developer runs
# Makefile targets are the single source of truth, CI only calls them
make lint
make test
make image TAG="$(git rev-parse --short HEAD)"
Tip

If a developer cannot run the same steps locally, debugging becomes a cycle of push and wait. Put the logic in scripts or a Makefile and keep the YAML to orchestration.

Check yourself
Why keep pipeline files next to the code?

They are versioned, reviewed and branched together with the application they build.

1.7

Environments and promotion

In plain words

An environment is a place where the service runs, such as dev, staging and production. Promotion is moving a tested artifact from one to the next, with rising confidence at each step.

The problem it solves

Deploying straight to production is risky, but environments that differ greatly from production give false confidence.

What it does

  • Each environment has its own namespace or cluster, its own credentials and its own configuration.
  • Gates between them can be automatic (tests pass) or manual (approval).
  • Keep staging close to production in version and shape, even if smaller in size.
  • Production credentials are only available to production jobs.

Namespaces per environment on one cluster

yamlKustomize overlay chooses the environment
# overlays/staging/kustomization.yaml
resources: [../../base]
namespace: shop-staging
images:
  - name: shop
    digest: sha256:0123abcd
Check yourself
What should differ between staging and production?

Scale, secrets and endpoints. The image and the deployment method should be identical.

Section 2 of 22

Trunk-based development and release flows

7 concepts · about 45 minutes

The branching model decides how often code integrates and how releases are cut. Pipelines are designed around it, so pick the model first.

Goals
  • Compare trunk-based development, GitHub flow and Gitflow
  • Use short-lived branches, required checks and merge queues
  • Tag and version releases so artifacts can be traced to a commit
2.1

Trunk-based development

In plain words

Everyone commits to one main branch (the trunk), either directly or through very short-lived branches that last hours or a day or two. Unfinished work is hidden behind feature flags.

The problem it solves

Long-lived branches diverge from main. The longer they live, the harder and riskier the merge, and the less often anyone tests the combined result.

What it does

  • Small pull requests merge to main several times per day.
  • Main is always releasable, protected by required checks.
  • Incomplete features ship dark behind a flag, so merging is separated from releasing.
  • Research on delivery performance (DORA) links trunk-based practice to higher deployment frequency.

Daily flow

bashShort-lived branch
git switch main && git pull --ff-only
git switch -c fix/timeout-retry
# ...small change...
git commit -am "Retry upstream call once on timeout"
git push -u origin fix/timeout-retry    # open a pull request, merge when green
Check yourself
How can unfinished work live on main safely?

Behind a feature flag that is off, so the code is deployed but not active.

2.2

GitHub flow

In plain words

GitHub flow is a light version of trunk-based work. Branch from main, open a pull request, get review and green checks, merge, and deploy from main.

The problem it solves

Teams need a simple, shared rule for how changes reach production without the ceremony of release branches.

What it does

  • One long-lived branch (main). Everything else is a feature branch.
  • The pull request is the place for review, discussion and automated checks.
  • Merge triggers deployment, often to staging first.

Branch protection as code

bashRequire checks on main with the GitHub CLI
gh api -X PUT repos/ORG/REPO/branches/main/protection --input - <<'JSON'
{
  "required_status_checks": {"strict": true, "contexts": ["test"]},
  "enforce_admins": true,
  "required_pull_request_reviews": {"required_approving_review_count": 1},
  "restrictions": null
}
JSON
Note

Rulesets are the newer way to express the same rules in GitHub. Check the current docs for syntax.

2.3

Gitflow and release branches

In plain words

Gitflow uses long-lived develop and main branches plus feature, release and hotfix branches. It suits software shipped in versions that several supported releases must coexist.

The problem it solves

Some products (installed software, libraries, firmware) must patch version 2.3 while building 3.0. A single trunk cannot express that.

What it does

  • Release branches stabilise a version while new work continues on develop.
  • Hotfixes branch from the released tag, then merge back.
  • It adds merge overhead and delays integration, which is why web services usually avoid it.

A release branch for a supported version

bashCut and patch a release branch
git switch -c release/2.3 v2.3.0       # start from the released tag
git cherry-pick 4f3a9c1                # take the fix from main
git tag v2.3.1 && git push origin release/2.3 v2.3.1
Check yourself
When is a release branch justified?

When you must keep supporting an older version while developing the next one.

2.4

Required checks and branch protection

In plain words

Branch protection lets the platform refuse a merge until named checks pass and reviewers approve. It turns the pipeline from advice into a gate.

The problem it solves

If checks are optional, a rushed merge on a Friday skips them, and the next person inherits a broken main.

What it does

  • Required status checks must be green and up to date with the target branch.
  • Reviews can be required from code owners listed in a CODEOWNERS file.
  • Force pushes and deletion of main can be blocked, and administrators can be included in the rules.
  • Signed commits can be required where the audit policy needs it.

CODEOWNERS

text.github/CODEOWNERS
# last matching pattern wins
*                    @org/platform-team
/deploy/             @org/sre
/.github/workflows/  @org/security
Tip

Make changes to workflow files require review from the security or platform team. The pipeline is a privileged place.

Check yourself
Why mark a check as required rather than just visible?

Only required checks block the merge button.

2.5

Merge queues

In plain words

A merge queue tests each pull request combined with the ones ahead of it before merging, so main never receives a combination that was not tested.

The problem it solves

Two pull requests can each pass alone and break main together. On busy repositories, forcing authors to rebase and rerun checks repeatedly wastes hours.

What it does

  • Pull requests join a queue, the platform builds a temporary branch of main plus queued changes, and runs the required checks.
  • On success it merges automatically, on failure it removes the pull request and continues.
  • In GitHub Actions the workflow must also listen to the merge_group event.

Workflow that supports the queue

yamlListen to merge_group as well
name: ci
on:
  pull_request:
  merge_group:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make test
Careful

If the required check does not run on merge_group, the queue waits forever. This is a common setup mistake.

2.6

Versioning and tagging

In plain words

A version number and a tag give a release a name that humans and machines can refer to. Semantic versioning uses MAJOR.MINOR.PATCH, where MAJOR breaks compatibility, MINOR adds features and PATCH fixes bugs.

The problem it solves

Without a name, nobody can say which commit runs in production, or what changed between two releases.

What it does

  • Git tags such as v1.4.2 point at a commit. Annotated tags carry a message and author.
  • Image tags can include both the version and commit, for example 1.4.2 and sha-4f3a9c1.
  • Conventional commits (feat:, fix:) let tools compute the next version and the changelog automatically.

Tagging and building from the tag

yamlRelease workflow triggered by tags
name: release
on:
  push:
    tags: ["v*.*.*"]
jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
      - run: echo "Releasing ${GITHUB_REF_NAME}"
Check yourself
What should an image tag tell you?

Which commit and which version it was built from, so production can be traced to source.

2.7

Monorepo and polyrepo pipelines

In plain words

A monorepo holds many services in one repository, a polyrepo gives each service its own. Each choice changes how pipelines decide what to build.

The problem it solves

In a monorepo, building and testing everything for every change is slow. In a polyrepo, shared pipeline logic gets copied and drifts.

What it does

  • Path filters run a workflow only when relevant directories change.
  • Build tools with caches and affected-target detection (Bazel, Nx, Turborepo) skip unchanged work.
  • Polyrepos share logic through reusable workflows or templates stored in one platform repository.

Path filters

yamlRun only when this service changes
name: orders-ci
on:
  pull_request:
    paths:
      - "services/orders/**"
      - ".github/workflows/orders-ci.yml"
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make -C services/orders test
Careful

A required check that is skipped by path filters stays pending and can block merges. Use a small always-running job that aggregates results, or check the platform docs for skipped-check behaviour.

GitHub Actions fundamentals

7 concepts · about 45 minutes

GitHub Actions runs workflows defined in YAML files under .github/workflows/. This section covers the building blocks you will use in every pipeline.

Goals
  • Read a workflow file and explain events, jobs, steps and runners
  • Use contexts, expressions and conditions to control what runs
  • Speed up jobs with matrix builds, caching and artifacts
3.1

Workflows, jobs and steps

In plain words

A workflow is one YAML file. It contains jobs, and each job contains steps. Jobs run on separate machines at the same time unless you order them. Steps inside a job run in sequence on the same machine and share its filesystem.

The problem it solves

You need a way to describe automation that is versioned with the code, runs on clean machines, and can be split into independent parts for speed.

What it does

  • A step either runs a shell command (run) or an action (uses), a reusable unit published as a repository.
  • needs creates order between jobs. Without it, jobs run in parallel.

Contexts, expressions and conditions

In plain words

What it does

Dependency caching

In plain words

The cache action stores files such as downloaded packages under a key, and restores them in a later run when the key matches.

The problem it solves

Downloading the same dependencies on every run adds minutes and depends on external registries.

What it does

  • actions/cache takes a path, a key and optional restore-keys for partial matches.
  • Build the key from a hash of the lock file, for example hashFiles('**/go.sum'). A changed lock file makes a new cache.
  • Many setup actions (setup-node, setup-go, setup-python) have a built-in cache option.
  • Caches are scoped by branch. A pull request can read the default branch cache but not the reverse. Old caches are evicted when the repository passes its size limit.

Manual cache step

yamlCache the Go module directory

  • For container images, push to a registry instead.

4.4

Concurrency control

In plain words

The concurrency key gives runs a group name. Only one run per group is active at a time, and you choose whether the older run is cancelled or the new one waits.

The problem it solves

Two deploys to the same environment at once can overwrite each other. Ten quick pushes to a pull request waste minutes on runs nobody will look at.

What it does

  • For pull request CI, use cancel-in-progress: true so only the latest push is tested.
  • For deployments, keep cancel-in-progress: false so a running deploy is never cut in half. Newer runs queue, and pending ones in the same group are replaced by the newest.
  • Group names can use expressions such as the ref or environment name.

Two common patterns

yamlCI cancels old runs, deploy does not

  pull_request:

    branches: [main]

  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
jobs:
  deploy:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    concurrency:
      group: deploy-production
      cancel-in-progress: false
    steps:
      - run: echo "deploying"

5.1

The GITHUB_TOKEN and permissions

In plain words

Every run gets an automatic token called GITHUB_TOKEN. The permissions: key sets exactly what that token may do, such as read contents or write packages.

The problem it solves

A token with broad write access lets a compromised step push code, change releases or edit other workflows.

  • Common scopes are contents, packages, pull-requests, id-token and attestations.
  • Once you set any permission, all unspecified ones become none.
  • The default for new repositories and organisations should be set to read-only in settings.

5.2

OIDC federation to AWS

In plain words

Instead of storing an AWS access key in GitHub, the workflow asks GitHub for a short-lived signed identity token (a JWT). AWS verifies it and hands back temporary credentials for an IAM role.

The problem it solves

Stored access keys are long-lived, can leak through logs or forks, and need manual rotation. Nobody knows which workflow used them.

What it does

  • AWS trusts GitHub as an OIDC identity provider at token.actions.githubusercontent.com.
  • The role trust policy checks the sub claim (repository, branch or environment) and aud so only specific workflows can assume it.
  • Credentials last about an hour and are never stored.
  • The workflow needs permissions: id-token: write.

  • Use StringEquals for an exact value and StringLike with a wildcard only where needed.
  • Custom claim templates exist at organisation or repository level. Check the current docs.

6.1

When to self-host

In plain words

Self-hosting means you run the runner agent on machines you manage. It connects out to GitHub, picks up jobs and reports results.

The problem it solves

Hosted runners cannot reach private clusters, internal artifact stores or special hardware, and heavy use gets expensive.

What it does

  • Gives access to private VPC resources such as an EKS private endpoint or an internal registry.
  • Allows custom sizes, GPUs, arm builds and large persistent caches.
  • Moves security duty to you: patching, isolation and cleanup.
  • Never attach self-hosted runners to public repositories that accept fork pull requests. Strangers could run code on your network.

6.2

Ephemeral runners

In plain words

An ephemeral runner accepts exactly one job and then unregisters and disappears. A new clean one is created for the next job.

The problem it solves

Persistent runners accumulate files, caches, credentials and malware between jobs. One job can influence all later jobs.

What it does

  • The --ephemeral option, or the equivalent in controllers, makes the runner exit after one job.
  • Pair with autoscaling so capacity follows the queue.
  • Each job sees a clean filesystem, like a hosted runner.
  • Cache outside the runner (remote cache, registry cache) to keep builds fast.

6.6

Hardening runners

In plain words

A runner holds credentials and executes arbitrary code from the repository. Hardening limits what a malicious job can do and what it can reach.

The problem it solves

A compromised build is a pivot point. If the runner can reach everything, so can the attacker.

What it does

  • Separate runner groups by trust level: untrusted pull request builds and trusted deploy jobs never share runners.

  • Block access to the cloud metadata service from job pods, or require IMDSv2 with hop limit 1.
  • Run as non-root, drop capabilities, use read-only root filesystems where the tools allow.
  • Keep the runner image minimal and rebuild it regularly.

Jenkins architecture

7 concepts · about 45 minutes

Jenkins is the long-standing open source automation server. It is extremely flexible and widely deployed, and it needs more operating care than a hosted service.

7.1

Controller and agents

In plain words

The controller (formerly master) hosts the web UI, stores configuration and schedules builds. Agents are the machines or pods that actually run the build steps.

The problem it solves

Running builds on the controller makes it slow and risky: a bad build could read credentials or crash the scheduler that every team depends on.

What it does

  • The controller keeps job definitions, build history, credentials and plugins in JENKINS_HOME.
  • Agents connect to the controller using WebSocket or inbound TCP (JNLP) or are started over SSH.
  • Set the controller to zero executors so builds never run on it.
  • Labels on agents let a pipeline ask for agent { label 'linux && docker' }.

Builds then cannot run on it, protecting its credentials and keeping the scheduler responsive.

7.2

Executors, queue and workspaces

In plain words

An executor is one build slot on a node. The queue holds builds waiting for a free slot with a matching label. Each build gets a workspace, a directory where its files live.

The problem it solves

Without these controls, builds fight for CPU and disk, or two builds overwrite each other's files.

What it does

  • Number of executors on a node is its parallel capacity. For container agents, usually one build per pod.
  • The queue shows why a build waits, for example "waiting for next available executor".
  • Workspaces are reused on static agents. Clean them (cleanWs()) to avoid stale files.
  • Builds of the same job can be limited with disableConcurrentBuilds().

7.7

Pipeline execution and durability

In plain words

A Pipeline run is executed by the Groovy CPS engine on the controller, while steps such as sh run on agents. State is saved to disk so a run can survive a controller restart.

The problem it solves

Heavy Groovy logic in a Jenkinsfile runs on the controller, not the agent, and can slow down every team's builds. Long runs should survive restarts.

What it does

  • Keep Groovy light. Do real work in sh steps, scripts or containers.

  • Durability settings trade speed for safety. Check the current docs for PERFORMANCE_OPTIMIZED and MAX_SURVIVABILITY.
  • Resume works for steps like sh that run on the agent while the controller restarts.

8.1

Declarative pipeline structure

In plain words

A declarative Jenkinsfile has a fixed shape: pipeline { agent ... stages { stage ... steps ... } post ... }. The structure is validated before the build starts.

The problem it solves

Free-form scripts make pipelines inconsistent between teams and fail late. Declarative syntax gives a predictable layout that can be linted and understood by anyone.

What it does

  • agent says where to run. stages holds ordered stage blocks. steps lists the actions.
  • environment, options, parameters, triggers, tools configure the run.
  • post runs after stages depending on result.
  • Syntax errors are reported at start, before any step runs.

Complete example

groovyJenkinsfile
pipeline {
  agent { label 'linux' }
  options {
    timeout(time: 30, unit: 'MINUTES')
    disableConcurrentBuilds()
    buildDiscarder(logRotator(numToKeepStr: '30'))
  }
  environment {
    IMAGE = "111122223333.dkr.ecr.eu-west-1.amazonaws.com/shop"
    TAG   = "${env.GIT_COMMIT.take(7)}"
  }
  stages {
    stage('Test') {
      steps { sh 'make test' }
    }
    stage('Build') {
      steps { sh 'docker build -t $IMAGE:$TAG .' }
    }
  }
  post {
    always  { cleanWs() }
    failure { echo 'build failed' }
  }
}
Check yourself
When is a declarative Jenkinsfile validated?

Before the run starts, so structural errors fail immediately.

8.2

Stages, parallel and when

In plain words

Stages run in order. parallel runs several branches at once, and when decides whether a stage runs at all.

The problem it solves

Serial pipelines are slow, and running a deploy on every feature branch is unwanted.

What it does

  • parallel { stage('Unit') {...} stage('Lint') {...} } runs branches on separate executors.
  • failFast true stops the others as soon as one fails.
  • when { branch 'main' }, when { changeRequest() }, when { tag 'v*' }, when { expression { ... } } and anyOf, allOf, not combine conditions.
  • beforeAgent true avoids allocating an agent for a stage that will be skipped.

Parallel and when

groovyFragment
stage('Checks') {
  failFast true
  parallel {
    stage('Unit') { steps { sh 'make unit' } }
    stage('Lint') { steps { sh 'make lint' } }
  }
}
stage('Deploy') {
  when { branch 'main'; beforeAgent true }
  steps { sh './ci/deploy.sh staging' }
}

It evaluates the when condition before allocating an agent, saving resources for skipped stages.

In plain words

The problem it solves

10.2

Rules, workflow and conditions

In plain words

rules: decides whether a job is added to the pipeline, using conditions on variables, changed files and the pipeline source. workflow:rules does the same for the whole pipeline.

The problem it solves

Without rules, every push creates duplicate branch and merge request pipelines and every job runs everywhere.

What it does

  • if: $CI_PIPELINE_SOURCE == "merge_request_event" matches merge request pipelines.
  • if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH matches the default branch. changes: matches paths.
  • when: manual makes a job a button. allow_failure: true lets the pipeline pass anyway.
  • Rules are evaluated top to bottom, first match wins, and a job with no match is not created.

Rules in use

yamlAvoiding duplicate pipelines
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH
    - if: $CI_COMMIT_TAG
unit:
  script: [make test]
  rules:
    - changes: ["**/*.go", "go.mod"]
deploy-prod:
  script: [./deploy.sh production]
  rules:
    - if: $CI_COMMIT_TAG
      when: manual

In plain words

In GitOps, a Git repository describes what should run. An agent inside the cluster pulls that description and applies it continuously, instead of a pipeline pushing changes from outside.

The problem it solves

What it does

  • Git is the source of truth with history, review and rollback by revert.
  • The controller compares live state with Git and reports or corrects differences.
  • Cluster credentials stay inside the cluster. CI needs only write access to Git.
  • Four commonly cited principles are declarative, versioned and immutable, pulled automatically, and continuously reconciled.

12.4

Sync policies and options

In plain words

Sync means applying the Git state to the cluster. It can be manual (someone clicks sync) or automated, with extra switches that decide how aggressive it is.

The problem it solves

Automatic deletion or overwriting can surprise teams, while manual sync leaves clusters out of date.

What it does

  • retry with back-off helps with ordering problems. ignoreDifferences skips fields set by other controllers, for example replica counts managed by an HPA.

12.7

Drift detection and self-heal

In plain words

Drift is any difference between Git and the cluster, such as a manual kubectl edit. Argo CD compares continuously, marks the app OutOfSync, and can revert the change with self-heal.

The problem it solves

Hotfixes made with kubectl and never committed disappear on the next deploy or create mysterious differences between environments.

What it does

  • The controller refreshes on a timer (three minutes by default) and on webhooks from Git.
  • The diff ignores fields that controllers legitimately change when configured via ignoreDifferences.
  • selfHeal: true reverts drift. Without it, the app stays OutOfSync until someone syncs.
  • For emergencies, disable auto-sync on that app, apply the fix, then commit it to Git and re-enable.

Break glass procedure

bashPause auto-sync during an incident
argocd app set shop-prod --sync-policy none     # stop reverting while you investigate
kubectl -n shop scale deploy/shop --replicas=10
# after the incident, commit the real fix to Git, then re-enable
argocd app set shop-prod --sync-policy automated --self-heal
Check yourself
How do you do an emergency change without fighting self-heal?

Temporarily disable auto-sync, apply the change, commit it to Git and re-enable.

In plain words

15.4

Signing images with cosign

In plain words

Signing attaches a cryptographic proof that a specific digest was published by a specific identity. cosign from the Sigstore project signs and verifies OCI artifacts.

The problem it solves

Anyone with registry write access, or an attacker who gets it, can replace an image. Without signatures the cluster has no way to tell the legitimate image from a tampered one.

What it does

  • Keyless signing: the CI job gets an OIDC token, Sigstore's Fulcio issues a short-lived certificate tied to the workflow identity, and the signature is logged in the Rekor transparency log. No long-lived private key to protect.
  • Key-based signing: a key pair, with the private key in AWS KMS (awskms:// URIs).
  • Always sign the digest, never a tag.
  • Verification checks the certificate identity and issuer, not just that some signature exists.

Deployment strategies and progressive delivery

8 concepts · about 55 minutes

How you swap the old version for the new one decides how many users see a bad release and how fast you can recover.

Goals
  • Choose between rolling, blue-green and canary releases for a given risk level
  • Run canaries with Argo Rollouts or Flagger using metric analysis
  • Handle feature flags, database migrations and rollbacks safely
16.1

Rolling updates

In plain words

A Kubernetes Deployment replaces pods gradually. New pods start, pass readiness, and then old pods are removed, so the service stays available.

The problem it solves

Stopping everything and starting the new version causes downtime. You need an update that keeps capacity while it changes.

What it does

  • maxSurge is how many extra pods may exist during the update. maxUnavailable is how many may be missing.
  • Readiness probes decide when a new pod receives traffic. Without them, traffic reaches pods that are not ready.
  • kubectl rollout undo reverts to the previous ReplicaSet. minReadySeconds and progressDeadlineSeconds add safety.
  • Both versions run at the same time, so the change must be backward compatible.

Strategy and probe

yamldeployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop
  namespace: shop
spec:
  replicas: 4
  minReadySeconds: 10
  progressDeadlineSeconds: 300
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels: {app: shop}
  template:
    metadata:
      labels: {app: shop}
    spec:
      containers:
        - name: shop
          image: 111122223333.dkr.ecr.eu-west-1.amazonaws.com/shop@sha256:4f3a9c1d2b7e8a0c5d6e7f8091a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4
          ports: [{containerPort: 8080}]
          readinessProbe:
            httpGet: {path: /healthz, port: 8080}
            periodSeconds: 5

16.2

Blue-green deployments

In plain words

Run two complete environments: blue is live, green has the new version. When green passes checks, switch traffic to it in one step. Blue stays for instant rollback.

The problem it solves

A rolling update mixes versions and rolling back means another rollout. Some changes need a clean cutover with a quick return path.

What it does

  • The switch is a Service selector change, an Ingress or load balancer target group change, or a weighted rule.
  • You can test green through a preview Service before the switch.
  • It costs double capacity for a while. State and database changes still need compatibility between versions.

Switching by selector

Check yourself
What is the main advantage over rolling updates?

Instant, clean cutover and rollback with no mixed versions serving at once.

16.3

Canary releases

In plain words

A canary sends a small share of traffic, for example 5 percent, to the new version, watches metrics, and increases the share only if the version behaves well.

The problem it solves

Staging cannot reproduce production traffic. A bug found by 5 percent of users is far cheaper than one found by all of them.

What it does

  • Steps raise weight in stages (5, 25, 50, 100) with pauses.
  • Automated analysis compares metrics such as error rate and latency to thresholds. Failure aborts and returns traffic to the stable version.
  • Traffic splitting needs support from an ingress controller, service mesh or Gateway API. Without it, weight is approximated by pod ratio.

Canary gates are only as good as the metrics they read. Define the success metrics before you automate.

16.4

In plain words

Argo Rollouts adds a Rollout resource, a replacement for Deployment, with built-in canary and blue-green strategies, traffic routing and automated analysis.

The problem it solves

A plain Deployment cannot do weighted traffic steps, pauses, or metric-based abort.

  • strategy.canary.steps lists setWeight, pause and analysis steps.

16.7

Database migrations

In plain words

Schema changes must work with both the old and new application version, because during any rollout both run at once. The safe method is expand and contract.

The problem it solves

Renaming a column while the old pods still read it breaks them. A rollback of the app cannot undo a destructive schema change.

  • Run migrations as a separate step (a Job, Argo CD PreSync hook, or Helm hook), not on app startup in every replica.

Pipeline security and secrets

The pipeline can change production, so it is a prime attack target. Secure it as you would a production system.

Where pipeline time goes

In plain words

Before optimising, measure. Split the total time into queue wait, setup, dependency download, build, test and publish. One or two of these usually dominate.

Parallelism, sharding and cancellation

In plain words

Run independent work at the same time, split big test suites into shards, and cancel runs nobody needs any more.

The problem it solves

A single serial job of 40 minutes delays every change, and obsolete runs consume capacity.

What it does

  • Separate jobs for lint, unit tests and image build can run in parallel. Use needs only where truly needed.
  • Shard tests with a matrix, giving each job a slice, then add a final job that checks all shards.
  • Use concurrency with cancel-in-progress for pull request runs, and skip documentation-only changes with path filters.
  • Balance by timing data when the tool supports it, so shards finish together.

18.4

Cost control

In plain words

Pipeline cost is minutes times price, plus storage for artifacts and caches. The largest savings come from running less, not from cheaper machines.

The problem it solves

Unmanaged pipelines accumulate scheduled jobs, large retained artifacts and oversized runners.

  • Set artifact retention-days, prune old caches, and expire registry images with lifecycle rules.
  • For self-hosted, use spot nodes and scale to zero outside working hours.
  • Review the top ten most expensive workflows monthly.

18.5

The four DORA metrics

In plain words

DORA research identifies four measures of software delivery performance: deployment frequency, lead time for changes, change failure rate and time to restore service. The last two measure stability, the first two measure throughput.

The problem it solves

Without shared measures, teams argue about whether delivery is improving, and local optimisation (speed with no stability) goes unnoticed.

What it does

  • Deployment frequency: how often you deploy to production.
  • Lead time for changes: from commit (or merge) to running in production.
  • Change failure rate: the share of deployments causing a failure that needs a fix, rollback or hotfix.
  • Time to restore: how long to recover from a failed production change or incident. Newer DORA reports also use a rework-related measure; check the current report for definitions.
  • Use them to find constraints for a team, not to rank people or teams against each other.

  - {type: deployment, fields: [sha, environment, finished_at, status]}
  - {type: incident, fields: [started_at, resolved_at, caused_by_sha]}

18.6

Measuring DORA from the pipeline

In plain words

19.1

Path filters for monorepos

In plain words

A workflow can run only when certain files change, using paths on the trigger or a filter step inside the job.

The problem it solves

In a repository with ten services, building everything on each commit wastes minutes and hides the real failure.

What it does

  • on.pull_request.paths skips the whole workflow when no listed file changed.
  • Caveat: a skipped required check stays pending and blocks merging. Use a filter job instead when the check is required.
  • dorny/paths-filter outputs one boolean per area; later jobs use if: needs.changes.outputs.api == 'true'.
  • Always include shared paths (libraries, the workflow file itself) in each filter.

Workflow

yaml.github/workflows/ci.yml
name: ci
on:
  pull_request:
jobs:
  changes:
    runs-on: ubuntu-latest
    outputs:
      api: ${{ steps.f.outputs.api }}
      web: ${{ steps.f.outputs.web }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: f
        with:
          filters: |
            api:
              - 'services/api/**'
              - 'libs/**'
            web:
              - 'services/web/**'
              - 'libs/**'
  api:
    needs: changes
    if: needs.changes.outputs.api == 'true'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make -C services/api test
  gate:
    if: always()
    needs: [changes, api]
    runs-on: ubuntu-latest
    steps:
      - run: test "${{ contains(needs.*.result, 'failure') }}" = "false"
Tip

Jenkins to GitHub Actions and a pipeline template library

7 concepts · about 60 minutes

Migration is mostly inventory and habit change; the syntax translation is the easy part.

Goals
  • Plan and execute a Jenkins to GitHub Actions migration in stages
  • Translate common Jenkinsfile constructs to workflow syntax
  • Design a versioned template library so teams get a golden path
20.1

Inventory and migration plan

In plain words

Before converting anything, list every job, what it does, who owns it and what it needs.

The problem it solves

Jenkins instances accumulate hundreds of jobs, plugins and hidden credentials. Converting blindly moves the mess.

What it does

  • Export a list of jobs with last build date; retire anything unused for six months.
  • Group jobs by pattern (build, test, deploy, cron) and migrate one pattern as a template.
  • Record credentials, plugins, agents and webhooks per job.
  • Pilot with two friendly teams, then migrate in waves with a firm shutdown date. Run both systems side by side during a wave only.

Listing jobs

bashJenkins job list
curl -s -u "$USER:$TOKEN" "$JENKINS_URL/api/json?tree=jobs[name,lastBuild[timestamp]]" | jq -r '.jobs[] | [.name, (.lastBuild.timestamp // 0)] | @tsv'
20.2

Translating a Jenkinsfile

In plain words

Most declarative constructs have a direct equivalent: stages become jobs, steps become steps, agents become runs-on.

The problem it solves

Without a map, each person invents their own translation and results differ.

What it does

  • agent { label 'linux' } becomes runs-on: [self-hosted, linux] or a hosted runner.
  • stage becomes a job; parallel becomes jobs with no needs.
  • when { branch 'main' } becomes if: github.ref == 'refs/heads/main'.
  • environment { } becomes env:; post { always { } } becomes a step with if: always().
  • input (manual approval) becomes an environment with required reviewers.

Side by side

groovyJenkinsfile
pipeline {
  agent { label 'linux' }
  stages {
    stage('Test')  { steps { sh 'make test' } }
    stage('Deploy') {
      when { branch 'main' }
      steps { sh './deploy.sh' }
    }
  }
  post { always { junit 'reports/*.xml' } }
}
yamlEquivalent workflow
name: ci

    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh
20.3

Credentials, agents and plugins

In plain words

The hard parts of migration are secrets, build machines and plugin behaviour.

The problem it solves

Jenkins credentials are stored centrally and often long-lived. Plugins quietly provide features no one documented.

What it does

  • Replace stored cloud keys with OIDC roles. Move remaining secrets into GitHub environment secrets or an external secret store.
  • Static Jenkins agents become runners: hosted ones, or Actions Runner Controller pods in your Kubernetes cluster.
  • For each plugin find the Actions equivalent, a CLI call, or drop the feature (for example Blue Ocean has no equivalent need).
  • Rotate every credential that was copied or ever visible in logs.
Check yourself
Why rotate credentials during migration?

Copying secrets between systems widens exposure and old values may have appeared in logs.

20.4

Shared libraries to reusable workflows

In plain words

Jenkins shared libraries hold common pipeline code. In Actions, reusable workflows and composite actions fill that role.

The problem it solves

Hundreds of Jenkinsfiles call buildJavaApp(...). You need the same one-line experience.

What it does

  • A function with parameters becomes a reusable workflow with inputs.
  • Helper steps become composite actions.
  • Keep a thin caller workflow per repository so teams still own triggers and settings.
  • Provide a migration script or template repository that creates the caller file.

Thin caller

20.5

Platform template library design

In plain words

A template library is a set of versioned reusable workflows and actions that encode the organisation's standard pipeline: build, test, scan, sign, deploy.

The problem it solves

Without it every team builds a slightly different, slightly insecure pipeline.

What it does

  • One repository, semantic version tags, a changelog, and a v3 moving major tag for consumers.
  • Templates per language and per deploy target; each includes the security steps by default (scan, SBOM, provenance).
  • Inputs for what varies; opinion for the rest. Provide escape hatches without forking.
  • Test templates with sample repositories in CI, and use Dependabot or Renovate to move consumers between versions.
20.6

Versioning and governing the library

In plain words

Consumers need stability. Maintainers need to ship fixes everywhere quickly.

The problem it solves

A breaking change in a shared template can break hundreds of pipelines at once.

What it does

  • Patch and minor releases move the v3 tag; breaking changes create v4 and need a migration note.
  • Security fixes may be forced centrally using organisation required workflows or rulesets; check the current availability for your plan.
  • Track adoption: which repositories use which version (code search in the organisation).
  • Deprecate with warnings in the workflow log, then remove after a published date.
Check yourself
How does a consumer get a template bug fix without editing files?

They reference a moving major tag such as v3, which maintainers advance for compatible releases.

20.7

Cutover and rollback checklist

In plain words

A cutover moves the trigger from Jenkins to Actions for one service and keeps a way back.

The problem it solves

A missed webhook or a different artifact name can break deployments on the day you switch.

What it does

  • Run both systems in parallel and compare artifacts and test counts.
  • Switch the deploy trigger last; disable the Jenkins job rather than deleting it for one release cycle.
  • Check: artifact names, version numbers, notifications, branch protection checks, and scheduled jobs.
  • Archive Jenkins build history (or export logs) for compliance before decommissioning.

Section 21 of 22

Pipeline troubleshooting and release engineering

8 concepts · about 60 minutes

Pipelines fail in a few repeating ways. Knowing them turns a stuck afternoon into a five minute fix. The second half covers how a release becomes a trustworthy, traceable artifact.

Goals
  • Diagnose common pipeline failures systematically
  • Version, tag and sign releases so they can be trusted and traced
  • Generate changelogs automatically from commit history
21.1

Method for debugging a failing pipeline

In plain words

Treat the failure like any incident: find what changed, reproduce it, then fix the cause rather than rerunning.

The problem it solves

Rerunning until green hides flaky tests, races and drifting dependencies, and trains the team to ignore red builds.

What it does

  • Read the first error, not the last; later errors are usually consequences.
  • Ask what changed: code, workflow, runner image, dependency, secret, external service.
  • Reproduce locally or in the same container image the job uses.
  • GitHub Actions: enable step debug logging by setting the secret ACTIONS_STEP_DEBUG to true; re-run with the debug option.
  • Record the root cause in the pull request or an issue.
21.2

Failure class, flaky tests

In plain words

A flaky test passes and fails on the same code. Typical causes are timing, shared state, ordering and external services.

The problem it solves

Flakiness destroys trust in CI and wastes reruns, and it multiplies: ten tests with 2 percent flake rate each fail about 18 percent of runs.

What it does

  • Arithmetic: probability that at least one of 10 independent tests flakes is 1 minus 0.98 to the 10th power, about 0.183.
  • Quarantine: move a flaky test to a non-blocking job with a ticket and a deadline.
  • Fix causes: replace sleeps with waits on conditions, isolate data per test, mock the network, fix random seeds.
  • Track flake rate per test from JUnit results; many CI systems and tools report it.
Check yourself
Pass rate of a suite with 20 tests that each flake 1 percent of the time?

0.99 to the 20th is about 0.818, so roughly 18 percent of runs fail.

21.3

Failure class, cache, dependency and runner problems

In plain words

Many failures come from the environment around the code: stale caches, unpinned dependencies, full disks and rate limits.

The problem it solves

The error message points at your code but the cause is elsewhere, so engineers debug the wrong layer.

What it does

  • Stale or corrupt cache: change the cache key, or run once without cache.
  • Unpinned dependencies: a new upstream release breaks the build; commit lock files and pin base images by digest.
  • Docker Hub pull rate limits: authenticate pulls or use an ECR pull-through cache.
  • Runner out of disk or memory: look for No space left on device or killed processes (exit code 137); clean images or use a larger runner.
  • Self-hosted runner offline: check the runner pod or service and its registration token.

Quick checks

bashOn a runner or in a job
df -h
docker system df
free -m
docker run --rm -it ubuntu:22.04 bash   # reproduce in a clean image
21.4

Failure class, permissions, OIDC and secrets

In plain words

Authentication failures are the most common reason a deploy job fails on first use.

The problem it solves

Cloud errors are terse (Not authorized to perform sts:AssumeRoleWithWebIdentity) and the cause may be a single character in a trust policy.

What it does

  • OIDC: the job needs permissions: id-token: write. Without it no token is issued.
  • The IAM trust policy sub condition must match the repository, branch or environment of the run, for example repo:acme/shop:environment:production.
  • Secrets are not available to pull requests from forks, and environment secrets only to jobs that declare the environment.
  • GITHUB_TOKEN permissions default can be read only; set permissions: per job explicitly.
Check yourself
Which permission makes a job able to request an OIDC token?

id-token: write

21.5

Failure class, deployment and timeout problems

In plain words

A deploy job can pass its commands and still leave a broken release, or hang until the timeout.

The problem it solves

kubectl apply returning success does not mean pods are healthy.

What it does

  • Wait for rollout: kubectl rollout status deploy/api --timeout=180s; fail the job and roll back on timeout.
  • Common causes: image pull error, failing readiness probe, quota exceeded, missing secret.
  • Set timeout-minutes on every job so a hang does not run for six hours (the default job limit).
  • Print kubectl describe and recent events on failure, so the log has the answer.

Safe deploy step

bashdeploy.sh
kubectl apply -f k8s/
if ! kubectl rollout status deploy/api --timeout=180s; then
  kubectl describe deploy/api | tail -30
  kubectl get events --sort-by=.lastTimestamp | tail -20
  kubectl rollout undo deploy/api
  exit 1
fi
21.6

Versioning schemes

In plain words

A version is a promise about what changed. Semantic Versioning writes it as MAJOR.MINOR.PATCH.

The problem it solves

Without a rule, consumers cannot tell if upgrading is safe, and operators cannot tell what is running.

What it does

  • SemVer: MAJOR for breaking changes, MINOR for compatible features, PATCH for compatible fixes. Good for libraries and APIs.
  • CalVer (for example 2026.10.3): good for applications released on a schedule.
  • Container images: tag with the version and the git SHA, and deploy by digest. Never deploy latest.
  • Pre-releases: 1.4.0-rc.1; build metadata after + does not affect precedence.

Image tags

bashTag and push

docker build -t registry.example.com/shop/api:${VERSION} -t registry.example.com/shop/api:${VERSION}-${SHA} .
21.7

Changelogs and release notes

In plain words

A changelog tells users what changed between versions. It can be generated from Conventional Commit messages.

The problem it solves

Hand-written release notes are skipped under time pressure, so users and support find out about changes from incidents.

What it does

  • Follow the Keep a Changelog layout: Added, Changed, Fixed, Removed, Security.
  • Tools: release-please, semantic-release, git-cliff and GitHub's generated release notes read commit or PR titles.
  • Quality depends on commit titles; enforce the format with commitlint or a PR title check.
  • Link each entry to the pull request and mention migrations or breaking changes prominently.

git-cliff run

Note

21.8

Signing releases and provenance

In plain words

Signing proves who built an artifact. Provenance records how. Together they let a cluster refuse anything not built by your pipeline.

The problem it solves

A registry compromise or a stolen credential could replace an image with a malicious one that has the same tag.

What it does

  • cosign signs container images. Keyless signing uses the CI job's OIDC identity and records the signature in the public Rekor transparency log.
  • Generate an SBOM (Syft or Trivy) and attach it; produce SLSA provenance with the GitHub attestation or slsa-github-generator workflows.
  • Verify at admission with a policy controller (Kyverno, Sigstore policy-controller or Connaisseur) that checks the signer identity.
  • Sign the digest, not the tag, as tags move.

Commands

  --certificate-oidc-issuer https://token.actions.githubusercontent.com
Check yourself
Why sign the digest and not the tag?

Tags can be moved to different content; a digest names exactly one image.

Section 22 of 22

Database migration pipelines with Flyway and Liquibase

7 concepts · about 50 minutes

Application code can be rolled back in seconds. A schema change usually cannot. Treat migrations as first class releases.

Goals
  • Run schema migrations from a pipeline safely
  • Use the expand and contract pattern for zero downtime changes
  • Choose between Flyway and Liquibase and run them as Kubernetes jobs
22.1

Why migrations belong in the pipeline

In plain words

Schema changes are versioned scripts stored beside the code and applied in order by a tool, not typed into a console.

The problem it solves

Manual changes drift between environments and nobody knows which version of the schema production has.

What it does

  • Each change is a numbered, immutable script; the tool records applied scripts in a history table in the database.
  • The same scripts run in dev, staging and production, in that order.
  • Reviewers see schema changes in the same pull request as the code that needs them.
  • Never edit a script after it has been applied anywhere; add a new one. Both tools verify checksums and fail if an applied script changed.
22.2

Flyway basics

In plain words

Flyway applies SQL files named V1__create_table.sql, V2__add_index.sql in version order, and tracks them in the table flyway_schema_history.

The problem it solves

You want the simplest possible tool that anyone who knows SQL can use.

What it does

  • Versioned migrations V<version>__<description>.sql run once. Repeatable R__name.sql rerun when their checksum changes.
  • Commands: info, validate, migrate, repair, baseline. Use baseline to adopt an existing database.
  • Configuration via a file or environment variables such as FLYWAY_URL.
  • Some features (undo migrations, advanced checks) are in paid editions; check the current Flyway docs.

Example

sqldb/migration/V3__add_orders_status.sql
ALTER TABLE orders ADD COLUMN status VARCHAR(20);
UPDATE orders SET status = 'NEW' WHERE status IS NULL;
bashRun Flyway
flyway -url=jdbc:postgresql://db:5432/shop -user=shop -locations=filesystem:db/migration info
flyway -url=jdbc:postgresql://db:5432/shop -user=shop -locations=filesystem:db/migration migrate
22.3

Liquibase basics

In plain words

Liquibase describes changes as changesets in XML, YAML, JSON or SQL, each identified by id and author, and tracks them in DATABASECHANGELOG.

The problem it solves

You need database-agnostic definitions, preconditions and rollbacks across several engines.

What it does

  • A changelog file includes changesets; each runs once.
  • Preconditions skip or fail a changeset if the state is not as expected.
  • rollback blocks define how to reverse a changeset; many automatic rollbacks exist for simple changes.
  • Commands: status, validate, update, rollback, updateSQL (preview SQL without running it).

Changelog

yamldb/changelog.yaml
databaseChangeLog:
  - changeSet:
      id: 3-add-orders-status
      author: platform
      changes:
        - addColumn:
            tableName: orders
            columns:
              - column:
                  name: status
                  type: varchar(20)
      rollback:
        - dropColumn:
            tableName: orders
            columnName: status
Check yourself
What does updateSQL do?

Prints the SQL that update would run, without changing the database, so it can be reviewed.

22.4

Choosing between Flyway and Liquibase

In plain words

Both work well. Pick on team habits and portability needs.

The problem it solves

Switching later means rewriting history and re-baselining every database.

What it does

  • Flyway: plain SQL, tiny learning curve, good fit when you use one database engine.
  • Liquibase: abstract changes, preconditions, rollbacks and contexts; more concepts to learn.
  • Both have Spring Boot integration, Maven and Gradle plugins, and official container images.
  • Alternatives exist for specific stacks (Alembic for Python, Atlas, golang-migrate, Rails migrations).

22.5

Expand and contract for zero downtime

In plain words

Change the schema in compatible steps so old and new application versions both work during the rollout.

The problem it solves

During a rolling deploy, old and new pods run together. Renaming a column breaks whichever version does not expect it.

What it does

  • Expand: add the new column or table, nullable, with no code dependency. Backfill in batches.
  • Migrate: deploy code that writes both and reads the new one.
  • Contract: in a later release, after the old code is gone, drop the old column.
  • Rename = add new, copy, switch, drop old, over at least two releases. Avoid long locks: create indexes concurrently on PostgreSQL (CREATE INDEX CONCURRENTLY) and add constraints in a not-validated state first.

Safe index creation

sqlV7__index_orders_customer.sql
-- Flyway needs executeInTransaction=false for this statement
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_customer ON orders (customer_id);
Careful

Dropping a column in the same release that stops using it breaks any pod still running the old version.

Check yourself
Why drop the old column in a later release?

Old pods may still run during the first rollout and would fail if the column vanished.

22.6

Running migrations in Kubernetes

In plain words

Run migrations as a one-off Kubernetes Job or a Helm hook before the new application version, not inside every application pod at start-up.

The problem it solves

Five replicas starting together would each try to migrate. Tools lock the history table, but long migrations then block pod readiness and cause restarts.

What it does

  • A Job using the official flyway/flyway or liquibase/liquibase image, with the SQL baked into your own image or mounted from a ConfigMap.
  • Helm: helm.sh/hook: pre-install,pre-upgrade with hook-delete-policy. Argo CD: a PreSync hook.
  • Use a separate database user with DDL rights; the application user gets only DML rights.
  • Credentials from a secret created by External Secrets; never in the image.

Argo CD hook Job

yamlmigrate-job.yaml
apiVersion: batch/v1
kind: Job
metadata:

  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation

  backoffLimit: 0

    spec:
      restartPolicy: Never

          envFrom:
            - secretRef:
                name: shop-db-migrator
22.7

Testing, rollback and safety nets

In plain words

Test migrations against realistic data, and plan how to recover if one fails halfway.

The problem it solves

A migration that takes 2 seconds on a laptop can lock a 500 million row table for an hour in production.

What it does

  • In CI, start a database container (Testcontainers or a service container), apply all migrations from scratch, then run tests.
  • Also test the upgrade from the previous release's schema with sample data.
  • Rehearse in staging with a production-sized copy where allowed (masked data).
  • Take a snapshot before production migrations (RDS manual snapshot); prefer forward fixes over undo scripts.
  • Set lock_timeout and statement_timeout so a blocked migration fails fast instead of queuing behind a long query.

PostgreSQL guard rails

sqlsession settings
SET lock_timeout = '5s';
SET statement_timeout = '15min';
